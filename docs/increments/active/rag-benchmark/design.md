# RAG benchmark

## Problem

MemoryOS has unit and contract tests for every capability but no measurement of retrieval or answer quality. Limits,
chunk sizes, search sizes and model choices were set without numbers: the MEM-46 verification says representative
retrieval quality is not closed, and the chunk-size question (structured chunks average 82 tokens in `.docx`, 737 in
`.md` on staging) cannot be answered by reasoning. Every later tuning decision needs one repeatable benchmark that
measures the whole path an answer takes, not a single component.

## Reference

- Onyx `40eb240df` `backend/tests/regression/search_quality/`: a question set with ground-truth documents, run against
  the live search API; top-1/3/5/10 accuracy, rank, per-category results, and RAGAS `ResponseRelevancy`,
  `Faithfulness` and `FactualCorrectness` on the generated answer. `backend/onyx/evals/`: chat evals on a dataset
  (Braintrust). `backend/scripts/debugging/opensearch/benchmark_retrieval.py`: retrieval latency.
- Chroma, [Evaluating Chunking Strategies for Retrieval](https://www.trychroma.com/research/evaluating-chunking) and
  [`chunking_evaluation`](https://github.com/brandonstarxel/chunking_evaluation) (MIT): LLM-generated questions with
  exact source excerpts; token-level recall, precision and IoU, so larger chunks do not win by default.
- LightRAG [`lightrag/evaluation`](https://github.com/HKUDS/LightRAG/blob/main/lightrag/evaluation/README_EVALUASTION_RAGAS.md):
  RAGAS context recall/precision, faithfulness and answer relevancy over the running system.

Onyx's document-level ground truth cannot distinguish chunkings (every chunking finds the same document), and RAGAS
alone depends on the judging model. The benchmark combines the three: excerpt-level ground truth (Chroma) measured
through the live API (Onyx) with answer metrics (RAGAS).

## Decisions

1. **One dataset, excerpt-grounded.** Each case has a question, the language, categories, and one or more ground-truth
   excerpts (`documentId`, exact text, character range in the canonical extraction) plus an optional reference answer.
   Categories: keyword, semantic, table lookup, multi-part, cross-document, English, Vietnamese, and unanswerable (no
   excerpt; the correct behaviour is to say the documents do not contain it). Cases are generated by an LLM from
   sampled excerpts (Chroma's pipeline, with its duplicate and excerpt-validity filters), then reviewed by a person;
   only reviewed cases are in the scored set. Cases are never written by the system under test.
2. **Four layers, each scored separately, same cases.**
   - *Chunking (offline):* token-level recall, precision and IoU of candidate chunkers over the canonical extractions
     with the production embedding model, in memory. Used to choose chunk policy before any reindex.
   - *Search (live):* `POST /api/search` as a benchmark user. Document hit@1/3/5/10 and MRR (Onyx), excerpt token recall
     and precision within the top results (Chroma), and p50/p95 latency.
   - *Chat (live):* a new session per case through the chat API with the tenant default model. Answer correctness
     against the reference (RAGAS `FactualCorrectness`), `Faithfulness` to the retrieved evidence, citation precision
     (a cited source contains a ground-truth excerpt), abstention on unanswerable cases, tool calls, tokens, cost and
     latency from the persisted message.
   - *Deep research (live, optional):* the same answer metrics on multi-part cases only; slow and expensive.
3. **Judge pinned and separate.** RAGAS metrics run with a named judge model and temperature 0, recorded in the run;
   the judge is never the model under test. Deterministic metrics (hits, token recall, citations, abstention by
   rubric) are reported first; LLM-judged metrics are secondary.
4. **Runs are comparable.** A run records the dataset hash, git SHA, chunk policy, search and chat settings, model and
   judge. Results are JSON per case plus a summary by layer and category; a comparison report shows the difference
   from a baseline run with per-case changes. No CI gate: live runs cost money and need a populated tenant. A small
   deterministic subset may become a nightly job later.
5. **Tooling.** A Python project under `tools/rag-benchmark/` (uv), reusing `ragas` and Chroma's `chunking_evaluation`
   rather than reimplementing them. It talks to MemoryOS only through its public API as an ordinary authorized user,
   so permissions are part of what is measured.
6. **Data stays private.** Corpus text, generated cases and run outputs contain tenant content: they live under
   `.tmp/rag-benchmark/` (ignored) or a private store, never in Git. The repository holds the code, the dataset
   schema, a synthetic public sample for tests, and summary numbers without content.

## Accepted decisions (2026-09-19)

- **Benchmark identity:** a confidential Keycloak client with a service account, mapped to a dedicated benchmark user
  in the staging tenant; the runner takes client-credentials tokens, with no interactive login.
- **Judge and generator:** OpenRouter `qwen/qwen3.8-27b`, temperature 0, with its own key
  (`RAG_BENCHMARK_OPENROUTER_API_KEY` in Infisical `dev` and `staging`), separate from the deployment's keys. JSON
  mode verified. Staging also serves this model to Chat, so a chat run scored by it grades its own answers: chat runs
  record the answering model and prefer another model under test; deterministic metrics stay primary.
- **Embeddings for the offline chunking layer:** the deployment's `text-embedding-3-large` key
  (`SPRING_AI_OPENAI_API_KEY`), so offline results match production vectors.
- **Corpus:** the 58 staging documents first (about 708K tokens; `.md` chunks average 737 tokens, `.docx` 82); the
  six scanned Tasco reports when they are indexed.

## Out of scope

Changing chunk policy, search sizes or models (each is a separate decision using the numbers), a benchmark UI, and a
CI quality gate.
