# MEM-139 — Usage reports: a period's review pack and data export

## Problem

The AI costs page answers "what does AI cost right now" for one person at the screen. Leadership asks a
different question once a month: how much did AI cost in the period, who used it, which models and tasks
spent it, and which members did not use it at all. They ask for it as a file they can forward and keep.
Nothing in MemoryOS produces that file, and there is no way to take the usage data out for their own analysis.

## Reference

Onyx, read on 2026-09-21 in `.tmp/onyx` (commit `40eb240df`):

- `backend/ee/onyx/server/reporting/usage_export_api.py`: `POST /admin/usage-report` queues generation for
  a period (or all time); `GET /admin/usage-report` lists generated reports; `GET /admin/usage-report/{name}`
  streams the ZIP. All three require the full admin panel permission.
- `usage_export_generation.py`: one ZIP per report with `usage_by_user.csv` (one row per user, day, model,
  flow and provider, with input, output, cache-read and cache-creation tokens and cost),
  `users.csv` (user id, active), `chat_messages.csv` (one metadata row per user message) and
  `usage_report.pdf`. The CSV and the PDF are built from the same rows so their totals reconcile.
  A PDF failure is logged and the ZIP ships without it. User-controlled cells are guarded against spreadsheet
  formula injection.
- `usage_report_data.py`: the PDF's figures are total cost and tokens, licensed seats, active people
  (including people since deactivated), active people holding a seat, dormant seats, top 10 users,
  top 8 models and flows (the rest folded into "Other (n)", never folding a single row), daily cost and
  daily active people, and cost per active person.
- `usage_report_pdf.py`: a cover (logo or application name, "Usage report", the period in UTC, three
  headline figures, a seats meter, one summary sentence, the top 3 models), then Adoption (a line of daily
  active people), Spend over time (a line of daily cost), Where the spend goes (bars and a table by model),
  Heaviest users, Spend by surface, Seats not in use (at most 25, the rest counted), and a closing note.
  Pages after the cover are numbered "N of M". An empty period gets a one-page report saying so.
- `web/src/views/admin/WorkspaceAnalyticsPage/UsageReports.tsx`: a "Usage reports" section at the foot of
  the analytics page. It has a Generate report menu (Today, Last 7 days, Last 30 days, Last 3 months,
  All time, Custom period…), a pending row polled every 3 s, a slow hint after 20 s and a timeout after 5 min.
  Each ready report is a row with its period, "Generated by {requestor} · {time}" and a download link.

## Decision

1. **The ZIP holds three files**: `usage_by_user.csv`, `users.csv` and `usage_report.pdf`, as in Onyx.
   `chat_messages.csv` is left out: message-level history belongs to MEM-125, and the usage rollup already
   answers the report's questions without reading chat content tables.
2. **The data is the `ai_usage` rollup** of MEM-98, the same table and the same period bound (at most
   366 UTC days) as the AI costs page, so the report and the page agree. There is no "All time" option.
3. **MemoryOS adds two cuts that Onyx does not have**, both named in the issue: cost by Group, and cost
   across the data boundary (Internal or External). The CSV carries the boundary on each row and the
   person's current Groups. The PDF has a section for each.
4. **Seats are active Tenant members.** "Not in use" lists active members with no usage in the period.
   People who used AI and have since left the Tenant still count in the totals and as active people, as in
   Onyx. System work, which has no person, counts in the totals and never as a person.
5. **Who can generate and read reports**: model managers (`MODELS_MANAGE`), the same people who can open
   AI costs. A separate capability for one section would be a speculative surface (ADR 0002).
6. **Generation runs in the background.** A request stores a pending report; a recurring Worker task
   claims pending reports with a lease, builds the ZIP, stores it through object storage and marks it
   ready or failed. The rollup is bounded, so building the ZIP inside the request would also be fast. The
   report is stored anyway so that it stays available to the other managers, which is Onyx's behavior.
7. **The PDF is written in Vietnamese**, with English kept for model, provider, input, output and token.
   It embeds the application's own typeface (Hanken Grotesk, static Regular and Bold, SIL OFL), because
   the PDF standard fonts cannot draw Vietnamese. It is drawn directly with PDFBox, which is already a
   `core` dependency: three simple charts and a few tables do not justify an HTML-to-PDF engine.
8. **Two layout changes from Onyx's PDF.** The model section is a single table with a bar in each row,
   where Onyx draws a bar chart and then a table of the same numbers. The note on how costs are counted
   sits on the cover, where it is read before the figures and cannot end up alone on a last page.
9. **Money is USD**, as recorded. Converting to VND at a rate set by an administrator needs a new Tenant
   setting and is left for a follow-up.
10. **No e-mail delivery**, as in Onyx.

## Scope

- Migration: an `ai_usage_report` table (Tenant, requester, period, status, attempts, lease, stored object,
  size, failure, created and finished times).
- `core/usage`: request, list and open for managers; the Worker's claim-and-build step; the export query;
  the CSV writer with a formula guard; the PDF renderer.
- API: `POST /api/ai-costs/reports`, `GET /api/ai-costs/reports`, `GET /api/ai-costs/reports/{id}/content`.
- Worker: one recurring task.
- Web: a "Usage reports" section at the foot of AI costs, using Onyx's copy. The period choices are
  the page's own presets. The download is a plain link that relies on the session cookie.

The ZIP is built in memory, streaming the CSV straight into it. The period bound keeps it well under the
100 MiB object storage limit.

## Out of scope

- Message-level export and query history (MEM-125).
- Usage limits (MEM-123).
- VND conversion, scheduled reports, e-mail.
- Deleting reports and a retention period for them. Onyx keeps them indefinitely.

## Verification

- The PDF renderer draws Vietnamese text and has more than one page for a populated period, and one page
  for an empty one.
- The CSV guards cells beginning with `=`, `+`, `-`, `@`, tab or carriage return.
- HTTP: a manager's request creates a pending report; the Worker step makes it ready; the ZIP holds
  the three files, one CSV row per rollup row, system work included. A member without `MODELS_MANAGE`
  receives 403 on request, list and download; an unknown id is not found.
- Repository: a claim leases the oldest report once; a failure requeues until the last attempt, which marks
  it failed with a reason; a lapsed lease is reclaimed and the stale Worker cannot mark it ready; another
  Tenant sees no report.
- A PDF render failure shipping the CSV files alone is covered by code review only: no test forces PDFBox to fail.
- Web: vitest for the section's states; screenshots at 1280 light and dark and at 390 of the empty,
  pending and ready states.
