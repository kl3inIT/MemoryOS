# Chat defaults provisioned with the Tenant

> **2026-09-25 — split.** The catalog part is `ai`'s `ModelCatalogProvisioner` and the default agent is `chat.application.ChatTenantProvisioner`; both listen to `TenantBootstrapped` in the bootstrap transaction and need no order ([ADR 0015](../../../decisions/0015-capability-module-map.md#step-2-what-ai-and-voice-hold)).

## Requirement

Owner decision 2026-09-24 (audit item 1.1, [owner-decisions.md](../audit-quality-fixes/owner-decisions.md)): Chat's per-Tenant defaults are provisioned when the Tenant is created, not lazily on every request. Before this change `ModelCatalogService` ran `INSERT INTO chat_model_default … ON CONFLICT DO NOTHING` from 19 entry points, and `provisionPersona` ran on every send, session create, agent list and model list, so no catalog read could be `readOnly`. No HTTP contract changes.

## Design

**Event.** IAM adds `io.memoryos.iam.tenant.TenantBootstrapped(TenantId tenantId, boolean created)`. `DefaultInitialTenantBootstrapper`, the only code that creates a Tenant, publishes it through `ApplicationEventPublisher` inside the bootstrap transaction, after the Tenant row is flushed: `created=true` when it creates the Tenant, `created=false` when a restart re-verifies the published Tenant. The repository already publishes domain events this way (`DocumentChanged`, `SourceAccessChanged`), and `chat` may already depend on `iam :: *`, so no module edge is added.

**Listener.** `chat.catalog.ChatTenantProvisioner` is a synchronous `@EventListener` with `@Transactional(propagation = MANDATORY)`, the style of `SearchProjectionMaintenance`. Spring Modulith's event publication registry and `@ApplicationModuleListener` are not configured in this repository. In-transaction rather than after-commit, because a Tenant without Chat defaults is not a usable Tenant: after-commit would reopen the window the lazy guard existed to close, and a failed provisioning (for example an invalid deployment base URL) now fails the bootstrap and rolls the Tenant back, as a failing `GroupProvisioner.bootstrap` already does. The listener runs exactly what the lazy path ran: when it inserts the `chat_model_default` row, it seeds the deployment OpenAI provider and model as the Chat default and one flow row per `ModelFlow`; it then inserts the built-in default agent with every agent tool when absent. The deployment model is API configuration (a `ModelCatalogService.Deployment` bean in `ChatModelCatalogConfiguration`); the provisioner itself is a core `@Component` that injects it (moved there by [ADR 0015](../../../decisions/0015-capability-module-map.md) step 0). The worker creates no Tenant and has no listener.

**Existing Tenants.** The re-verification event is the backfill. Every API start already re-runs the idempotent `groupProvisioner.bootstrap` for the published Tenant; the Chat listener runs in the same transaction, so a Tenant created before the listener existed is provisioned on the next start, and a provisioned Tenant is left unchanged because every step is insert-only. There is no V126 migration. A SQL migration cannot seed the defaults: they need the deployment base URL, model name, pricing and known-model capabilities from properties and `ChatKnownModels`, and the persona name, instructions and model from `PersonaProperties`. A Flyway Java migration bean could receive that configuration, but it would copy one snapshot of it into the database once, beside a restart path that already exists. The [persistence policy](../../../guidelines/persistence.md) also rules out backfill machinery. The repository's precedent for provisioning an existing Tenant is the idempotent restart bootstrap, which repeats with the current configuration. The deployment runs one fixed Tenant, and bootstrap refuses Tenant rows without a published bootstrap, so the bootstrap reaches every Tenant.

**No per-request guard.** The only window without defaults is the first start after this deploy on a Tenant that never used Chat, between the web server starting and the `ApplicationRunner` finishing. A request in it gets the existing "unavailable" error and succeeds on retry. Production Tenants that already used Chat were provisioned lazily. So no guarded write is kept on any request path.

**Reads.** Removed call sites: all 19 `initialize(tenant)` calls and the private method in `ModelCatalogService`; `provisionPersona` in `ModelCatalogService.personas` and `availableModels`, `DefaultChatSessionService.create`, `ChatTurnPersistence` (send/edit/regenerate) and `ChatPersonaService.list`. Session creation and the model list read the default agent with `JdbcChatRepository.defaultPersona` and answer unavailable when it is missing. `ModelCatalogService` reads (`requireModelsManage`, `providers`, `models`, `defaultModel`, `flowDefaults`, `groupOptions`, `providerConnection`, `personas`, `personaModel`, `availableModels`, `availableModelsForPersona`, `availableWebModels`, `validationSelection`) are `@Transactional(readOnly = true)`. PostgreSQL rejects `SELECT … FOR SHARE` in a read-only transaction, so these reads use the non-locking `IamAuthorization.require` and `TenantAccessResolver.findActiveMembership`, as the other read-only Chat reads (`DefaultChatSessionService.list`, `ChatPersonaService.administration`) already do. Writes, `probeProvider` and the `resolve`/`resolveFlow` family keep their locks. `ChatPersonaService.list` stays read-write because it seeds the actor's pins.

## Risks

- Admin list reads no longer hold the shared Tenant lock, so providers, models and defaults read in one request can interleave with a concurrent exclusive catalog change. This is the trade-off the repository already accepts for its other read-only reads.
- Bootstrap now fails at startup when the deployment model is invalid, instead of the first Chat request failing. This is intended.
