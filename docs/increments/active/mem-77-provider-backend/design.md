## Delivered backend foundation

- `core.chat.catalog`: concrete catalog records, authorized application service and the public `ChatProviderAdapter` extension. Main's `core.chat.persistence.ModelCatalogRepository` owns JPA lifecycle and bounded JDBC projections/locks; the former standalone JDBC lifecycle repository is not retained.
- `api.chat`: native OpenAI adapter, credential/client composition and HTTP endpoints. The executor consumes an acquired native binding; it does not choose a provider or interpret provider options.
- JPA lifecycle stores Tenant-owned providers/models/defaults with Hibernate revisions; capability-local SQL retains authorization projections, association batching and bulk reference mechanics. Stable configuration IDs distinguish the same API model name at different endpoints. Transcript retains requested/selected IDs and the actual model name, never credentials or a configuration snapshot.
- A send resolves explicit selection → Persona selection → Tenant Chat default, after conversation ownership and catalog authorization. Unavailable selections may fall back only to an authorized default; the response identifies the actual selection and a generic fallback reason.
- Credentials are deployment references or encrypted Tenant BYOK. Admin writes explicitly keep, replace or remove credentials. Reads expose only configured state. HTTP endpoints on internal networks remain supported; URL credentials/query/fragment are rejected.
- Acquire a client binding per turn. Reuse unchanged bindings; a changed configuration produces a new binding. Retire superseded clients and close only after their last lease. Bound the cache and close on shutdown. Authorization is always read afresh and never cached with the client.
- Capabilities describe chat model input/output and options. Web search and image generation remain separately configured tools; this change does not implement them or advertise them as chat capabilities.

## Compatibility and limits

The deployment provider initializes the Tenant catalog once, preserving existing send callers without a model ID. Subsequent admin edits are authoritative. Existing in-memory setup, local Stop, RAM replay and HTTP/SSE contracts remain in place. No DB run snapshot, Redis, distributed cancellation or worker dispatch is introduced.

Only the existing OpenAI protocol adapter is shipped. Explicit adapter validation, native framework options and contract tests establish its supported configuration; registering another adapter does not certify every local model. Unknown pricing remains unknown, and a finite cost budget requires known pricing. Production behavior includes authorization, DB constraints, bounded resources, credential redaction, stale-write rejection and preserving partial failures.

## Review decisions

Generated APIs distinguish validation results from Search results and describe all browser mutation headers.

### Safe administration while Access is deferred

- Full-replacement provider edits preserve the exact loaded `isPublic`, `groupIds` and `personaIds`, guarded by the provider revision. Never send empty associations or `isPublic=true` merely because the new UI has no Access controls. A conflict requires an explicit reload/reconciliation, not blind resubmission.
- New providers created by this UI explicitly use `isPublic=false`, empty Group/Persona associations: manager-only under the existing backend contract. This is a conservative UI creation policy, not a change to the SQL default or server access predicate.
- The UI explains that new providers are not automatically available to every Tenant member. Making them public or assigning Groups remains deferred; no hidden promotion occurs when choosing a default.
- Tenant default selection offers only eligible visible, enabled, credential-ready, public, Persona-unrestricted configurations. Existing eligible providers remain usable. A new manager-only local provider is not a Tenant-default candidate until the authorization-owned workflow grants the required access.
- A manager can verify the local model through explicit UUID selection or an eligible Persona default. Persona default selection grants no access; other users continue to follow the existing authorized-default fallback.
- Deleting a non-Tenant-default model/provider clears affected Persona defaults and retains transcript history. Do not introduce the incorrect rule that every Persona reference blocks deletion.

## Evidence behind the adapter decision

The reference checkout `.tmp/onyx` was inspected at `06aa2b09cc4aa5135fa2627e5235814e996f1514`.

- Its tokenizer helper converts provider strings to `EmbeddingProvider`; `openai_compatible` falls back to the default document tokenizer, normally Nomic, rather than loading the served model's tokenizer. The 5% history margin is an estimate, not a context guarantee: [tokenizer selection](https://github.com/onyx-dot-app/onyx/blob/06aa2b09cc4aa5135fa2627e5235814e996f1514/backend/onyx/natural_language_processing/utils.py#L125-L182), [margin](https://github.com/onyx-dot-app/onyx/blob/06aa2b09cc4aa5135fa2627e5235814e996f1514/backend/onyx/chat/llm_loop.py#L811-L815).
- An isolated probe executing unchanged Onyx tokenizer definitions measured 23 Nomic tokens versus 52 SmolLM2 tokens for the Vietnamese sample below. The original twenty-repeat receipt reported 460 versus 1,041; the exact pinned-HF/native corpus now measures **1,040 SmolLM2 tokens**, correcting that earlier count. This was not a full Onyx runtime test.
- The historical Spring AI 2.0.1/JTokkit 1.1.0 O200K probe measured 18 tokens for the sample and 361 for its repeated form. Its earlier 1,071 framed-token report is not carried forward as a current native-framing receipt. Raw tokenizer parity and complete native template/output fit are separate checks; even the corrected 1,040 raw tokens exceed the 1,024 context before framing/output.
- Onyx discovery reads `context_length`; retained MEM-66 `/v1/models` evidence exposes `max_model_len:1024` instead. Discovery alone is neither tokenizer discovery nor authoritative deployment-limit validation.

Sample: `Hãy giải thích cách hệ thống lưu trữ và tìm kiếm tài liệu tiếng Việt.`

Pinned [vLLM v0.28.0 protocol](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/entrypoints/openai/chat_completion/protocol.py) supports both `max_tokens` and `max_completion_tokens`, standard Chat Completions JSON/SSE and usage. Current native Spring AI requests streaming usage. Source inspection and retained raw-HTTP gateway evidence do not certify the complete MemoryOS Java path, error decoding or cancellation timing; those remain live gates.

**Decision:** reuse `OpenAiChatProviderAdapter` and type `openai` for the verified local Chat Completions path. Do not add a `vllm` adapter merely to change endpoint, model name, tokenizer or CPU/GPU deployment. A separate adapter requires a reproduced protocol/native-integration difference that cannot be handled cleanly at the existing boundary. Do not add LiteLLM or rewrite the Embabel/Spring AI execution loop.

### Small-model baseline and host fit

Pin the SmolLM2 weights, tokenizer, template, dtype/quantization and serving image as a candidate manifest. Start from the research CPU settings, context 1,024 and output 128. Native qualification must confirm that the complete prompt, short follow-up history and reserved output fit before the final limits/profile are frozen. If they do not, adjust explicit context/resource settings within measured host capacity and record the reason rather than truncate required instructions or substitute a larger model. The trial's 2-CPU/4-GiB envelope is a starting measurement, not proof of headroom on the deployment host.

Measure actual target CPU/RAM, disk/cache capacity and competing application/Docling load for this small CPU model. Record a low-concurrency workload, accepted first-content/end-to-end latency, bounded queue wait and resource ceilings appropriate to that deployment. Do not require GPU procurement, a comparative model search or high-throughput capacity to complete MEM-77. Insufficient host capacity remains a blocker; the research run alone does not prove safe co-location.

Acceptance concerns complete administration, defaults, native text streaming, token/context correctness, Stop, errors, history and operational lifecycle with the small model. Exercise English/Vietnamese input handling without equating correct encoding with fluent or useful Vietnamese answers. Record the model's known language/reasoning limitations; higher-quality answers, better standalone language suitability and retrieval/citation quality are not MEM-77 closure gates. Advertise only verified capabilities: the baseline is text-only, with tools, vision and reasoning disabled. Existing capable bindings must retain their behavior.

Keep the existing hosted deployment bootstrap and Tenant default unchanged. Create SmolLM2 as a separate manager-only provider/model through normal catalog writes and encrypted BYOK, then select it as the builtin Persona default for manager acceptance. The current deployment importer adds input and output limits and initializes a public provider/Tenant default; redirecting it to the 1,024/128 local model would misstate its limit and bypass the approved Access boundary. The literal `deployment` credential reference is not a general-purpose secret-reference registry.

Unknown local pricing remains `null`. Use the existing unlimited-USD sentinel, `MEMORYOS_CHAT_COST_BUDGET_USD=1.7976931348623157E308`, while retaining finite token/output/deadline/concurrency limits. Zero or infinity is invalid execution configuration; zero model prices would falsely assert known free usage. A finite USD budget requires genuine prices and otherwise rejects both send and Validate. This is an existing configuration policy, not a new local-only runtime mode.

Monitoring Compose resolves its backend from the selected serving receipt, not a stale candidate-network value in the observability environment. Serving-only rollback must reject a different accepted client or backend network before drain/start: the unchanged API and monitoring attachments cannot be silently moved with the previous gateway.

Candidate/local product smoke is pre-merge evidence, not an exact-release receipt. Publish an approved successful main release before target rollout and its final acceptance. Record post-merge target results in the active execution record; do not require future deployment evidence inside a PR as a pre-merge condition. MEM-77 closes only after that release passes authenticated Chat, workload, readiness, overload, Stop, warm restart, credential rotation and compatible serving rollback. MEM-70's historical health-only exception does not apply.

### Replacing the model later

A better model normally reuses the same provider protocol, catalog/UI, UUID selection, defaults, executor and operational path. Replace the serving weights/configuration and model identity, then select matching tokenizer/template assets, explicit limits and verified capabilities. Measure the new CPU/GPU/RAM/VRAM requirements and re-run native Chat/context/Stop/usage and lifecycle smoke; upgrade vLLM or configure a parser only when the replacement requires it.

This is a controlled model/configuration rollout, not a guarantee that editing the API model name is sufficient. A different tokenizer/template can require shipping a new immutable installed profile and a narrowly scoped framing policy; profiles are not arbitrary admin-uploaded files. Unsupported protocol/native behavior may need an integration change. Drain before replacing weights on the same endpoint, or route new bindings to a separate versioned endpoint when capacity permits; never change the model behind an active turn's lease. Preserve the previous manifest/profile for rollback. MEM-77 must implement that reusable boundary, but need not select, deploy or certify a second, larger local model.

## Implemented tokenizer and budgeting contract

### Explicit profile identity

`ModelSettings` now requires `tokenizerProfile`, separate from provider wire `options`. Installed profiles cover the hosted baseline and the initial small local model:

- `openai-o200k-v1`: retains the current OpenAI baseline behavior; it is not a claim that every OpenAI-compatible model uses O200K.
- `smollm2-135m-12fd25f-v1`: the revision-bearing SmolLM2-135M-Instruct profile matching tokenizer/template assets at `12fd25f77366fa6b3b4b768ec3050bf629380bac`. Reuse requires matching tokenizer/framing assumptions, not merely the same protocol.

Profile metadata is a small immutable composition-owned data catalog, not a tokenizer-plugin hierarchy or a serving-model registry. Each profile records tokenizer family, asset revision/checksum, prompt-framing assumptions and display name. Use `smollm2-135m-12fd25f-v1` for the initial pinned local profile; any incompatible asset/framing change requires a new identity. Reuse across models requires matching those assumptions, not matching provider type or API model name.

Extend each existing adapter descriptor with `tokenizerProfiles: [{id, displayName}]`. Both fields and the array are required; expose only profiles supported by that adapter. `ModelSettings.tokenizerProfile` is a required nonblank ID; adapter/catalog validation rejects unknown/incompatible IDs and capability settings contradicting the installed profile's supported contract, locally without network/native loading in a transaction. No admin-supplied path/URL, per-turn download, silent fallback or generic profile-discovery endpoint is accepted.

`model_configuration.settings` stores JSONB. V37 backfills existing settings to `openai-o200k-v1`; deployment import writes that profile explicitly. Main's applied V34–V36 are unchanged. Existing UUIDs, revisions, associations and history remain intact. Source DTOs/OpenAPI/generated callers require the profile instead of preserving a missing-field alias.

### Concrete tokenizer integration

The API uses CPU-only `ai.djl.huggingface:tokenizers:0.38.0`, wrapping Hugging Face's Rust tokenizer and loading pinned local `tokenizer.json`: [upstream usage](https://github.com/deepjavalibrary/djl/blob/v0.38.0/extensions/tokenizers/README.md), [published artifact](https://repo.maven.apache.org/maven2/ai/djl/huggingface/tokenizers/0.38.0/tokenizers-0.38.0.pom). Token IDs and shared concurrency have controlled Windows and corrected Linux runtime-base receipts; neither is final API-image acceptance.

Keep the native dependency and concrete profile loading in API provider composition; `core` retains its public settings and existing Spring `TokenCountEstimator` boundary. The API ships only verified tokenizer assets/native dependencies, not model weights or a PyTorch/ONNX inference engine; the managed vLLM deployment separately owns model weights. Record license/source/checksum and make ordinary API/serving startup independent of model-Hub downloads.

The implemented packaging selects CPU/offline mode, installs checksum-verified JNI readonly at `/application/native/tokenizers/libtokenizers.so`, and adds `libgcc`/`libstdc++` only to API. `/tmp` remains noexec; native libraries are not loaded from writable extraction there. Tokenizer licenses/notices ship under API `META-INF/licenses/chat-tokenizers`; worker receives no DJL assets. Raw encodes disable truncation/padding/implicit special tokens, and heavyweight immutable state is shared with last-binding-use ownership through retirement/shutdown. Windows and corrected Linux runtime-base parity/concurrency are measured; the **actual final API image** at UID1654, readonly root, egress denied and bounded native/cgroup memory is still required. Docker is reachable again, but the [last final-image build is canceled and no native-load receipt exists](verification.md#latest-main-integration-and-phase-1-recheck--2026-09-11); the base probe does not satisfy this gate. Failure must be resolved before shipping, never by handwritten BPE or O200K substitution.

Qualify against the pinned [DJL native loader](https://github.com/deepjavalibrary/djl/blob/v0.38.0/extensions/tokenizers/src/main/java/ai/djl/huggingface/tokenizers/jni/LibUtils.java), not only tokenizer examples: CPU flavor, companion libraries, cache extraction and download behavior are part of the gate.

### Context admission and request boundary

Preserve `effectiveOutput = min(deploymentOutput, modelOutput)` and `inputBudget = min(deploymentInput, modelContext - effectiveOutput)`. Catalog limits must match the measured deployment, not the model repository's nominal maximum or a discovery guess. Context 1,024/output 128 is the initial SmolLM2 baseline, subject to the full-request fit gate above. SmolLM2 renders the pinned text-only template; hosted O200K preserves an explicit allowance. Validate uses the same boundary, and final-cycle tools-off remains independent. A post-commit guard alone is not used to promise pre-reservation rejection.

Count the actual profile's role/template markers, generation prefix and framework-added content. Reject mandatory instructions/question/output that cannot fit **before reserving the pair or advancing the tree**; select history with the same framing rules, retaining the current newest-first and orphan-assistant behavior. Native qualification must compare complete outgoing prompts with pinned HF/template counts and real provider prompt usage where supplied. Preserve the existing hosted profile's contract without claiming exact knowledge of its server-side template.

Apply capability/budget/output policy to **every resulting native call**, after framework tool/options conversion, and independently retain last-cycle tools-off. Validate uses that same boundary. For SmolLM2, remove unsupported tool callbacks/choice on all calls and keep tools/vision/reasoning disabled; supporting their catalog fields does not enable them. A later tool-result expansion that exceeds budget fails safely before further provider IO with the already-reserved turn's normal outcome; it does not retroactively erase the tree, retry or silently reinterpret input. Keep provider/model-name switches and a new inference loop/Jinja engine out of `ChatModelExecutor`.

Provider-reported usage remains accounting authority. Local estimates never fill missing streaming usage or convert unknown cost to zero. Preserve the finite-cost-budget requirement for known pricing.
