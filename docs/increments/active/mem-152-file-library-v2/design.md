# MEM-152 — File library v2: reuse, direct upload, content search and bulk download

[MEM-152](https://linear.app/memory-os/issue/MEM-152) · sub-issue of [MEM-142](../../completed/mem-142-file-library/design.md) · builds on [MEM-144](../../completed/mem-144-session-files/design.md)

## Problem

MEM-142 made every file Chat holds for a person visible in `/library`, and MEM-144 put a conversation's own files behind its header. Both are read-only views. A file `run_python` wrote or an image the model generated cannot be attached to a later question, a Project or an assistant without downloading and uploading it again; the composer's "choose an existing file" lists uploads only; the library cannot take a file in without a conversation, finds files only by name, and downloads one file at a time.

| Phase | Parts |
| --- | --- |

| 2 — Bring in and find | 4 direct upload, 5 content search, 6 rename and favourite |

| 4 — Limits and safety | 9 storage usage and quota, 10 trash with restore (needs an ADR) |

## Phase 1 decisions — reuse

1. **An artifact becomes reusable by copying it into an upload, not by referencing it.** Every consumer that accepts files — turn admission, Projects, assistants, `edit_image`, file search — takes `chat_user_file` ids and runs through the upload's extraction and authorization. Teaching each of them a second kind of file id would widen every authorization check; a copy reuses them all unchanged. `POST /api/chat/library/{source}/{id}/copy` with `source` `GENERATED` or `IMAGE` returns the upload (`ChatFileResponse`), which is `PROCESSING` until the file worker extracts it like any other upload.
2. **The server copies the bytes; the browser never round-trips them.** `ObjectUploadService.write` stores bytes the server already holds as a *verified* upload of the `CHAT_FILE` purpose, following the browser path's lifecycle: the stored object and upload rows are reserved first, the bytes are written and inspected, and the caller adopts the upload in its own transaction. An upload never adopted — a crash between write and adoption, or a lost race — is reclaimed by the existing abandoned-upload cleanup, so no new reaper is needed. Storage IO runs outside any transaction; ownership and the artifact's existence are checked again under the owner lock before adoption.
3. **Asking twice returns the same copy.** V92 records `copied_from_source`/`copied_from_id` on the upload, with a unique index over the owner's *live* copies (status not `DELETING`/`DELETED`). A double click, a retried request or two tabs therefore yield one upload; the loser of a concurrent race discards its verified upload and returns the winner's. Deleting the copy frees the artifact to be copied again.
4. **The copy is independent of its artifact.** Deleting the artifact, or the MEM-143 purge removing its conversation, leaves the copy readable, because the copy owns its own stored object. Only an artifact the library lists can be copied: owned by the caller, in the active Tenant, not deleted, in a conversation that is not deleted. A foreign or absent artifact answers 404, as every owner-private file route does.
5. **Rows say which message they belong to.** The listing gains `messageId`: the answer that produced an artifact, and — when the list is narrowed to one conversation — the first message there that attached an upload. The conversation panel uses it to jump to the message. It is a hint for navigation, not an authorization.
6. **The composer picker is the library, not a second list.** "Choose an existing file" opens a dialog over `GET /api/chat/library` with the library's source and category filters and name search, following the Grok/Dash modal: search on top, flat rows with kind icon, name, source and size, multi-select up to the 20-file admission limit, and one primary *Attach* action. Picking a generated file or image calls the copy route and the dialog waits until the copy is `READY` before attaching it, so the composer only receives files it can send and its readiness rule stays unchanged. The popover keeps the three most recent uploads for the quick case and opens the library for everything else.
7. **The conversation panel and the library act on files, not only show them.** Each row gains *Attach to next message* (through the copy for artifacts), *Show in conversation* (scrolls to and highlights `messageId`; a message on another version is brought onto the selected path first, one version choice at a time from the top down, as the version arrows would — the history already holds the whole selected path, so nothing else needs loading) and *Add to Project*. Adding to a Project reuses `PUT /api/chat/projects/{id}` with the project's revision and file list; removing a file from a Project only removes the link. The panel refreshes its count when a turn finishes, so a file a run just produced appears without reloading.

## Phase 2 decisions — bring in and find

8. **Uploading into the library is the composer's upload, without a conversation.** The page drives `/api/chat/files` and the `chat_file_work` pipeline exactly as the composer does, so there is no second upload path and no new authorization; such an upload simply belongs to no conversation, which the listing already allows. The page adds an *Upload* button, a whole-page drop target and a tray with one row, one progress bar and one cancel per file (Proton Drive / ElevenLabs).
9. **A pending upload is a view of the same listing, not a second list.** `status=PENDING` lists the owner's uploads that are `UPLOADING`, `PROCESSING` or `FAILED` (artifacts are excluded, because an artifact is only ever recorded once it exists), with `status` and `errorCode` on the row; `READY`, the default, keeps the usable list unchanged. The pending view offers *Retry* on `/api/chat/files/{id}/retry` and *Remove* on the delete route, and the list polls while anything is processing, so a file becomes usable without a reload.
10. **Renaming rewrites the file's own name; there is no second display name.** The issue proposed a `display_name` column beside `filename`, which every listing, search, download and history card would then have to coalesce. Instead `PATCH /api/chat/library/{source}/{id}` updates the row's `filename` — for an upload, a generated file or an image — so every surface that already reads it follows at once, and the stored object, its key and its bytes are untouched. A message's own file descriptor keeps the name it was sent with, which is the history it recorded. The new name is trimmed, must carry no control character or slash, and keeps the file's extension (appended when the person leaves it out), because previews, categories and the model read the type from it.
11. **Starring is a timestamp, and it sorts.** V93 adds `favorite_at` to the three tables; the same `PATCH` sets or clears it, `favorite=true` filters by it, and `sort=NAME` is added for the case a person renamed files to find them by name.
12. **Content search reuses Chat's own file search.** `GET /api/chat/library/search?query=…` runs `ChatFileSearchService.search` — the search behind the `search_files` tool — over the owner's most recent 4000 `READY` uploads that have an indexed document, and returns each file as a library row with up to three matching passages. Nothing else is in scope: never a Source document, never another member's file, and never a generated file, which is not indexed; the UI says so rather than pretending otherwise. The results are the search's own order, and a file the library no longer lists is dropped before answering.

## Phase 3 decisions — many files at once

13. **A ZIP is a recorded request a Worker packs, not a response the API streams.** `POST /api/chat/library/archives` records the selection and answers 202; `memoryos-chat-library-archive-v1` claims it with a lease and an attempt count exactly as the usage report does, packs the bytes from object storage, and stores the ZIP as a tracked server write. The browser polls `GET /api/chat/library/archives/{id}` and then downloads `…/content`. Packing a hundred files inside a request would hold a web thread for as long as storage takes, and a lost connection would lose the work.
14. **The archive is bounded because it is written as one object.** The storage adapter writes at most 32 MiB, so a request takes at most 100 files and 30 MiB together, refused up front with a named reason, and one owner may queue three at a time. A selection whose files are all gone fails with its own reason rather than storing an empty ZIP, which still carries an end-of-directory record.
15. **The selection is resolved twice, and disappearance is reported.** Ownership and existence are read from the library when the request is recorded and again when it is packed, because a person keeps deleting and renaming while an archive waits. A file gone by packing time is skipped and named in `skipped`, which the page shows; only a request with nothing left to pack fails.
16. **The download is the owner's own route, and the archive expires.** There is no signed URL: `…/content` streams to the owner alone while `expires_at` (six hours) holds, and an expired archive leaves the listing at once. The sweep in the same Worker task releases its bytes the way the artifact cleanup does — mark delete-pending, delete the key outside any transaction, then release ownership and the row under its claim.
17. **Previews gain what an image viewer has, and nothing more.** The preview modal (MEM-111/MEM-142 already highlight code, tab spreadsheets and render PDF and docx) adds rotation, drag-panning while zoomed, and previous/next across the files the page is listing, with the arrow keys; `siblings` is presentation only, and each step re-reads through the same owner-private route.

## Phase 4 decisions — limits and safety

18. **Used bytes are the library's own sum.** `GET /api/chat/library/usage` answers what the caller's library holds, per category, from the same union the listing pages — never a listing of object storage — so the bar on the page and the number a limit is checked against cannot drift apart.
19. **A storage limit is a Tenant setting with per-person exceptions, administered by model managers.** V98 adds `storage_quota_bytes` to `chat_settings` and a `chat_storage_quota` row per person; no limit recorded means no limit, which is how Chat behaved before. Administration uses `MODELS_MANAGE`, as every other Tenant-wide Chat limit does — a new IAM capability would have to be granted everywhere before the page could be used, and this bounds storage rather than authority. `MEM-123` remains the AI-usage limit; this is the storage one.
20. **A limit is checked before bytes are written, and never fails a turn.** An upload is refused at `POST /api/chat/files/uploads` before an upload URL is signed (`409 CHAT_STORAGE_FULL`), and a server-side copy is refused the same way. A generated file or image is not stored when its owner's library is full, and the tool says so in the answer — `run_python` names the files it could not keep, `generate_image`/`edit_image` say the image was not kept — so the turn continues instead of failing. The check reads the used bytes at that moment: two writes racing may both be admitted and the next one refused, because a quota bounds a library rather than fencing a transaction.
21. **Deleting a file moves it to a trash; see [ADR 0014](../../../decisions/0014-file-library-trash.md).** The window (`MEMORYOS_CHAT_TRASH_AFTER`, default 30 days) delays only the byte release, which stays in the existing DELETE work and artifact sweep; `0` reproduces the MEM-142 behaviour. `status=TRASH` lists what was deleted with `deletedAt`/`purgeAfter`, and restore, delete-for-good and empty-the-trash act per file or for everything the owner deleted. The page's delete confirmation follows the configured window, so a deployment without a trash still says deletion is final.

## The library surfaces, after the phases

22. **The page carries its own rail; the toolbar stays one row.** Four phases each added a full-width bar above the list — search, nine filter chips, the storage bar, the view tabs, the selection bar — and the list ended up below the fold. The views (*All files*, *Favourites*, *Processing*, *Trash*) and the storage meter move into a rail beside the list, as Proton Drive, Skiff and Retool Storage place them, and the source and kind filters move into one *Filters* popover (Langdock) that reports what is active as removable pills. The rail scrolls as a row below the `lg` breakpoint, so a phone still opens on the files.
23. **Favourites are a view, not also a filter.** Starring had become a rail entry and a switch in the same popover; the switch is gone, because one thing asked for in two places is two things to keep in step.
24. **A file is a row of facts, not a row of cells.** The table becomes list items: the name, then source, kind, size and date on one line, with a thumbnail for an image and the actions revealed on hover and on keyboard focus. The conversation panel and the composer's picker use the same row, the same kind filter and the same empty states, so the three surfaces that list files read alike. Each empty view says what it means and offers the way out of it, and every notice the page raises is one alert region rather than five stacked paragraphs.

## Security

Every phase-2 route stays inside the same owner-private boundary: the listing filters, the `PATCH` and the content search all require the caller to own a file the library lists, and the content search's scope is built from the caller's own uploads. The copy route reads only what the caller's library already lists and writes only an upload owned by the caller in the same Tenant, so it grants no new access; the copied upload is thereafter authorized exactly as an upload. Logs and metrics carry counts and sources, never file names, prompts or object keys.

## Out of scope

Folders, sharing a single file with someone else, referencing an artifact without copying it, and files of an assistant owned by someone else. A trashed file does not count against the storage limit, and there is no per-Tenant report of who holds what — the AI usage report (MEM-139) covers spend, not storage.
