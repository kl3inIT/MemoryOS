# MEM-109 — Image editing in Chat

Status: Delivered — [PR #193](https://github.com/kl3inIT/MemoryOS/pull/193), merge `97836eb5`. Linear: [MEM-109](https://linear.app/memory-os/issue/MEM-109). Builds on [MEM-97](../mem-97-chat-image-generation/design.md) (image generation). Plan: [plan.md](plan.md).

## 1. Problem

MEM-97 generated images one way only:

- An attached image reached the chat model as vision context only; nothing fed it to the image provider.
- `ImageProviderClient` had only `generate()`, and `GenerateImageTool` stated it was not for editing.
- `flux-1-schnell` is text-to-image and takes no input image.
- History kept earlier answers as text, so a later turn lost the ids of generated images.

As a result, "keep every detail, change only the shirt colour" produced a different picture.

## 2. Goals

- **(A)** Edit an attached image.
- **(B)** Edit an image generated in an earlier turn.
- **(C)** Edit inside a user-selected area (mask) while every pixel outside it stays unchanged.

## 3. Evidence (Workers AI probes, 2026-09-15)

Schemas came from `GET /accounts/{id}/ai/models/schema`; each model ran on a 1024×1024 portrait generated by `flux-1-schnell`.

| Model | Protocol | Result |
|---|---|---|
| `@cf/black-forest-labs/flux-2-klein-4b` | multipart `prompt` + `input_image_0` (+ `width`/`height`); JSON `result.image` (base64 JPEG) | 5.8 s; kept face, hair, pose, lighting and background and changed only the shirt colour; accepts PNG input and sizes down to 48×48 |
| `@cf/runwayml/stable-diffusion-v1-5-inpainting` | JSON `image`/`mask` uint8 arrays; binary PNG | 7–16 s; kept the old colour and printed garbled text or patterns; 512 px by default |
| `@cf/runwayml/stable-diffusion-v1-5-img2img` | — | schema 404, no longer served |

## 4. Decisions

| # | Decision | Reason |
|---|---|---|
| D1 | A separate `edit_image` tool next to `generate_image` | Clear tool descriptions for the model; the generate contract is unchanged |
| D2 | Cloudflare edits always use `flux-2-klein-4b`; no SD 1.5 | §3 |
| D3 | `OPENAI_IMAGE` edits through multipart `POST {base}/images/edits`, with `input_fidelity=high` for `gpt-image-*` models | Same provider contract; no connection change |
| D4 | Masks are applied on the server: the provider edits the whole image and the server takes its result only inside the white area, feathered inward, keeping the source everywhere else | One mask meaning for every provider; guaranteed preservation outside the mask; provider masks are only hints |
| D5 | App-managed state: an edit source is an image generated in the owner's session or a file attached in the turn's context | Provider-agnostic (the Onyx pattern); no `previous_response_id` |
| D6 | The model refers only to ids present in the conversation: attachments carry ids in their metadata and earlier answers list the `image_id` of their images | The model never guesses or invents ids |
| D7 | A mask is a PNG uploaded through the existing chat file pipeline and named `mask-for-<image_id>.png`; the server reads the target image from that name when present | No API contract change; deterministic targeting even if the model passes another id |
| D8 | Working images are normalized: long side at most 1024 px, sides on multiples of 16, PNG; ImageIO decoding with pixel limits; PNG or JPEG only | Klein tile cost; safe decoding (`java.desktop` is already in the runtime, see `ChatImageExtractor`) |
| D9 | Lineage `source_artifact_id`/`source_file_id` on `chat_image_artifact` (V62), without foreign keys | Traceability; the source may be deleted later |
| D10 | Reuse `IMAGE_GENERATE` | No new permission |

## 5. Contracts

- **Tool** `edit_image(imageId, prompt, maskId?)`: at most 4 calls per answer; emits `ChatImageEvent` like generate; the result is a new artifact on the current answer and its `image_id` is returned to the model.
- **Provider** `ImageProviderClient.edit(connection, prompt, image)` → `Result`; Cloudflare calls `/ai/run/@cf/black-forest-labs/flux-2-klein-4b`, OpenAI calls `/images/edits`.
- **Images**: working-image normalization and mask compositing live in `core/chat/image` (`ImageEditImages`, plain Java2D).
- **Storage**: `ImageArtifactService.sessionImage(...)` reads a source; `store(..., sourceArtifactId, sourceFileId)` records lineage.
- **History**: `TurnContext.generatedImages` (message id → artifact ids) is loaded in `ChatTurnPersistence`; `ChatTurnSetup` appends the `image_id` line to earlier answers.
- **Web**: an edit action on generated images opens a dialog with an optional brush mask and an instruction; it attaches `mask-for-<id>.png`, turns image mode on and fills the thread composer.

## 6. Security

- Edit sources are only images in the owner's session (`JdbcImageArtifactRepository.inSession`) or files attached in the turn's context (`ChatTurnSetup.fileIds()`) that the owner can read and that are READY (`ChatFileContentService.image`).
- Untrusted images are decoded with size and pixel limits; every provider input is a PNG re-encoded by the server.
- Provider errors and credentials never reach model output or the UI; `memoryos.chat.image.request` keeps bounded provider, operation and outcome tags.

## 7. Known limitations

Klein re-renders the whole image, so background tone and subject position can shift slightly. With a mask, pixels outside the painted area stay identical, but a stroke that crosses smooth background can show a seam (seen live: a horizontal band across the background and neck left a clear line). The edge is feathered inward by about 1.2% of the long side; an unpainted edit is the most seamless. Tone matching around the edge is a possible later improvement.

## 8. Out of scope

Automatic masks, multi-image composition, an edit action on uploaded images (editing them by instruction in chat works), and WebP as an edit source.
