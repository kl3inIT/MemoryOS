# Delivery verification

> Delivery policy — 2026-09-12: CD ends at verified image identity, migration/startup and health/readiness. Business acceptance belongs to the user. Recovery is manual; deployment success does not prove login/Search acceptance or restore correctness.

| Contract | Verification | Evidence boundary |
| --- | --- | --- |
| Required dependencies cannot silently skip integration | Mandatory Testcontainers classes; `clean check`; bounded no-Docker JUnit probe | Docker absence fails a required container; the three opt-in live Docling checks remain separate |
| Runtime defaults survive context consolidation | `BearerAuthenticationIntegrationTest` | HTTP health, virtual-thread executor, disabled normal springdoc handler and bearer security in the same context |
| Frontend failures remain visible | Vitest worker cap, zero-retry fixture Playwright suite | Synthetic browser/API behavior, not a deployed provider |
| A failed/skipped job cannot authorize release | `CI Gate` checks the exact dependency set and every result with jq; selected jobs must succeed and unselected jobs must skip | GitHub workflow execution, including matrix failures and exact-tree test reuse on main. Unknown PR paths select every area |
| The deployed artifact is the main artifact | CI validates source labels and records registry digests, release run/attempt and configuration checksums | Main publication required. PRs and dispatches have no deployment authority |
| Workflow and script syntax/configuration remain valid | actionlint and ShellCheck in CI; IDE checks on workflow YAML | Static checks do not prove a server rollout |
| Dependency upgrades preserve public API and frontend navigation | OpenApiContractTest, generated client/route stability, frontend check and zero-retry browser suite | Inspect generated differences before accepting an updated contract; fixture browser tests do not prove staging authentication |
| Every built JavaScript asset, including the `.mjs` pdf.js module worker, is served with a JavaScript MIME type under `nosniff` | `frontend-image` CI job runs the production image and checks each `assets/*.js`/`*.mjs` content type | The stock nginx `mime.types` maps only `.js`; a failed worker made pdf.js fall back to a main-thread import and the stale-chunk handler reload the page on staging |
| Every web response keeps the CSP, nosniff, framing, referrer and permissions headers | `web/scripts/nginx-config.test.mjs` fails if any nginx location declares `add_header` (which drops the inherited set); the `frontend-image` job checks the headers on `/`, an `.mjs` asset and the SPA fallback of the running image | A location-level `add_header` served `/runtime-config.js` without them until 2026-09-28 |
| The production build runs under the deployment policy | `frontend-preview` CI job on main and dispatch: shell, Group administration, Search, meetings and file-preview specs with `MEMORYOS_E2E_PREVIEW=1` (production build served with nginx.conf's literal headers); `tests/e2e/deployment-policy.ts` fails on any CSP or Permissions-Policy report outside its listed third-party ones | Fixture origins stand in for the object-storage `connect-src`; the dev-server shards send no policy |
| Web base-image upgrades preserve the serving boundary | Build the pinned image; inspect nginx version and rendered config; exercise SPA/asset routes, forwarding, CSP and invitation cache/log rules as its configured non-root user | A bounded synthetic upstream verifies proxy behavior; real provider and staging acceptance remain separate |
| The public landing image keeps its serving boundary | `landing/scripts/smoke-image.sh` in the `landing` CI job: read-only, capability-free UID 101 container; `/`, `/healthz`, public files, 404 for unknown paths, CSP and security headers, immutable asset caching | Local container only; DNS, TLS, HSTS and the `www` redirect are checked on the deployed host per the [landing runbook](../runbooks/landing.md) |
| The landing release stays independent of the application release | `landing-image` artifact outside `candidate-*`; `Publish landing` after landing and secrets; the application `images.env` lists only API, worker, web, interpreter, interpreter executor and Keycloak | Deployment is a manual operator step; the application script never manages `memoryos-landing` |
| The interpreter joins the release reachable only on the internal network, with one key shared with the API, without breaking a runtime accepted before it (MEM-110, again since ADR 0033) | `test_deploy_workflow.py::test_interpreter_images_join_the_release_contract`, `test_interpreter_is_reachable_only_on_the_internal_network`, `test_interpreter_and_api_share_one_key_secret`, `test_the_release_names_its_images_once` and the gate cases; the CI `interpreter` job's service checks, integration tests against a real executor and e2e tests against the service container | Staging health and a `run_python` answer prove the runtime; the first staging deployment of the change proves the swap |
| The sandbox leaves the release (ADR 0033): no CI job, Compose service, secret or image names it, a runtime that still runs its server has the container removed, and a rollback to such a runtime starts it again | `test_deploy_workflow.py::test_the_sandbox_is_gone_from_a_release_but_not_from_a_rollback`, `test_the_release_names_its_images_once`; the first staging deployment of the change | The removal of a live container is proved by that deployment, not by a test; the conversations' sandbox containers the server left are removed by the operator ([CI/CD runbook](../runbooks/ci-cd.md#sandbox-removal)) |
| API migration/readiness precedes new worker | Compose script sequential `--wait` rollout with explicit deadlines | Exercise failure and recovery on staging before enabling automatic deployment |
| Concurrent or interrupted mutation is contained | GitHub concurrency, server flock and persistent reservation | A pending transaction blocks a newer release until accepted/recovered |
| Failure/cancellation does not silently roll back or remove a reservation | Reporting-only workflow failure step; behavioral transaction checks retain pending on failed health/revision/serving readiness and reject takeover | Operator explicitly selects recovery; runner termination can interrupt credential cleanup |
| Deployment does not depend on a business account | `test_deploy_workflow.py` executes healthy finalization without business-account environment and checks the committed runtime/reservation outcome | Isolated POSIX transaction with Docker/serving dependencies controlled; user business acceptance remains separate |
| Recovery cannot silently discard a reservation | Optional exact `recovery_release`, main ancestry check, existing transaction `finish` image/health/ownership guard; behavioral tests reject another owner and schema drift, and retain pending until healthy finalization | Manual selection only; never deletes pending directly, restores a database or accepts a mixed runtime |
| Real accepted Search flow | User acceptance through normal identity and FILE/Search UI; optional `web/tests/staging/search.spec.ts` | Not run by CD; record separately from deployment success |
| Rollback is explicit and compatible | Prior image IDs/configuration, schema comparison before restoring images, database backup, health/revision verification | Backup catalogue is not restore proof; changed schema needs operator recovery |

Deployment and manual recovery require the SSH/server configuration in the [runbook](../runbooks/ci-cd.md), not a smoke identity. Static regression checks and workflow validation do not establish live deployment or rollback correctness. The delivered [delivery simplification increment](../increments/completed/staging-deploy-simplification/plan.md) records its implementation evidence; post-merge runtime evidence belongs in Linear.
