# Connector capability contract

Integration boundary: this contract combines the implemented Google branch with main IAM/Search. The [isolated integration plan](../increments/active/google-drive-structured-ingestion/plan.md#isolated-main-integration--2026-09-09) tracks pending combined verification; linked prior tests/runtime observations remain pre-integration evidence.

## Ownership

Connector owns Tenant-scoped Connector, Credential, ConnectorCredentialPair, ConnectorItem/version, source synchronization, index/cleanup operation association, Pair-to-Document provenance and Source–Group associations. The public product read model is Source; `sourceId` is the operational Pair identifier and never exposes persistence association names. IAM owns Groups and authority, not Source persistence.

FILE and GOOGLE_DRIVE are implemented. FILE creation requires global `SOURCES_MANAGE`, serializes on the Tenant authorization row, creates or reuses exactly one NO_AUTH Credential, and creates one PUBLIC Pair. Omitted or empty creation Group selection defaults to Admin. Membership role alone never authorizes Source management.


Google consent creates an independent Tenant-owned GOOGLE_OAUTH Credential, not a Source or a new per-Actor credential ownership model. OAuth continuations remain initiating-Actor-bound. Multiple Sources may share it; every Source has a distinct Connector and RESTRICTED Pair attached to main's protected Admin Source association, independent selection, synchronization progress and item/Document identity. V23 removes Google singleton constraints while preserving existing IDs, encrypted grants, roots and content.


## Browser product model

The browser separates provider types from configured Sources. `/admin` uses expandable provider groups with search and provider/status/access filtering, operational summaries and direct navigation to `/admin/sources/{sourceId}`. Access is read-only: PUBLIC is displayed as active Tenant-member access, not anonymous Internet access; Google remains Restricted. `/admin/sources/new` has searchable FILE and Google Drive tiles, with no unimplemented provider entries. Existing Source screens use the shared Onyx-aligned layout and responsive setup rail, not new backend stages.

FILE setup remains one form with source name, drag/drop or file browsing, a removable file summary and one Upload and create action. A blank name is populated from the filename. Selection validates one supported file of 1 byte–10 MiB before creating a Source. One guarded submit creates, uploads and finalizes, then opens detail for indexing status. Upload retries retain the Source; finalization retries reuse the upload without another PUT. The single Upload file step is presentation only.

Source identity is route-owned through the detail path parameter, so creation, direct navigation, and browser history address one deterministic configured Source. Pending FILE finalization state lives above the Source routes and retains only the initiating Source/upload identifiers plus filename, never the presigned URI or bytes. Navigation to another Source exposes a return link; retry occurs against the initiating Source and emits no second provider PUT.

Detail loads the Source summary independently from the current Files page. The below-table Files pagination bar has Rows (5/10/25/50/100, default 25), the current page and labelled previous/next icon buttons; there is no page/file-count/order subtitle above the table. Page-size changes reset the cursor and previous-page stack. Previous/Next replace rows rather than appending them; no total is invented from cursors. Status polling does not reload all items; explicit refresh targets the current page. Successful upload/finalization invalidates the Source's cached pages and returns to the first page at the selected size. Reindex/removal keep observing exact item/operation IDs across page changes until leaving the Source or reaching a terminal outcome.

Current-file rows show name, size, status, Last indexed and actions. Last indexed is a plain accessible timestamp for the current version's retained successful processing completion, or Unknown. There is no expandable Added/queued/start/completion detail or repeated subtitle beneath the filename.

Google Drive Indexing attempts is a collapsible compact table of actual Source runs, not individual file operations. It displays Started, Outcome, Checked (`counts.scanned`), Indexed (`counts.published`), Unchanged, Completed/duration and safe Errors. Completion time and duration sit beside each other on one non-wrapping line. Rows omit repeated trigger and indexing-status subtitles. Additional counts appear behind Details only when nonzero or unknown; all-zero successful runs have no redundant details control. Retry timing and paged safe errors remain available. No Current activity/Last completed/Last successful dashboard is rendered. The list is read only while expanded; active runs are polled. Null historical values remain Unknown. Current Source document totals are never substituted for run counters.

FILE Sources instead show File processing history: filename, queued/start/completion times, duration, status and safe error. Both histories default to 5 rows with 5/10/25/50 choices; size or Source changes reset the cursor. Only FILE history displays current/total pages from the required nonnegative `SourceOperationPage.totalItems`, counting all retained authorized Tenant/Source attempts independently of the cursor; empty history displays 1/1. Drive run pages have no fabricated total. Previous/Next replace rows using cursors, and narrow tables scroll inside their own containers.

Google setup presents Credential → Connector using the Onyx-aligned credential card and Create New modal. The picker has a separate selection column before four metadata columns: ID (short UUID with full value on hover), Name (without repeating an identical account email), Created and Last Updated (local dates without times). On narrow screens the same metadata stacks into labelled groups without horizontal scrolling. Unusable credentials retain a warning and cannot be selected. The labelled three-dot Manage button discloses attachment count and guarded reconnect/revoke/delete actions. New consent selects the created credential; an existing active credential needs no JSON upload or repeat consent. Connector submission names the Source and queues durable validation; worker activation atomically persists its General/Specific scope and initial sync. Specific is the safe default and accepts explicit file/folder links; General explains the connected account's My Drive boundary and hides the link editor. Mode is chosen only at creation, where Specific link drafts survive toggling General and back and no saved-selection summary is shown. Detail renders saved mode without a selector. General retains its summary despite its empty public roots list and has no link editor or selection-save/reload actions. Specific lists saved roots only when present; its link draft survives refresh and independent interval saves until explicit Save selection. Concurrent root/credential/actor authority changes require explicit reload rather than stale retry. App/redirect configuration remains under collapsed Setup instructions; shared credential management and cleanup remain available. No account browser, document viewer, ACL editor, reader linking, Groups or Drive PUBLIC control is added.

Synchronization, Selected content and history place question-mark help popovers beside their titles rather than persistent explanatory subtitles. Guidance remains pointer- and keyboard-accessible, including the broader OAuth-permission boundary. History help does not toggle its disclosure; Escape closes help and restores trigger focus. Link-field counts, validation errors, conflict warnings and pending validation remain visible. Selection errors remain distinct from synchronization/interval errors; editing or retrying clears field errors without replacing the complete draft. Detail has no redundant Saved scope heading. Saved roots use filled, MIME-aware icons with accessible type labels for Sheets, Docs, Slides, Word, Excel, PowerPoint, PDF and CSV, with a generic fallback. Non-interactive file rows have no hover fill; Reindex/Remove retain distinct button hover and focus surfaces.

Specific detail places Edit selection inside the initially collapsed File and folder links disclosure below the tree, not beside the Selected content heading. Explicit Edit loads the complete bounded `selection-draft` when needed, pins scope/discovery/credential revisions and focuses the textarea; an existing draft is reused without dropping approvals. Select for sync on an eligible linked target and Deselect for sync on an approved target load that same complete draft, adding or removing only that target while preserving other saved approvals. The checkbox receives focus when enabled; otherwise focus moves to Cancel. Neither action opens or closes the root-links disclosure or enters its editor. Approval-only Save selection, Cancel and Reload saved selection controls appear directly below the tree; root editing keeps the same controls inside the editor. Reload resets to the saved selection without switching editing mode. The draft owns all root links and approved IDs independently of visible pages, search and status polling. Cancel discards local edits without a write and restores the originating Select/Deselect control, or Edit when appropriate. Save submits the whole draft for validation; acceptance is not activation. Failed validation retains the draft. Receipt recovery resolves an interrupted/lost-response submission before another write is inferred. Closing the page does not cancel durable work; no public Cancel validation command is exposed. Creation accepts links directly without the detail edit guard.

Saved linked approvals remain reversible even when their target becomes unavailable: Deselect is enabled, but the unchecked draft checkbox cannot reapprove an unavailable target. Both selected and deselected draft labels are explicitly provisional. Targets covered by roots have no independent Select/Deselect control because their inclusion is governed by the root selection.

Read-only links have a transparent, non-resizable presentation and a visible Read only indicator. The saved-links disclosure and detail editor reuse only the labelled link field, not another Selected content heading, help trigger or scope description; the read-only count shows saved links without an editing quota. The detail panel owns its single heading/help in all states, while creation retains its heading/help and scope picker. Edit selection uses the shared secondary button with a visible boundary. Both read-only and editable fields retain horizontal/vertical padding and keyboard focus visibility; selecting text for copying does not enter edit mode. Google provider errors are presented once in Synchronization rather than repeated below the Source title; other Source errors and per-file errors remain visible.

Selected content defaults to lazy folder → actual file → recorded linked-target branches, including files without recorded links. The same target may appear beneath several parents but shares one approval keyed by provider file ID. Search/type filters retain a compact unique projection where explicit roots take precedence over linked appearances. Unreachable retained linked targets remain accessible outside root branches; cycles terminate without recursive expansion. The default tree has no persistent root/file/link-count subtitle. Provenance groups distinct parent/location references by source document; Technical paths and raw path identifiers are not rendered. Expanding folders reads bounded authorized Google metadata; expanding file links reads stored evidence, never discovery or approval writes. Bulk selection affects eligible loaded targets while the complete draft retains off-page approvals and targets whose prior provenance disappeared. Folder inclusion cannot be excluded by checkbox; unavailable/unsupported targets cannot become new approvals. Loading, empty, unavailable and changed-authority states remain distinct.

The Credentials disclosure retains a visible chevron in both states: down when collapsed, up when expanded. Its action label changes from Manage connection to Close instead of disappearing. The whole native summary remains pointer- and keyboard-operable.

Each Google Source displays its saved Automatic interval as the fifth field in the Source summary card, with an Edit action beside the value. FILE keeps its four-field summary. Google Drive retains ownership of configuration queries, drafts and schedule mutations; the shared card is presentation only. Synchronization below retains its actions/help/errors without a duplicate interval display. Loading or unavailable configuration has an explicit state rather than an invented saved value. The inline Edit interval form accepts whole minutes from 1 to 2147483647, supports Save interval, Cancel and keyboard operation. Status refresh preserves interval and link drafts. A schedule conflict requires explicit Reload saved interval, without automatically retrying or replacing the root draft/revision. Editing an interval alone does not block Synchronize now, and a schedule save does not save or discard edited links.

Source management uses accessible, dismissible Radix notifications for creation, upload/finalization, Reindex, Synchronize now, remove/delete, selection/interval saves, credential management and explicit refresh/reload. Accepted asynchronous commands announce acceptance, then observe the returned operation ID for success, failure or supersession; disappearing aggregate `pendingWork` is not proof of that command's success. A status-read failure reports an unknown outcome, not failed processing. Reindex/removal observers are item-specific and cancelled on Source navigation. Synchronization completion means acquisition finished; upload/finalization acceptance also leaves indexing status to normal Source polling. The root notification provider keeps named creation/deletion results visible across redirects while clearing ordinary notices on pathname changes. Every notice, including errors, closes after five seconds without pausing for hover, keyboard focus or window blur; navigation does not restart the timer, and early dismissal remains available. Creation/upload retries retain known partial success instead of repeating completed work. Credential connection is confirmed only from a validated callback and active credential read; confirmation/OAuth failures remain accessible inside their dialog. Validation, conflicts and drafts remain in their editors. Background polling, ordinary navigation and opening/closing an editor do not generate toast noise.

The browser consumes server-projected Source actions (`upload`, `reindex`, `remove_items`, `delete`, `manage_groups`). A scoped manager sees only associated Sources and upload/reindex controls; global capability holders receive their applicable actions. Creation/detail Group selectors persist real associations, and Group detail exposes only authorized Source associations. Authority-revision changes reset mounted private queries before removal, including when capability tokens remain unchanged.

## Application and persistence boundary

`DefaultSourceManagementService` owns authorization, validation, upload adoption, orchestration, transaction boundaries, transition decisions and typed failures. It injects concrete Connector persistence plus public `ObjectUploadService`, `IamAuthorization` and Group-scope contracts; it never imports another capability's persistence. `JdbcSourceUploadRepository` binds a generic upload to one Pair and persists its finalized item/version/attempt receipt. `JdbcSourceGroupRepository` owns Tenant-qualified associations. Application code contains no SQL, row mapping, locks, claims or bulk updates; single internal JDBC implementations have no repository interfaces.

Google grant lifecycle, revision-fenced provider sessions, and root configuration/sync scheduling belong to `DefaultGoogleDriveAuthorizationService`, `DefaultGoogleDriveConnectionService`, and `DefaultGoogleDriveSourceService`. They use capability-owned persistence and public IAM/storage services. Google acquisition uses `ObjectWriteService`, never a fabricated browser-upload receipt.

## Source summaries and Files pages

`GET /api/sources/{sourceId}` and `POST /api/sources/file` return `SourceSummary` directly, without an embedded item list or a one-field detail wrapper. Reads require global `SOURCES_READ` or associated managed-Group scope; FILE creation requires global `SOURCES_MANAGE`.

`GET /api/sources/{sourceId}/items` (`listSourceItems`) returns `SourceItemPage { items, nextCursor }`. It accepts `cursor` and `size`, defaulting to 25 with a maximum of 100, ordered by item `created_at DESC, id DESC`. Cursors are scoped to Tenant, Source and item-page kind; malformed positions, foreign scopes and unsupported timestamps are rejected after authority checks. New uploads ahead of a cursor do not duplicate or shift already visited rows. No OFFSET or whole-corpus count is required to fetch a page.

Each `SourceItem` carries separate `searchStatus` for downstream Search readiness, nullable `lastIndexedAt`, the latest successful attempt completion for its current version only, and nullable `latestAttempt` with `id`, nullable `filename`, `status`, `createdAt`, nullable `startedAt`, nullable `completedAt` and nullable safe `errorCode`. Missing history remains unknown rather than using upload time. `uploadedAt` remains original item creation. The obsolete `latestOperationId` field is removed. `/index-attempts` returns the same richer file-attempt projection; generic operation polling is unchanged.

`JdbcSourceQueryRepository` materializes at most `size + 1` item candidates before projecting versions, the latest attempt and successful completion for the current version. V29 provides Source item keyset and latest-attempt indexes. Summary polling, paged items, run history and item-attempt history remain separate read contracts.

## Google authorization and credential authority

Google ingestion authorization is separate from MemoryOS login: it never replaces the Actor or links a reader identity. `POST /api/credentials/google-drive/authorization` validates global `SOURCES_MANAGE` authority, credential name and `oauthClientJson` before returning an authorization URL. The JSON must be a downloaded Web application client, at most 16 KiB UTF-8, with nonblank client ID/secret and the exact configured redirect URI; desktop/service-account credentials, ambiguous duplicate/trailing JSON and untrusted endpoint values are rejected. Provider endpoints are fixed, never fetched from uploaded URLs.

Reauthorization requires `credentialId` and `expectedCredentialRevision` together. JSON may be omitted only when that credential already retains an owner app; there is no server-wide default app. The ten-minute, one-use consent continuation binds encrypted app data, Actor, Tenant, target credential and expected authority to the existing browser session, state, PKCE S256 and nonce. The callback `/login/oauth2/code/google-drive` validates signed OIDC identity, issuer, that app's audience/authorized party, nonce, verified email and agreement with the Drive account before rechecking global `SOURCES_MANAGE` authority. Required scopes are OpenID/email plus Drive, Sheets and Docs read-only. The Google subject pins the account across reconnects.

Callbacks redirect only to Google setup with a safe `connected` / `authorization-failed` outcome and credential identity where applicable. Owner app credentials and refresh grants are encrypted at rest with Tenant/credential/key-version binding; access tokens remain transient. Browser JSON is cleared before submission/on unmount and does not enter React Query mutation variables, browser storage or returned configuration. Authority changes remount the setup form and abort outstanding consent requests. Requests, continuations, responses and errors redact secrets. Missing Google encryption/redirect configuration fails Google operations closed without disabling FILE. Historical V21 requires owner-app reauthorization for legacy grants; V23 itself requires no new consent.

`GET /api/credentials/google-drive` returns only the current Tenant credential catalog to an actor with global `SOURCES_MANAGE`: ID, name, safe account email, status (`ACTIVE`, `NEEDS_REAUTHORIZATION`, `REVOKED`), authority `credentialRevision`, app-configured flag, creation/update timestamps and attached Source count. Normal refresh-token rotation compare-and-sets authority and payload revisions, increments only `payload_revision`, and preserves publication authority. Reauthorization, accepted authentication failure and revoke advance authority and fence every attached Source atomically; obsolete refresh results cannot defeat newer authority or a winning rotation. Publication checks usable authority inside its acceptance transaction. Locks follow Tenant → credential → Source, with attached Sources ordered deterministically.

`POST /api/credentials/google-drive/{credentialId}/revoke` requires `expectedCredentialRevision`. It commits local revocation, destroys the refresh grant, invalidates mappings and cancels sync/index work across every attachment before best-effort remote revocation. Remote failure or an unavailable encryption key cannot restore local authority. Revoke preserves all Sources, selections and the encrypted owner app for same-subject reconnect. Generic Source deletion cleans only that Source and retains its credential. `DELETE /api/credentials/google-drive/{credentialId}` requires a strong quoted numeric `If-Match`; only an unattached credential at that revision can be deleted. Known foreign IDs and missing IDs have the same result for an authorized other-Tenant administrator; actors without global `SOURCES_MANAGE` are rejected before lookup.

## Google selection and synchronization

`POST /api/sources/google-drive` accepts `requestId` (UUID), `name`, `credentialId`, required `scopeMode` (`GENERAL` or `SPECIFIC`) and `links`. Both create and replacement use durable asynchronous verification, returning `202` with `{sourceId, operation}` after bounded admission without waiting for Google. Create reserves a Source ID but creates no active Source row until successful activation. GENERAL requires empty links and worker verification of the credential's actual My Drive root; SPECIFIC requires nonoverlapping explicit links within backend policy. Neither admits Shared with me/account-wide browsing or other users' drives. Mode/shape/quota/authority failure cannot create a partial Source. Different Sources retain separate item/Document identity for the same provider file.

`GET /api/sources/google-drive/selection-policy` exposes `maxExplicitRootsPerSource`, `maxRequestBytes` and `maxLinkedDocuments` to actors with global `SOURCES_MANAGE`. Defaults are 1,000 roots, 3,145,728 request bytes and 500 linked approvals. Deployment bounds are 1–10,000 roots and 1,024–4,194,304 bytes; request-body and UTF-8 service budgets remain separate from per-link length, provider and parser limits. Folder descendants do not consume explicit-root quota. These configured limits are not a live Google capacity claim.

Bounded capacity evidence covers 20/21/100/1,000 mixed roots, shared ancestor checkpoints, one linked approval per scenario, overlap and 1,001-root quota rejection in real PostgreSQL/services with a deterministic provider-port fixture. The [Connector verification matrix](../tests/connector.md#measured-selection-and-history-capacity--2026-09-08) owns timings, calls and connection/resource caveats. A separate [controlled 100k-file no-change traversal](../tests/ingestion.md#controlled-100k-file-traversal) exercises the real HTTP adapter and persisted sync frontier. Neither establishes production pooling, live Google limits or initial corpus acquisition/indexing; folder-corpus size remains separate from explicit-root quota.

`GET /api/sources/{sourceId}/google-drive` is a no-store summary with credential identity/state/revision, app-configured flag, immutable scope mode, scope revision/ETag, independent interval/schedule revision, root/linked counts, discovery metadata/errors, last sync time, pending work/error and `pendingSelectionOperation`; it no longer returns full roots/linked trees. `GET .../google-drive/selection` accepts `search`, `kind` (`FOLDER`, `FILE`, `LINKED`), `cursor` and `size` (default 25, max 100). The database excludes linked targets that are explicit roots in the same tenant and Source before filtering or paging; linked/approved-linked counts use the same exclusion. Every visible row, including roots, receives its stored provenance. The cursor pins tenant, Source, scope/discovery/credential revisions and filters. `GET .../google-drive/selection-draft` explicitly loads all bounded active links/approval IDs and their three revisions for editing; this unique read projection does not delete discovery or approval state. General never exposes its system root as a selected user link.

`GET .../google-drive/selection-tree` (`getGoogleDriveSelectionTree`) accepts optional `parentId`, `cursor` and `size` (default 25, maximum 100). Its response contains `revision`, `discoveryRevision`, `credentialRevision`, `items`, `nextCursor` and `counts`; items add `expandable` to selection metadata. Root reads include retained disconnected links; folder reads list actual accessible children and file reads return retained link evidence. Parent authority is restricted to selected roots, verified descendants or exact approved supported files, with General fenced to the real My Drive root and excluding Shared Drives. Scope/credential authority is rechecked after provider I/O; cursors pin authority, parent and provider-page identity. Reads are metadata-only, with no selection/discovery/content writes. Provider I/O stays outside SQL transactions and is bounded by 256 metadata operations, 64 ancestry steps, 1,000 provider-page entries and a 120-second deadline.

`PUT .../google-drive/roots` requires `requestId`, immutable `scopeMode`, `links`, `linkedDocumentIds`, `discoveryRevision`, `credentialRevision` and strong quoted scope `If-Match`. Admission records an immutable intent and supersedes older pending proposals, not the active selection. The request receipt is Tenant/initiating-Actor scoped: replaying the same request/body returns the same receipt, and reusing its ID for different content conflicts. `GET /api/sources/google-drive/selection-requests/{requestId}` recovers a lost receipt; `/api/source-operations/{operationId}` polls the accepted operation without run-only fields. A reserved create ID is not a navigable Source before activation.

The worker verifies fixed-host Google metadata outside SQL transactions with durable metadata/ancestor checkpoints, one selection claim per credential, bounded batches and retry budgets. Only the fenced activation transaction rechecks active Tenant and initiating Actor global `SOURCES_MANAGE`, credential identity/revision, Source mode/scope/discovery authority and claim before atomically creating Source/roots/initial sync or replacing roots/approvals and fencing obsolete sync/index/publication. Invalid, inaccessible, overlapping, stale, revoked or superseded proposals cannot replace active roots, change intervals or invalidate Documents. Credential/Tenant/Source lifecycle cancellation covers pending intents. There is no small synchronous-selection fallback. Specific still rejects whole-drive links, trash, shortcuts and ancestor/descendant overlap, while explicit files/folders inside Shared Drives remain supported.

`POST .../google-drive/sync` returns a durable `SYNC_SOURCE` operation (`202`) using current usable authority and the saved scope. Its acquisition completion does not assert downstream indexing completion. Both modes reconcile persisted roots and descendants through the same PostgreSQL frontier/membership/checkpoint pipeline without account-wide Changes. Successful selection activation preserves the independent interval and schedule revision.

`POST .../google-drive/linked-documents/discover` is an explicit Specific-only global `SOURCES_MANAGE` command with the current scope `If-Match` and the existing browser mutation guard. It reads content inside saved roots and from previously approved exact-file targets, extracts Google document links offline, and resolves target metadata through the authorized provider. It never fetches supplied websites, executes formulas, approves new targets, schedules work or changes scope/schedule revisions. General rejects discovery and linked approvals.

Discovery admits at most 100 content files, 500 target IDs, 2,000 provenance edges, 512 metadata/list operations and 2,500 pending paths, with a 120-second deadline checked between bounded calls and before publication. Native Sheets/Docs, XLSX, DOCX, PPTX, PDF and UTF-8 CSV/text/Markdown readers retain independent content, archive, XML and document limits. Per-input failures have safe codes; a global bound failure preserves the previous snapshot rather than presenting truncation as complete. The API reverse proxy permits 300 seconds so an already-running bounded call can finish and return the deadline failure.

V26 stores candidates, link origins, approvals and input errors separately. Origins identify the actual scan anchor (`rootId`), containing document (`parentId`), parent name and location; old ancestry is not projected into new evidence. Publication rechecks current global `SOURCES_MANAGE` authority, Source, credential, scope and discovery authority. An older discovery cannot replace a newer snapshot. Existing approvals survive lost provenance; new approvals must belong to current discovery and pass fresh metadata/authority validation.

Saving root links and approved file IDs commits together under scope authority and uses the existing cancellation/publication fence without changing the interval. Approved targets enter the same durable SOURCE_SYNC frontier, file identity, membership generations, snapshot adoption and indexing path as roots. They grant exact-file membership only, never folder authority. A target becoming a folder cannot widen traversal or turn an incomplete run into pruning evidence. Only a complete current generation prunes excluded content; duplicate paths still produce one Item per Source/file ID. Google remains RESTRICTED, with no new reader or ACL grant.

`PUT .../google-drive/schedule` accepts `{ "syncIntervalMinutes": 15 }` with one strong quoted numeric `If-Match` taken from the configuration body's `scheduleRevision`, not the GET response's scope ETag. The interval is an integer from 1 to 2147483647; V24 defaults new and existing Sources to 5 minutes and schedule revision 1 while preserving existing due timestamps. The command requires an authenticated active Tenant member with global `SOURCES_MANAGE` and the existing same-origin browser mutation guard. It locks Source authority, rechecks global `SOURCES_MANAGE` authority, and compare-and-sets only the interval, schedule revision and next due time. Stale schedules return `SOURCE_GOOGLE_REVISION_CONFLICT`. Success returns the full configuration with `200`, no-store caching and the new schedule ETag.

Saving schedules the next run from the database statement time plus the new interval. It neither enqueues nor cancels work, changes scope/generation/credential authority, nor invalidates existing Documents or other Sources. Local schedule edits remain available when the Google grant is unavailable and make no Google request. In-flight work completes normally and its next scheduling transition reads the latest saved interval. The minute-level due check is not a wall-clock start guarantee; no cron, independent pruning schedule or automatic-sync disable mode is exposed.

Folder reconciliation temporarily clears membership eligibility. Incomplete generations release successfully adopted, confirmed inputs for indexing but do not prune unseen items; failed files remain discoverable on later syncs. General verifies its saved My Drive root before traversal and pruning; missing, changed, trashed, shared-drive or unverifiable roots cannot become empty completed generations. Only a complete scoped traversal permits pruning. Legacy whole-drive roots stored as SPECIFIC fail closed. Scope replacement, credential revocation and explicit removal fence obsolete work; exact-current input awaiting only membership confirmation is deferred without consuming extraction retries. Execution belongs to [ingestion](ingestion.md); current Document/artifact publication belongs to [document](document.md).

## Synchronization run history

`source_sync_attempts` anchors a synchronization run; `index_attempts` remains item processing. V28 stores nullable legacy trigger/actor/counters, acquisition and end-to-end timestamps, revision snapshots, exact owned-child attribution and retained safe errors. Automatic index creation at input adoption records tenant/source-safe `source_sync_attempt_id` in the same transaction. Manual reindex/FILE attempts remain unattributed; observing an older live attempt adds `alreadyPending` without taking ownership of its publication.

| Counter | Meaning |
| --- | --- |
| `scanned` | Unique file IDs observed by this run, not folders, pages or retry calls |
| `acquired` | New/changed input versions adopted by this run |
| `published` | Owned child index operations that published successfully |
| `unchanged` | Unchanged input; not proof an earlier index succeeded |
| `alreadyPending` | Existing processing observed but not owned by this run |
| `acquisitionFailed` / `indexingFailed` | File acquisition failures / terminal failures of owned child indexing |
| `skipped` / `removed` | Skipped files / removals finalized only by complete reconciliation |
| `indexingPending` / `indexingSuperseded` / `indexingCancelled` | Unfinished or terminal-fenced owned children |

Counters are durable and idempotent across duplicate delivery, retry, supersession, bulk cancellation and item cleanup. Acquisition may finish while owned indexing continues; end-to-end completion requires terminal acquisition and all owned children terminal. Reconciliation deferral is not a terminal child outcome and does not spend extraction retry budget. A later manual retry/reindex cannot reattribute or rewrite a closed run. Unknown legacy facts stay null/Unknown, not zero inferred from current Source Documents. Counters overlap and must not be summed into document totals or a fabricated progress percentage.

Global/scoped `SOURCES_READ`-authorized `GET /api/sources/{sourceId}/runs` returns keyset pages ordered by descending `(created_at,id)`, default 25/max 100, with optional `status`, `trigger`, `from` and `to`. It also returns independent `current`, `lastCompleted` and `lastSuccessful` summaries. `GET .../runs/{runId}` returns one run; `GET .../runs/{runId}/errors` pages errors by `(occurred_at,id)` with the same size bounds. Cursors bind tenant/Source and query context; foreign identifiers cannot become an authority oracle. `/api/sources/{sourceId}/index-attempts` remains paged item history, not an alias for synchronization runs. Generic operation polling remains a separate contract.

Read states distinguish queued, acquiring, retry scheduled, recovery pending, indexing, succeeded, completed with errors, failed, superseded/cancelled and unknown legacy outcome. Expired claims report recovery pending, not an active worker. No owned children gives indexing `NOT_REQUIRED`. The compact table distinguishes loading, empty and unavailable reads and renders null counts as Unknown. No changes requires a successful end-to-end outcome with no indexing needed and known zero acquisition/publication side effects, removals, failures, skipped or pending work; acquisition success alone cannot hide ongoing owned indexing. Counter/error details expose retained run facts rather than current Source Document totals. `INDEXED` does not mean search-ready. Independent `current`, `lastCompleted` and `lastSuccessful` API summaries remain available but are not rendered as dashboard cards.

Errors retain safe `PROVIDER`, `STORAGE_READ`, `STORAGE_WRITE`, `EXTRACTION`, `PUBLICATION` or `SYSTEM` stage, code, time and known run/operation/item/file identifiers/name. Run-wide failures differ from file failures. Storage read/write/connectivity/TLS messages do not instruct the owner to fix Google links. Raw exceptions, tokens, signed URLs, provider bytes and internal object paths are not public error detail. Historical failures remain visible after later successful runs; recovery uses current Synchronize now or item Reindex, not replay of old authority.

Retention defaults are `memoryos.connector.run-history.summary-retention=P90D` and `detail-retention=P14D`, with positive detail duration no longer than summary duration and maintenance batches capped at 100. Terminal details/frontier compact only after owned work finishes; `detailsExpired` distinguishes compacted detail from an empty error page. Live children, current-input attempts, upload receipts and unresolved current failures are protected; protected references may retain summaries beyond 90 days. Summary counters survive detail/item cleanup. Source deletion removes history in dependency order without deleting live stored-object references. This is operational history, not a compliance audit store or metrics-derived authority.

## File and operation lifecycle

A FILE upload declares 1 byte–10 MiB, a normalized display filename, media type and lowercase SHA-256. The API authorizes the concrete Source, commits a Pair-bound generic upload intent, returns a provider-neutral presigned PUT authorization and receives no file bytes. Finalization verifies provider metadata outside the Connector transaction, then reacquires shared Tenant authority and rechecks concrete Source scope before adopting a new immutable `StoredObject` or discarding a duplicate staged object. Revocation during provider IO therefore prevents adoption. Duplicate content in one FILE Pair converges on one item/version/live attempt; finalized receipts make lost-response replay idempotent. Detection and extraction never run in the API transaction.

Reindex is idempotent while work is nonterminal. Item removal and source deletion are explicit POST commands that immediately invalidate retrieval mappings and return durable cleanup operations. Google item removal also excludes that item from subsequent sync acceptance. Connector owns adopted raw-object cleanup for both providers: provider deletion completes before upload/write ownership, versions/items, object metadata, and unreferenced Documents are removed in dependency order. Tracked writes can be released only after their version references are removed, in the same acceptance/cleanup transaction. See [object storage](object-storage.md) for reservation, adoption and abandoned-write cleanup. Cleanup results remain queryable after target deletion; `SUCCEEDED` and `SUPERSEDED` are terminal success states.

Source-level indexing errors represent unresolved failures of currently FAILED items at their current input version, not historical failed attempts. Successful reindex clears the recovered item's contribution while preserving errors from other still-failed items. Historical operations remain available without keeping a recovered or removed item failed in the Source aggregate.

`Source.pendingWork` includes nonterminal item cleanup even while the source remains ACTIVE. The existing detail polling therefore continues through DELETING and refreshes the item/count after durable cleanup completes; terminal cleanup does not keep polling alive.

Source status/error reconciliation uses the newest attempt per Connector item. A successful retry clears that item's historical failure without hiding another item's current failure. Historical attempts remain queryable; reconciliation does not delete evidence or treat an old failed attempt as current.

## Management authority and Group associations

All management requires current active IAM authority. Global access is capability-derived; scoped access requires a manager edge in an ordinary Group associated with the concrete Source.

| Operation | Authority |
| --- | --- |
| Source list/detail, items, run/error history, attempt history and operation polling | Global `SOURCES_READ` or associated managed-Group scope |
| Source creation and Google credential/configuration/selection/discovery/sync/schedule operations | Global `SOURCES_MANAGE` only |
| Upload initiation/finalization and reindex | Global `SOURCES_MANAGE` or associated managed-Group scope |
| Item removal and Source deletion | Global `SOURCES_DELETE` only |
| Source–Group replacement | Global `SOURCES_MANAGE` only |

Out-of-scope reads and concrete Source operations fail without revealing the target; global-only denied commands do not fall back to scoped management. Source and operation queries enforce Tenant/scope predicates before exposing results. Scope is checked again on replay/finalization, not inferred from a previously issued upload intent or operation ID.

V16 gives Source–Group rows Tenant-qualified foreign keys to both resources and seeds existing Sources to Admin. Replacement requires a nonempty validated selection; Group deletion can cascade its associations without deleting Sources. Globally authorized administrators retain access. Association changes serialize exclusively on the same Tenant authority row and advance its revision; protected Source commits use the shared lock. Source associations add no cross-capability JPA relationship or provider credential; reusable Google credentials have their separate lifecycle above.

## Document-content access

`SourceDocumentAccessResolver` grants PUBLIC read clearance only when the actor has current active tenant membership and a live retrieval-eligible mapping whose PUBLIC FILE Pair, FILE Connector, and Document are active/eligible. GOOGLE_DRIVE remains RESTRICTED and is explicitly excluded from that resolver, including after successful indexing. Source-management authority does not imply document-read access; inactive/deleting state fails closed. Google permissions are not collected or enforced, and neither tenant membership nor the ingestion account email supplies a Drive read policy.
