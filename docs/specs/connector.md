# Connector capability contract

## Ownership

Connector owns Tenant-scoped Connector, Credential, ConnectorCredentialPair, ConnectorItem/version, source synchronization, index/cleanup operation association, Pair-to-Document provenance and Source–Group associations. The public product read model is Source; `sourceId` is the operational Pair identifier and never exposes persistence association names. IAM owns Groups and authority, not Source persistence.

FILE and GOOGLE_DRIVE are implemented. FILE creation requires global or scoped `SOURCES_MANAGE` and serializes on the Tenant authorization row. It creates or reuses exactly one NO_AUTH Credential. FILE access is PUBLIC or PRIVATE; SYNC is rejected. Global creation defaults to PUBLIC, may omit Group associations and records no Source manager; no system Group is added automatically. Scoped creation requires PRIVATE access, records its creator as the Source manager, and accepts only ordinary Groups managed by that actor, including none at all — a private Source with no Group reaches nobody until it is attached. Membership role alone never authorizes Source management.


Google consent creates an independent Tenant-owned GOOGLE_OAUTH Credential, not a Source. New credentials record their authorizing Actor; scoped users may use only their own credentials, while legacy unknown ownership remains global-only. OAuth continuations remain initiating-Actor-bound. Multiple Sources may share a credential; each Source has a distinct Connector and Pair, an access mode chosen at creation (Auto Sync by default; see [Source access modes](#source-access-modes)), validated Group associations, independent selection, synchronization progress and item/Document identity. V26 removes Google singleton constraints while preserving existing IDs, encrypted grants, roots and content; V47 adds nullable ownership without inventing legacy owners.


## Browser product model

The browser separates provider types from configured Sources. `/admin` lists configured Sources in one table with a search field, Provider, Status and Access filter menus, an overview of counts, status and access badges, empty states and direct navigation to `/admin/sources/{sourceId}`. Access is read-only in the list: PUBLIC is displayed as active Tenant-member access, not anonymous Internet access; Private and Auto Sync have their own badge and filter. `/admin/sources/new` has searchable FILE and Google Drive provider cards, with no unimplemented provider entries. Source screens use the shared MemoryOS layout and shadcn components without inventing backend stages.

FILE setup is one form with a drop zone that also browses files, a removable file summary, the source name, a Visibility dropdown whose options name and describe each mode, and one Upload and create action. Access groups appear only when Private is chosen, and always for scoped managers, whose FILE Sources are Private: a field of removable group chips that opens a searchable list of ordinary Groups. The Google Drive connector step has the same form: Source name, Visibility (Auto Sync by default), Access groups for Private or for a scoped manager's Auto Sync, and the links field, whose selection error shows once the field is edited. Groups are submitted only while their field is shown. A blank name is populated from the filename. Selection validates one supported file of 1 byte–100 MiB (104,857,600 bytes) before creating a Source; the detail-page uploader enforces the same size bound. One guarded submit creates, uploads and finalizes, then opens detail for indexing status. Upload retries retain the Source; finalization retries reuse the upload without another PUT. Upload progress is a progress bar; there is no step rail.

Source identity is route-owned through the detail path parameter, so creation, direct navigation, and browser history address one deterministic configured Source. Pending FILE finalization state lives above the Source routes and retains only the initiating Source/upload identifiers plus filename, never the presigned URI or bytes. Navigation to another Source exposes a return link; retry occurs against the initiating Source and emits no second provider PUT.

Source detail opens with a breadcrumb back to Sources, the Source name, and its status and access badges beside the provider name. A Source actions menu holds Rename source, Change visibility and Delete source, each shown only with its permission. Rename and visibility open a dialog; the visibility dialog reuses the Visibility dropdown from creation, and deletion keeps its confirmation. The summary above the tabs says in words who can read the Source and lists its non-system Groups, the indexed document count and the last successful indexing; Google Drive adds its interval and, for editors, an Automatic synchronization switch. FILE detail has Files, Indexing history and Groups tabs; Google Drive has Content, Sync history and Connection and settings tabs.

Detail loads the Source summary independently from the current Files page. The below-table Files bar uses the same `TablePagination` component as Users and Groups: Rows (5/10/25/50/100, default 25), `current / total` and labelled text Previous/Next buttons. There is no page/file-count/order subtitle above the table. The total comes from authorized `totalItems`, never cursors or successful Document counts. Page-size changes reset the cursor and previous-page stack; a refreshed count that invalidates the current page returns to the first page. Previous/Next replace rows rather than appending them. Status polling does not reload all items; explicit refresh targets the current page. Successful upload/finalization invalidates the Source's cached pages and returns to the first page at the selected size. Reindex/removal keep observing exact item/operation IDs across page changes until leaving the Source or reaching a terminal outcome.

Current-file rows show name, size, status, Last indexed and one actions menu. The name carries a per-extension file icon with its type as accessible text; Google Docs, Sheets and Slides use their brand marks. The menu offers Reindex and Remove; Remove asks for confirmation, and either request in flight blocks the menu. Last indexed is a plain accessible timestamp for the current version's retained successful processing completion, or Unknown. There is no expandable Added/queued/start/completion detail or repeated subtitle beneath the filename.

Current file status uses an icon badge; the table does not repeat the separate Search-readiness state. The header carries the status and access badges and the provider name on one line, not a separate provider-type subtitle. A Source error appears after the complete synchronization overview and before the tabs, rather than above the overview.

Pending rows show Queued only when their latest attempt is `NOT_STARTED`, or Processing when it is `IN_PROGRESS`. Other item states remain authoritative; a differing latest-attempt outcome appears separately, and missing or unrecognized state never implies completion. Search readiness remains separate from extraction status. The aggregate activity label is Work pending, not a processing percentage. Indexed means processing completed, not that financial values were verified.

The Files table has a 42rem minimum width inside its own focusable horizontal-scroll region. Size, Status, Last indexed and Actions reserve 6rem, 9rem, 9rem and 6rem respectively; the filename receives the remaining width, wraps and exposes its full value through the title attribute. Narrow viewports scroll the table rather than compressing status, timestamps and actions into overlapping columns.

Google Drive Sync history is a table of actual Source runs, newest first, not individual file operations. It displays Started (relative within the last week, the local time beneath), Status, Trigger (automatic schedule, manual or initial synchronization), Duration and Activity; Activity is one line of the nonzero checked (`counts.scanned`), indexed (`counts.published`), removed, pending and failed counts. A Status filter chip ticks one or more statuses, sent to `GET /api/sources/{sourceId}/runs` as repeated `status` parameters; its own clear button removes them. The current run, or else the latest completed run, and the last successful run appear above the table when they exist. A row, or its View details control, opens the run in a side Sheet with Overview (run ID, trigger, start, end, duration, next retry), Stages (reading and indexing content, each with its duration and state), File counts and paged safe errors; closing the Sheet returns focus to the row's View details control. Active runs are polled. Null historical values remain Unknown. Current Source document totals are never substituted for run counters.

FILE Sources instead show File indexing attempts in the Indexing history tab: filename, queued/start/completion times, duration, status and safe error. View details opens one attempt in a side Sheet with its timeline, duration, translated error, error code and attempt ID; attempts carry no item identity, so a failed attempt points to Reindex in the Files tab. Both histories use the shared Users/Groups pagination component with `current / total`, Rows and text Previous/Next controls; their default is 5 rows with 5/10/25/50 choices. Required nonnegative `totalItems` counts retained authorized Tenant/Source attempts independently of the cursor; Drive run totals additionally apply the active status, trigger and time filters. Empty history displays `1 / 1`; an unavailable total is not fabricated. Size/Source changes and a count that invalidates the current page reset cursor navigation. Previous/Next replace rows using cursors, remain grouped on narrow screens, and wide tables scroll inside their own containers.

Source detail uses a 40px top-level Drive provider mark and consistent icon-backed major headings for Upload content, Synchronization, Credentials, Selected content, Files, indexing histories and Group associations where applicable. Group associations uses the same plain divided section and table surface rather than a nested outer card; authorization, editable drafts, Save and Cancel remain unchanged.

Files and both history queries use zero stale time rather than the shared 30-second freshness window. Returning to a cached cursor page refetches its rows and total, including the first-page reset after removal or retention; otherwise a fresh cached first page could restore the obsolete total indefinitely for terminal FILE history. Existing polling intervals remain. FILE history loads when its tab opens; Google run history mounts in the selected Sync history tab, and run-error queries mount only for the selected run.

Google setup presents Credential → Connector using the shared credential card and Create New modal. The picker has a separate selection column before four metadata columns: ID (short UUID with full value on hover), Name (without repeating an identical account email), Created and Last Updated (local dates without times). On narrow screens the same metadata stacks into labelled groups without horizontal scrolling. Unusable credentials retain a warning and cannot be selected. The labelled three-dot Manage button discloses attachment count and guarded reconnect/revoke/delete actions. New consent selects the created credential; an existing active credential needs no JSON upload or repeat consent. Connector submission names the Source and queues durable validation; worker activation atomically persists its General/Specific scope and initial sync. Specific is the safe default and accepts explicit file/folder links; General explains the connected account's My Drive boundary and hides the link editor. Mode is chosen only at creation, where Specific link drafts survive toggling General and back and no saved-selection summary is shown. Detail renders saved mode without a selector. General retains its summary despite its empty public roots list and has no link editor or selection-save/reload actions. Specific lists saved roots only when present; its link draft survives refresh and independent interval saves until explicit Save selection. Concurrent root/credential/actor authority changes require explicit reload rather than stale retry. App/redirect configuration remains under collapsed Setup instructions; shared credential management and cleanup remain available. Connector submission also carries the [access mode](#source-access-modes): Auto Sync by default, Private, or Public for global managers only, with mode-specific help above the Group picker. No account browser, document viewer, ACL editor or reader linking is added.

Google Source detail keeps overview and synchronization controls together above Content, Sync history and Connection/settings tabs. Content contains selected scope and acquired files; connection and Source-group management belong together under settings. Selection drafts remain mounted across tab changes. Synchronization and Selected content retain keyboard-accessible help popovers; run history instead has a concise purpose description and an explicit details action. The obsolete disclaimer that Google document access is not configured here is removed. Link-field counts, validation errors, conflict warnings and pending validation remain visible. Selection errors remain distinct from synchronization/interval errors; editing or retrying clears field errors without replacing the complete draft. Detail has no redundant Saved scope heading. Saved roots use filled, MIME-aware icons with accessible type labels for Sheets, Docs, Slides, Word, Excel, PowerPoint, PDF and CSV, with a generic fallback. Non-interactive file rows have no hover fill; Reindex/Remove retain distinct button hover and focus surfaces.

For Drive managers with retained connection data, Source-summary and Drive-configuration refresh failures share one warning in Synchronization and its existing Refresh status action; no duplicate Source-level warning or Refresh source button appears above the detail. Either failed read keeps mutations disabled until fresh state is available. FILE detail and scoped readers without Drive administration retain their Source-level recovery action.

Specific detail places Edit selection inside the initially collapsed File and folder links disclosure below the tree, not beside the Selected content heading. Explicit Edit loads the complete bounded `selection-draft` when needed, pins scope/discovery/credential revisions and focuses the textarea; an existing draft is reused without dropping approvals. Select for sync on an eligible linked target and Deselect for sync on an approved target load that same complete draft, adding or removing only that target while preserving other saved approvals. The checkbox receives focus when enabled; otherwise focus moves to Cancel. Neither action opens or closes the root-links disclosure or enters its editor. Approval-only Save selection, Cancel and Reload saved selection controls appear directly below the tree; root editing keeps the same controls inside the editor. Reload resets to the saved selection without switching editing mode. The draft owns all root links and approved IDs independently of visible pages, search and status polling. Failed validation retains the draft. Receipt recovery resolves an interrupted/lost-response submission before another write is inferred. Closing the page does not cancel durable work; no public Cancel validation command is exposed. Creation accepts links directly without the detail edit guard.

Saved linked approvals remain reversible even when their target becomes unavailable: Deselect is enabled, but the unchecked draft checkbox cannot reapprove an unavailable target. Both selected and deselected draft labels are explicitly provisional. Targets covered by roots have no independent Select/Deselect control because their inclusion is governed by the root selection.

Read-only links have a transparent, non-resizable presentation and a visible Read only indicator. The detail panel owns its single heading/help in all states, while creation retains its heading/help and scope picker. Edit selection uses the shared secondary button with a visible boundary. Google provider errors are presented once in Synchronization rather than repeated below the Source title; other Source errors and per-file errors remain visible.

Selected content defaults to lazy folder → actual file → recorded linked-target branches, including files without recorded links. The same target may appear beneath several parents but shares one approval keyed by provider file ID. Search/type filters retain a compact unique projection where explicit roots take precedence over linked appearances. The action label changes from Manage connection to Close instead of disappearing. This includes PUBLIC Sources visible to a scoped manager; Source creator identity does not replace the concrete action policy.

## Application and persistence boundary

`DefaultSourceManagementService` owns authorization, validation, upload adoption, orchestration, transaction boundaries, transition decisions and typed failures. It injects concrete Connector persistence plus public `ObjectUploadService`, `IamAuthorization` and Group-scope contracts; it never imports another capability's persistence. `JdbcSourceUploadRepository` binds a generic upload to one Pair and persists its finalized item/version/attempt receipt. `JdbcSourceGroupRepository` owns Tenant-qualified associations. Application code contains no SQL, row mapping, locks, claims or bulk updates; single internal JDBC implementations have no repository interfaces.

Google grant lifecycle, revision-fenced provider sessions, and root configuration/sync scheduling belong to `DefaultGoogleDriveAuthorizationService`, `DefaultGoogleDriveConnectionService`, and `DefaultGoogleDriveSourceService`. They use capability-owned persistence and public IAM/storage services. Google acquisition uses `ObjectWriteService`, never a fabricated browser-upload receipt.

Provider synchronization and acquisition remain explicit implementations, while indexing after snapshot adoption is shared. `ProviderAuthorityService` is the provider boundary for publication and replay: its default dispatcher routes only the implemented `GOOGLE_DRIVE` and `SHAREPOINT` types to their owning connection service, and a provider-backed `FILE` or unknown mapping fails closed. The indexing repository verifies the captured provider scope before calling that authority. Google additionally requires current eligible, non-excluded membership; SharePoint requires the current `sharepoint_sources.scope_revision`. Both require the version's captured credential revision to remain usable and current. The generic Source lock orders Tenant → attached Credential → Source for every credential kind. Terminal supersession recomputes aggregate Source status, so a Source with no remaining live attempts cannot remain `INDEXING`.

## Source summaries and Files pages

`GET /api/sources/{sourceId}` and `POST /api/sources/file` return `SourceSummary` directly, without an embedded item list or a one-field detail wrapper, including the nullable `managerActorId`. Reads require global `SOURCES_READ` or the permitted scoped browse policy; FILE creation requires global or scoped `SOURCES_MANAGE`.

`GET /api/sources/{sourceId}/items` (`listSourceItems`) returns `SourceItemPage { items, nextCursor, totalItems }`. It accepts `cursor` and `size`, defaulting to 25 with a maximum of 100, ordered by item `created_at DESC, id DESC`. Cursors are scoped to Tenant, Source and item-page kind; malformed positions, foreign scopes and unsupported timestamps are rejected after authority checks. New uploads ahead of a cursor do not duplicate or shift already visited rows. Rows remain keyset-bounded without OFFSET. Required nonnegative `totalItems` is a separate count over the same Tenant/Source/current-version candidate scope, without the cursor or limit; pending and failed items without Documents still count. Page and count are separate read-committed statements, not a pinned snapshot across requests, so concurrent ingestion/removal can change totals.

Each `SourceItem` carries separate `searchStatus` for downstream Search readiness, nullable `lastIndexedAt`, the latest successful attempt completion for its current version only, and nullable `latestAttempt` with `id`, nullable `filename`, `status`, `createdAt`, nullable `startedAt`, nullable `completedAt` and nullable safe `errorCode`. Missing history remains unknown rather than using upload time. `uploadedAt` remains original item creation. The obsolete `latestOperationId` field is removed. `/index-attempts` returns the same richer file-attempt projection; generic operation polling is unchanged.

`JdbcSourceQueryRepository` materializes at most `size + 1` item candidates before projecting versions, the latest attempt and successful completion for the current version. V32 provides Source item keyset and latest-attempt indexes. Summary polling, paged items, run history and item-attempt history remain separate read contracts.

## Google authorization and credential authority

Google ingestion authorization is separate from MemoryOS login: it never replaces the Actor or links a reader identity. `POST /api/credentials/google-drive/authorization` validates current global or scoped `SOURCES_MANAGE`, credential name and `oauthClientJson` before returning an authorization URL. New credential creation may supply an app with scoped authority. Supplying an OAuth app for an existing credential requires global `SOURCES_MANAGE`, even if the supplied app equals the saved one. The JSON must be a downloaded Web application client, at most 16 KiB UTF-8, with nonblank client ID/secret and the exact configured redirect URI; desktop/service-account credentials, ambiguous duplicate/trailing JSON and untrusted endpoint values are rejected. Provider endpoints are fixed, never fetched from uploaded URLs.

Reauthorization requires `credentialId` and `expectedCredentialRevision` together. A scoped owner may reconnect by omitting JSON and reusing the saved app only while every attached Source remains manageable. There is no server-wide default app; repairing a missing app on an existing credential requires global authority. The ten-minute, one-use consent continuation binds encrypted app data, Actor, Tenant, target credential and expected authority to the existing browser session, state, PKCE S256 and nonce. The callback `/login/oauth2/code/google-drive` validates signed OIDC identity, issuer, that app's audience/authorized party, nonce, verified email and agreement with the Drive account before rechecking current credential authority. After global permission is revoked, a scoped continuation may reuse only an unchanged saved client ID and secret; changed or missing apps fail closed before provider token exchange or credential completion. Required scopes are OpenID/email plus Drive, Sheets and Docs read-only. The Google subject pins the account across reconnects.

Callbacks redirect only to Google setup with a safe `connected` / `authorization-failed` outcome and credential identity where applicable. Owner app credentials and refresh grants are encrypted at rest with Tenant/credential/key-version binding; access tokens remain transient. Browser JSON is cleared before submission/on unmount and does not enter React Query mutation variables, browser storage or returned configuration. Authority changes remount the setup form and abort outstanding consent requests. Requests, continuations, responses and errors redact secrets. Missing Google encryption/redirect configuration fails Google operations closed without disabling FILE. Historical V21 requires owner-app reauthorization for legacy grants; V23 itself requires no new consent.

`GET /api/credentials/google-drive` returns the current Tenant catalog for global `SOURCES_MANAGE`, or only actor-owned credentials for scoped authority: ID, name, safe account email, status (`ACTIVE`, `NEEDS_REAUTHORIZATION`, `REVOKED`), authority `credentialRevision`, app-configured flag, creation/update timestamps, attached Source count and allowed actions. `reauthorize` does not imply OAuth app replacement: `replace_oauth_client` is global-only and both reconnect UIs require that action plus current global authority. Normal refresh-token rotation compare-and-sets authority and payload revisions, increments only `payload_revision`, and preserves publication authority. Reauthorization, accepted authentication failure and revoke advance authority and fence every attached Source atomically; obsolete refresh results cannot defeat newer authority or a winning rotation. Publication checks usable authority inside its acceptance transaction. Locks follow Tenant → credential → Source, with attached Sources ordered deterministically.

`POST /api/credentials/google-drive/{credentialId}/revoke` requires `expectedCredentialRevision` and global authority or scoped ownership with management scope over every attached Source. It commits local revocation, destroys the refresh grant, invalidates mappings and cancels sync/index work across every attachment before best-effort remote revocation. Remote failure or an unavailable encryption key cannot restore local authority. Revoke preserves all Sources, selections and the encrypted owner app for same-subject reconnect. Generic Source deletion cleans only that Source and retains its credential. `DELETE /api/credentials/google-drive/{credentialId}` requires a strong quoted numeric `If-Match`; only an unattached credential at that revision can be deleted. Foreign and missing credentials remain indistinguishable to scoped callers.

## Google selection and synchronization

`POST /api/sources/google-drive` accepts `requestId` (UUID), `name`, `credentialId`, required `scopeMode` (`GENERAL` or `SPECIFIC`) and `links`. Both create and replacement use durable asynchronous verification, returning `202` with `{sourceId, operation}` after bounded admission without waiting for Google. Create reserves a Source ID but creates no active Source row until successful activation. GENERAL requires empty links and worker verification of the credential's actual My Drive root; SPECIFIC requires nonoverlapping explicit links within backend policy. Neither admits Shared with me/account-wide browsing or other users' drives. Mode/shape/quota/authority failure cannot create a partial Source. Different Sources retain separate item/Document identity for the same provider file.

`GET /api/sources/google-drive/selection-policy` exposes `maxExplicitRootsPerSource`, `maxRequestBytes` and `maxLinkedDocuments` to actors with global `SOURCES_MANAGE`. Defaults are 1,000 roots, 3,145,728 request bytes and 500 linked approvals. Deployment bounds are 1–10,000 roots and 1,024–4,194,304 bytes; request-body and UTF-8 service budgets remain separate from per-link length, provider and parser limits. Folder descendants do not consume explicit-root quota. These configured limits are not a live Google capacity claim.

Bounded capacity evidence covers 20/21/100/1,000 mixed roots, shared ancestor checkpoints, one linked approval per scenario, overlap and 1,001-root quota rejection in real PostgreSQL/services with a deterministic provider-port fixture. The [Connector verification matrix](../tests/connector.md#measured-selection-and-history-capacity--2026-09-08) owns timings, calls and connection/resource caveats. A separate [controlled 100k-file no-change traversal](../tests/ingestion.md#controlled-100k-file-traversal) exercises the real HTTP adapter and persisted sync frontier. Neither establishes production pooling, live Google limits or initial corpus acquisition/indexing; folder-corpus size remains separate from explicit-root quota.

`GET /api/sources/{sourceId}/google-drive` is a no-store summary with credential identity/state/revision, app-configured flag, immutable scope mode, scope revision/ETag, independent interval/schedule revision, root/linked counts, discovery metadata/errors, last sync time, pending work/error and `pendingSelectionOperation`; it no longer returns full roots/linked trees. `GET .../google-drive/selection` accepts `search`, `kind` (`FOLDER`, `FILE`, `LINKED`), `cursor` and `size` (default 25, max 100). The database excludes linked targets that are explicit roots in the same tenant and Source before filtering or paging; linked/approved-linked counts use the same exclusion. Every visible row, including roots, receives its stored provenance. The cursor pins tenant, Source, scope/discovery/credential revisions and filters. `GET .../google-drive/selection-draft` explicitly loads all bounded active links/approval IDs and their three revisions for editing; this unique read projection does not delete discovery or approval state. General never exposes its system root as a selected user link.

`GET .../google-drive/selection-tree` (`getGoogleDriveSelectionTree`) accepts optional `parentId`, `cursor` and `size` (default 25, maximum 100). Its response contains `revision`, `discoveryRevision`, `credentialRevision`, `items`, `nextCursor` and `counts`; items add `expandable` to selection metadata. Root reads include retained disconnected links; folder reads list actual accessible children and file reads return retained link evidence. Parent authority is restricted to selected roots, verified descendants or exact approved supported files, with General fenced to the real My Drive root and excluding Shared Drives. Scope/credential authority is rechecked after provider I/O; cursors pin authority, parent and provider-page identity. Reads are metadata-only, with no selection/discovery/content writes. Provider I/O stays outside SQL transactions and is bounded by 256 metadata operations, 64 ancestry steps, 1,000 provider-page entries and a 120-second deadline. Proving a folder is still in scope walks its ancestors, so file metadata read for that walk, and every file a folder listing already returned, is kept in Redis for 60 seconds under the reading credential and its revision. Only this browsing endpoint reads that cache; synchronization, discovery and indexing always read Google directly. A Source browsed without Redis stays correct and only repeats the ancestor reads.

`PUT .../google-drive/roots` requires `requestId`, immutable `scopeMode`, `links`, `linkedDocumentIds`, `discoveryRevision`, `credentialRevision` and strong quoted scope `If-Match`. Admission records an immutable intent and supersedes older pending proposals, not the active selection. The request receipt is Tenant/initiating-Actor scoped: replaying the same request/body returns the same receipt, and reusing its ID for different content conflicts. `GET /api/sources/google-drive/selection-requests/{requestId}` recovers a lost receipt; `/api/source-operations/{operationId}` polls the accepted operation without run-only fields. A reserved create ID is not a navigable Source before activation.

The worker verifies fixed-host Google metadata outside SQL transactions with durable metadata/ancestor checkpoints, one selection claim per credential, bounded batches and retry budgets. Only the fenced activation transaction rechecks active Tenant and initiating Actor global `SOURCES_MANAGE`, credential identity/revision, Source mode/scope/discovery authority and claim before atomically creating Source/roots/initial sync or replacing roots/approvals and fencing obsolete sync/index/publication. Invalid, inaccessible, overlapping, stale, revoked or superseded proposals cannot replace active roots, change intervals or invalidate Documents. Credential/Tenant/Source lifecycle cancellation covers pending intents. There is no small synchronous-selection fallback. Specific still rejects whole-drive links, trash, shortcuts and ancestor/descendant overlap, while explicit files/folders inside Shared Drives remain supported.

`POST .../google-drive/sync` returns a durable `SYNC_SOURCE` operation (`202`) using current usable authority and the saved scope. Its acquisition completion does not assert downstream indexing completion. Both modes reconcile persisted roots and descendants through the same PostgreSQL frontier/membership/checkpoint pipeline without account-wide Changes. Successful selection activation preserves the independent interval and schedule revision.

`POST .../google-drive/linked-documents/discover` is an explicit Specific-only global `SOURCES_MANAGE` command with the current scope `If-Match` and the existing browser mutation guard. It reads content inside saved roots and from previously approved exact-file targets, extracts Google document links offline, and resolves target metadata through the authorized provider. It never fetches supplied websites, executes formulas, approves new targets, schedules work or changes scope/schedule revisions. General rejects discovery and linked approvals.

Discovery admits at most 100 content files, 500 target IDs, 2,000 provenance edges, 512 metadata/list operations and 2,500 pending paths, with a 120-second deadline checked between bounded calls and before publication. Native Sheets/Docs, XLSX, DOCX, PPTX, PDF and UTF-8 CSV/text/Markdown readers retain independent content, archive, XML and document limits. Per-input failures have safe codes; a global bound failure preserves the previous snapshot rather than presenting truncation as complete. The API reverse proxy permits 300 seconds so an already-running bounded call can finish and return the deadline failure.

V29 stores candidates, link origins, approvals and input errors separately. Origins identify the actual scan anchor (`rootId`), containing document (`parentId`), parent name and location; old ancestry is not projected into new evidence. Publication rechecks current global `SOURCES_MANAGE` authority, Source, credential, scope and discovery authority. An older discovery cannot replace a newer snapshot. Existing approvals survive lost provenance; new approvals must belong to current discovery and pass fresh metadata/authority validation.

Saving root links and approved file IDs commits together under scope authority and uses the existing cancellation/publication fence without changing the interval. Approved targets enter the same durable SOURCE_SYNC frontier, file identity, membership generations, snapshot adoption and indexing path as roots. They grant exact-file membership only, never folder authority. A target becoming a folder cannot widen traversal or turn an incomplete run into pruning evidence. Only a complete current generation prunes excluded content; duplicate paths still produce one Item per Source/file ID. Approval grants no reader access; readers follow the Source's [access mode](#source-access-modes).

The command requires an authenticated active Tenant member with global `SOURCES_MANAGE` or concrete scoped operational authority, plus the existing same-origin browser mutation guard. Saving schedules the next run from the database statement time plus the new interval. It neither enqueues nor cancels work, changes scope/generation/credential authority, nor invalidates existing Documents or other Sources. Local schedule edits remain available when the Google grant is unavailable and make no Google request. In-flight work completes normally and its next scheduling transition reads the latest saved interval. V47 adds automatic-sync pause; pausing does not cancel active work or deny an otherwise authorized manual synchronization. The minute-level due check is not a wall-clock start guarantee; no cron or independent pruning schedule is exposed.

## Source pause and resume

`POST /api/sources/{sourceId}/pause` and `POST /api/sources/{sourceId}/resume` let a Source manager (global `SOURCES_MANAGE` or the recorded manager's scoped write decision) stop and restart new synchronization and indexing work for one Source. Pause is a resource-prioritization control, not deletion, failure suppression or Search authorization.

Pause writes durable `PAUSED` on `connector_credential_pairs` and cancels every queued (never-claimed) `source_sync_attempts` and `index_attempts` row for that Source with `error_code = 'SOURCE_PAUSED'`. In-flight attempts are not killed; they settle through the existing claim/current-version fences and record `CANCELLED` at a safe boundary. While a pair is `PAUSED`, the dispatch repository excludes it from SOURCE_SYNC and INGESTION candidate selection, the `due` scheduler skips it, `attempts.create` and `synchronize` reject with a conflict, and the summary reports `PAUSING` while any in-flight attempt remains, then `PAUSED` once drained.

Resume clears `PAUSED`, re-enqueues one `index_attempts` row per item whose latest attempt was canceled by pause and whose current version still needs indexing, and — for Google Drive Sources — enqueues a `RESUMED` `source_sync_attempts` run that inherits the canceled run's phase, page tokens and full frontier when scope and credential revisions still match; otherwise it starts a fresh run. Resume never forces a full reindex.

Pause is not deletion: indexed Documents, items, ACL membership and history remain readable and authorized. Deleting remains stronger — a `DELETING` pair cannot be paused. Pause is not failure: canceled rows carry `SOURCE_PAUSED`, not an extraction or provider error, so retry budgets and Source error banners are unchanged. Docling containers are not killed; an in-flight extraction finishes or fails on its own and its result is fenced out at publication.

A Drive provider version also advances for sharing or metadata changes. When re-read bytes and filename equal the current version under the same scope and credential revisions, acquisition records the newer provider version on that version and counts the file unchanged; no new version, index attempt or re-extraction is created. A real content change adopts a new version while the current Document stays retrievable until the new version publishes over the same mapping; a failed reprocessing leaves the previous Document available. Search keeps serving the previous ready generation while the published replacement is indexed, and switches only when the replacement is ready ([Search](search.md)). Folder reconciliation temporarily clears membership eligibility. Incomplete generations release successfully adopted, confirmed inputs for indexing but do not prune unseen items; failed files remain discoverable on later syncs. General verifies its saved My Drive root before traversal and pruning; missing, changed, trashed, shared-drive or unverifiable roots cannot become empty completed generations. Only a complete scoped traversal permits pruning. Legacy whole-drive roots stored as SPECIFIC fail closed. Scope replacement, credential revocation and explicit removal fence obsolete work; exact-current input awaiting only membership confirmation is deferred without consuming extraction retries. Execution belongs to [ingestion](ingestion.md); current Document/artifact publication belongs to [document](document.md).

## SharePoint credential authority

A SharePoint Source authenticates as an Entra application, not as a person: there is no consent flow and no reader identity. `POST /api/credentials/sharepoint` takes the Directory and Application IDs as GUIDs — a domain name is rejected, so the credential pins one directory — the worldwide cloud, and either a client secret Value of at most 256 characters or a PKCS#12 keystore of at most 16 KiB with its password. A keystore must hold exactly one RSA private key of at least 2,048 bits with an unexpired certificate.

Every draft is verified with Microsoft outside the storing transaction, so a credential Entra rejects is never stored. Verification acquires a token and reads `/sites/root`: a rejected token fails the request with the Entra number classified into what an administrator must change (wrong or expired secret, certificate not registered, unknown directory or application, missing admin consent), and Microsoft's own text never reaches the response. A token that works but cannot read the whole Tenant is a working credential; it records that the "All sites" scope is unusable, which is expected for `Sites.Selected`. Success records the Tenant SharePoint host.

Only the encrypted secret or private key is stored, together with the certificate, its SHA-1 thumbprint and expiry; the uploaded keystore and its password are not. Encryption binds format, Tenant, credential, credential kind, key version and purpose, and SharePoint uses its own key: `memoryos.sharepoint.credential-encryption-key` and `memoryos.sharepoint.credential-key-version`. A missing key fails SharePoint closed without affecting FILE or Drive. Responses never carry the secret, the private key or the keystore.

`GET /api/credentials/sharepoint` returns the Tenant catalog for global `SOURCES_MANAGE`, or only actor-owned credentials for scoped authority: identifiers, cloud, authentication method, status (`ACTIVE`, `NEEDS_UPDATE`), certificate thumbprint and expiry, resolved Tenant host, authority revision, timestamps, attached Source count and allowed actions. Renaming, replacing the authentication and deleting all require a strong quoted numeric `If-Match`; only an unattached credential can be deleted, and foreign or missing credentials stay indistinguishable to scoped callers. `POST …/{credentialId}/test` re-checks a stored credential and marks it `NEEDS_UPDATE` when Microsoft rejects it. There is no revoke: an application-only credential has no grant to withdraw.

## SharePoint scope and synchronization

`POST /api/sources/sharepoint` takes `requestId`, `name`, `credentialId`, `access`, optional Groups and a scope: `ALL_SITES` or `SPECIFIC` with site, library or folder addresses, exclusions for sites and paths, whether documents and pages are collected, and the synchronization and prune intervals. Create and `PUT …/{sourceId}/sharepoint/scope` both answer `202` with `{sourceId, operation}` after local admission, and apply only after a worker resolves every address with Microsoft. Repeating a `requestId` recovers the same receipt instead of verifying twice; a scope change also requires the current scope and credential revisions. Nothing is stored when an address does not resolve.

Addresses are accepted as pasted: sharing links and library view addresses reduce to the underlying path, and `/sites/`, `/teams/` and `/personal/` are all recognised on the Tenant host. A library is matched by the path of its own URL rather than its display name, so a site created in Vietnamese, whose library shows as "Tài liệu" while its URL segment is still `Shared Documents`, resolves like any other. No root may contain another, and every address must be on one host. Exclusions follow Onyx's shell-style wildcards, matched case-insensitively over Unicode names.

A refresh reads each library's change log from the end of the previous successful window minus a thirty-minute overlap. What the change log returns is applied without being filtered by the window again, because an item moved into scope keeps its timestamp; Graph keeps a change log only for a library root, so a folder root is walked breadth first through every subfolder, as Onyx does; files are filtered by the window, folders never are, and the folder being listed and those still waiting survive a hand-back. A Source that collects only pages reads no library. A tombstone removes the document it names, matched by the Graph identifier it carries, so a deletion is reflected within one refresh cycle rather than waiting for a prune. A change link or window Microsoft no longer accepts (HTTP 410) restarts that library from its start. A scope change hides the documents of the previous scope and clears the refresh window, so the next refresh reads the whole new scope rather than only recent changes. Content is downloaded only from the Tenant SharePoint host, following at most one redirect, and its short-lived address never appears in a log or a failure.

A prune lists the whole scope and removes what it did not see, but only after recording that the listing finished: a site that cannot answer leaves every document in place. Its default interval is 168 hours and `0` disables it; the first prune is scheduled one interval after the Source is created. Queuing a scheduled run moves only the refresh schedule; the run becomes a prune while the prune is due, and only a finished prune moves its schedule. A prune that cannot start or fails waits for the next refresh slot instead of retrying on every scheduler tick. Pruning still matters for what a change log cannot report — an item the application loses permission to read, one moved out of a folder root, and anything missed when a stale token forces a full rescan.

Site pages are collected when the Source asks for them. Pages have no change log, so a refresh lists each site's pages and compares versions, and each page's canvas is read on its own, so an unreadable page affects only itself. The stored snapshot holds the title, the text above it, the description, the HTML of each text web part and the searchable text Microsoft prepared for the others; layout and web part configuration are not kept. The reader turns that into canonical blocks, so headings, paragraphs, list items and tables survive.

Runs share the Source attempt record with the other connectors and report whether they were a refresh or a prune. A run stops instead of writing when its Source scope, credential or generation has moved on, or when the Source is paused; a paused Source is not scheduled. At most one run per Source is open: an attempt that ends without completing closes its run, and a new attempt cancels a run an abandoned attempt left open. Provider requests are counted by operation and outcome, both bounded vocabularies, and runs log their start and result with no site address or item name.

## File and operation lifecycle

A FILE upload declares 1 byte–100 MiB (104,857,600 bytes), a normalized display filename, media type and lowercase SHA-256. Google binary acquisition and offline binary link reading share that ceiling; a lower configured provider limit remains allowed. The API authorizes the concrete Source, commits a Pair-bound generic upload intent, returns a provider-neutral presigned PUT authorization and receives no file bytes. Finalization verifies provider metadata outside the Connector transaction, then reacquires shared Tenant authority and rechecks concrete Source scope before adopting a new immutable `StoredObject` or discarding a duplicate staged object. Revocation during provider IO therefore prevents adoption. Duplicate content in one FILE Pair converges on one item/version/live attempt; finalized receipts make lost-response replay idempotent. Detection and extraction never run in the API transaction.

Reindex is idempotent while work is nonterminal. Item removal and source deletion are explicit POST commands that immediately invalidate retrieval mappings and return durable cleanup operations. Google item removal also excludes that item from subsequent sync acceptance. Connector owns adopted raw-object cleanup for both providers: provider deletion completes before upload/write ownership, versions/items, object metadata, and unreferenced Documents are removed in dependency order. Tracked writes can be released only after their version references are removed, in the same acceptance/cleanup transaction. See [object storage](object-storage.md) for reservation, adoption and abandoned-write cleanup. Cleanup results remain queryable after target deletion; `SUCCEEDED` and `SUPERSEDED` are terminal success states.

Source-level indexing errors represent unresolved failures of currently FAILED items at their current input version, not historical failed attempts. Successful reindex clears the recovered item's contribution while preserving errors from other still-failed items. Historical operations remain available without keeping a recovered or removed item failed in the Source aggregate.

`Source.pendingWork` includes nonterminal item cleanup even while the source remains ACTIVE. The existing detail polling therefore continues through DELETING and refreshes the item/count after durable cleanup completes; terminal cleanup does not keep polling alive.

Source status/error reconciliation uses the newest attempt per Connector item. A successful retry clears that item's historical failure without hiding another item's current failure. Historical attempts remain queryable; reconciliation does not delete evidence or treat an old failed attempt as current.

## Management authority and Group associations

All management requires current active IAM authority. Global access is capability-derived and does not depend on who created a Source. Scoped operational access belongs to the Source's recorded manager (`manager_actor_id`) while that Actor remains an active standard member managing at least one ordinary Group, and never applies to a PUBLIC Source; an existing non-public groupless Source keeps its narrow creator exception for deletion. Associating a Source with further Groups confers nothing on those Groups' managers beyond detaching it from their own Group. Scoped browse visibility includes PUBLIC Sources, membership-associated Sources, the actor's own non-public groupless Sources and the Sources they manage; visibility alone is not write authority, and catalog visibility is never document-content access. See [ADR 0011](../decisions/0011-source-manager-group-attachment-authority.md).

| --- | --- |
| Source list/detail, items, run/error history, attempt history and operation polling | Global `SOURCES_READ` or the permitted scoped browse/receipt policy |

| Existing Google credential OAuth app replacement | Global `SOURCES_MANAGE` only, rechecked across consent/provider IO |
| Rename, upload initiation/finalization, reindex, Google manual sync/schedule/pause | Global `SOURCES_MANAGE` or concrete scoped operational authority |
| Item removal and shared Source deletion | Global `SOURCES_DELETE` derived from `SOURCES_MANAGE` or Admin; only existing non-public groupless creator cleanup has a scoped exception |
| Source–Group replacement | Global `SOURCES_MANAGE` may save any ordinary-Group selection, including an empty one; the recorded manager may change only Groups they manage, so every added and every removed Group must be theirs and the remaining associations must match the stored set exactly |

Out-of-scope reads and concrete Source operations fail without revealing the target; global-only denied commands do not fall back to scoped management. Source and operation queries enforce Tenant/scope predicates before exposing results. Scope is checked again on replay/finalization, not inferred from a previously issued upload intent or operation ID.

Source associations accept only ordinary Groups (`system_key IS NULL`). Source option rows and totals exclude system Groups at the SQL boundary, and creation/replacement rejects Admin/Basic IDs even from a global administrator. V16 originally seeded Admin links; V48 removes those and any Basic links, advances affected Tenant authorization revisions, and guards new system associations or conversion of an associated Group into a system Group. Sources, ordinary associations, memberships and grants remain intact. Legacy pending Google intents containing system IDs fail current activation validation rather than silently changing their hash-bound proposal. Association changes serialize exclusively on the Tenant authority row; protected Source commits reauthorize under the corresponding lock. Admin receives all Source capabilities from `SYSTEM_ADMIN` expansion and retains global access without any Source association. This is Source administration, not a bypass of document-content ACLs.

A group manager's scoped operational authority is not this global bundle: it cannot remove items or delete shared Sources, apart from the narrow existing creator/groupless cleanup case in the matrix. ## Document-content access

A Source that is indexing other items keeps its retrieval-eligible Documents readable and searchable; `NOT_STARTED`, `FAILED` and `DELETING` Sources are excluded. `SourceDocumentAccessResolver` requires current active Tenant membership and a live retrieval-eligible mapping whose FILE or Google Drive Pair, Connector and Document are active/eligible. Each mapping is read according to its Pair's [access mode](#source-access-modes): PUBLIC by active Tenant members, PRIVATE additionally through current membership in at least one associated ordinary Group, and SYNC through the mapped file's retained Google permissions. Neither global administration, scoped management nor creator identity bypasses that content policy, and the ingestion account's email grants nothing. Actor-bound Search scopes are narrowed server-side, and current membership, eligible origins, grants and generation are rechecked after index IO and during passage expansion. Private Chat files use their separate Chat-owned authorization, not this Source resolver. Group replacement and access-type changes publish `SourceAccessChanged` inside their transaction; `SourceSearchService` exposes index-time `DocumentAccess` and per-request reader tokens for the Search projection ([Search index access](search.md)).

## Google Drive ACL observations — MEM-88

This is the observation and handoff contract; [Auto Sync](#source-access-modes) is its only consumer. As in Onyx, collected permissions are consumed server-side only: no HTTP endpoint or UI displays them, and the earlier read-only inspector was removed. Public and Private Sources ignore these observations. No Google Group expansion or Owner bypass is provided.

`GoogleDriveProvider.Session.permissions(fileId)` uses the existing OAuth grant and fully traverses `permissions.list` with `supportsAllDrives=true`, within existing cumulative request/time/byte limits. Permission page size is capped at 100. Duplicate IDs, cyclic page tokens, malformed or missing permission arrays, invalid field types and later-page failures do not return a partial snapshot. An explicit successful empty array is distinct from unknown or failed retrieval. Provider HTTP 404/410 and a file-level 403 on metadata or content use the unavailable-file `SOURCE_GOOGLE_NOT_FOUND` classification; this is not proof of deletion. A 403 whose reason is `insufficientPermissions`, or whose ErrorInfo detail is `ACCESS_TOKEN_SCOPE_INSUFFICIENT`, is `SOURCE_GOOGLE_SCOPE_INSUFFICIENT` on any Drive call: every Drive flow that stops for authentication stops for it (`requiresReconnect()`), and SOURCE_SYNC ends the run and marks the credential for reconnect. Any other non-quota 403 from `permissions.list` is `SOURCE_GOOGLE_ACCESS_DENIED`: the connected account can read the file but not its sharing settings. It is recorded on that file's snapshot while content synchronization continues. Quota reasons keep `SOURCE_GOOGLE_QUOTA`.

Permissions retain opaque Google IDs, type, role, nullable email/domain, expiration, deleted-account and pending-owner flags, `allowFileDiscovery`, `view`, `inheritedPermissionsDisabled` and all returned permissionDetails (permissionType, role, inheritedFrom, inherited). Missing optional fields stay unknown rather than becoming false. The API's ordinary permission view is requested; additional published-view permissions are not explicitly requested. Preserving a returned view does not turn published or metadata-only visibility into full-content access. Completion means the requested pages were collected, not that all effective access or group membership is known. My Drive does not necessarily expose inheritedFrom; do not infer missing ancestry.

SOURCE_SYNC collects after selected membership is checked and before content reuse. Folder permissions are collected once at their FILE frontier node, not once per child-list page. A metadata-version postflight rejects an observation if the version changes during retrieval. Provider I/O stays outside database transactions; the existing source/credential/scope/operation fences guard publication. A non-authentication ACL failure records failure independently of content acquisition; authentication retains the existing credential invalidation path. A successful content run therefore does not imply a successful ACL refresh.

### Handoff identity and state

V75 stores one `google_drive_acl_snapshots` row per `(tenant_id, source_id, file_id)` with source-qualified cascading deletion. Internal `JdbcGoogleDriveAclRepository.read(TenantId, SourceId, fileId)` returns `Optional<GoogleDriveAclSnapshot>` in one database statement, including current SourceItem/Document mapping. The consumer read `readByDocument` shares this lifecycle projection. Neither read performs actor authorization, and no HTTP endpoint exposes either.

| Data | Meaning |
| --- | --- |
| `revision` | Monotonic successful-observation revision, not an effective-policy revision; zero means no successful snapshot |
| `permissions` | Last complete provider result; failure cannot partially replace it |
| `status`, `errorCode` | Latest attempt SUCCEEDED/FAILED and sanitized error; evaluate independently of retained payload |
| `lastAttempt`, `lastSuccess` | Actual timestamps, operation, credential identity/revision, scope revision and traversal generation; lastSuccess is nullable |
| `contextStatus` | CURRENT, STALE, INVALID or UNOBSERVED for the retained successful observation |
| `currentContext` | Current tenant/source/credential activity, credential/scope revisions, traversal and membership generations, selected/excluded/removal evidence |
| `sourceItemId`, `documentIds` | Nullable/empty before publication; source-qualified provider-to-content mapping, never an Actor identity |
| `readAt` | Database observation time for the projection |

CURRENT only means matching active lifecycle and traversal provenance. It does not mean recent enough, SUCCEEDED on the latest attempt, complete effective access or permission to read. Consumers must examine status, lastSuccess, expiration and their own freshness policy. Failed-only rows have no successful provenance; missing rows are Optional.empty. Credential revocation/reconnect, scope changes, removal/exclusion, source deletion and traversal changes invalidate or stale old evidence rather than silently blessing it. No wall-clock freshness threshold or revocation SLA is fabricated: runs can queue, fail or stop.

#### Consumer read API and change event

Enforcement consumes two public `connector` types instead of reading the table.

`GoogleDriveAclReader.readByDocument(TenantId, DocumentId)` returns `List<GoogleDriveAclSnapshot>`, one per (Source, file) whose current SourceItem maps to the Document, ordered by Source and file ID. It makes no provider calls and performs no actor authorization. The mapping is keyed by `(tenant, Source, Document)`, so a Document has at most one Drive file per Source, and Google Sources assign their own Document identity: in practice the list holds zero or one snapshot. Consumers must not assume exactly one and must deny on an empty list.

`GoogleDriveAclChanged(tenantId, sourceId, fileId, documentIds, revision, status, errorCode)` is a Spring application event published inside the snapshot-writing transaction when the stored permission payload or the latest-attempt status changes. `fileId` is the Google provider file ID, `documentIds` are the currently mapped Documents (empty before publication) and `revision` is the successful-observation revision after the write. The event is a hint to re-read through `readByDocument`; grants must not be derived from it alone.

```json
{"tenantId": "7c…", "sourceId": "3a…", "fileId": "1Fx…Q9", "documentIds": ["9d…"],
 "revision": 4, "status": "SUCCEEDED", "errorCode": null}
```

`permissions` are exactly what `permissions.list` returns: direct entries and, where Google reports them, inherited entries with their `permissionDetails`. They are not a computed effective-access list. `expirationTime` is returned unchanged for the consumer to apply. `anyone` and link sharing keep the provider type, role and `allowFileDiscovery`; how they map to Tenant visibility is enforcement policy.

| Situation | status | revision | permissions | contextStatus | `GoogleDriveAclChanged` | Enforcement reading |
| --- | --- | --- | --- | --- | --- | --- |
| First successful observation | SUCCEEDED | 1 | Complete result | CURRENT | Yes | Grants apply; `ACCESS` refresh queued |
| Share added, role changed or share removed | SUCCEEDED | +1 | New complete result | CURRENT | Yes | Grants replaced; `ACCESS` refresh queued |
| Identical re-observation | SUCCEEDED | +1 | Unchanged | CURRENT | No | Nothing changes; `lastSuccess` advances |
| Later attempt fails, for example `SOURCE_GOOGLE_ACCESS_DENIED` | FAILED | Unchanged | Last complete result retained | Unchanged | Only when status changes | Retained grants apply until the next successful read |
| Never successfully observed | FAILED | 0 | Empty | UNOBSERVED | Yes, on the first failure | Deny: empty means unknown, not shared with nobody |
| No row yet | `Optional.empty` | — | — | — | No | Deny |
| A newer traversal has not re-observed the file | Either | Unchanged | Retained | STALE | No | Retained grants apply while the Document stays eligible |
| Deselected or removed file, scope or credential change, inactive Tenant/Source/credential | Either | Unchanged | Retained | INVALID | No | Retained grants apply only while the mapping stays retrieval-eligible; deselection, removal, revocation and inactive Tenant/Source hide the Document |

Context changes do not publish `GoogleDriveAclChanged`; lifecycle changes act through mapping eligibility. The enforcement reading is the Auto Sync policy of [Source access modes](#source-access-modes); Public and Private Sources do not read these snapshots.

ACL refresh does not require OCR. If provider version is unchanged, no content acquisition occurs. A sharing-only change that advances the provider version while bytes and filename stay identical follows the re-synchronization rule above: the current version's provider version is refreshed in place and its extraction reused, so the ACL snapshot updates without a new version, index attempt or re-extraction, and later observations of that version avoid repeated downloads. A changed file requires normal acquisition/indexing. Byte-identical comparison does not claim semantic deduplication of native snapshot envelopes.
