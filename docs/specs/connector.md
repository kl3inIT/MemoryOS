# Connector capability contract

## Ownership

Connector owns tenant-scoped Connector, Credential, ConnectorCredentialPair, ConnectorItem/version, source synchronization, index/cleanup operation associations, and Pair-to-Document provenance. The public product read model is Source; `sourceId` is the operational Pair identifier and never exposes persistence association names.

FILE and GOOGLE_DRIVE are implemented. Only an active tenant OWNER manages Sources and credentials; membership or possession of a Google account alone grants no management authority. FILE creation serializes on the tenant row, creates or reuses exactly one NO_AUTH Credential, and creates a PUBLIC Pair. Google consent creates an independent GOOGLE_OAUTH Credential, not a Source. Multiple Sources may share it; every Source has a distinct Connector and RESTRICTED Pair, independent selection, synchronization progress and item/Document identity. V18 removes Google singleton constraints while preserving existing IDs, encrypted grants, roots and content.

## Browser product model

The browser separates provider types from configured Sources. `/admin` uses expandable provider groups with search and provider/status/access filtering, operational summaries and direct navigation to `/admin/sources/{sourceId}`. Access is read-only: PUBLIC is displayed as workspace-member access, not anonymous Internet access; Google remains Restricted. `/admin/sources/new` has searchable FILE and Google Drive tiles, with no unimplemented provider entries. Existing Source screens use the shared Onyx-aligned layout and responsive setup rail, not new backend stages.

FILE setup remains one form with source name, drag/drop or file browsing, a removable file summary and one Upload and create action. A blank name is populated from the filename. Selection validates one supported file of 1 byte–10 MiB before creating a Source. One guarded submit creates, uploads and finalizes, then opens detail for indexing status. Upload retries retain the Source; finalization retries reuse the upload without another PUT. The single Upload file step is presentation only.

Source identity is route-owned through the detail path parameter, so creation, direct navigation, and browser history address one deterministic configured Source. Pending FILE finalization state lives above the Source routes and retains only the initiating Source/upload identifiers plus filename, never the presigned URI or bytes. Navigation to another Source exposes a return link; retry occurs against the initiating Source and emits no second provider PUT.

Google setup presents Credential → Connector using the Onyx-aligned credential card and Create New modal. The picker has a separate selection column before four metadata columns: ID (short UUID with full value on hover), Name (without repeating an identical account email), Created and Last Updated (local dates without times). On narrow screens the same metadata stacks into labelled groups without horizontal scrolling. Unusable credentials retain a warning and cannot be selected. The labelled three-dot Manage button discloses attachment count and guarded reconnect/revoke/delete actions. New consent selects the created credential; an existing active credential needs no JSON upload or repeat consent. Connector submission names the Source and atomically persists its General/Specific scope and initial sync. Specific is the safe default and accepts explicit file/folder links; General explains the connected account's My Drive boundary and hides the link editor. Creation has no saved-selection summary. Detail shows saved Specific roots only when present, never an empty “No files selected” state; saved General retains its scope summary despite its empty public roots list. Scope and link drafts survive mode round-trips, refresh and interval saves until explicit Save selection. Concurrent scope/credential/actor authority changes require explicit reload rather than stale retry. App/redirect configuration remains under collapsed Setup instructions; shared credential management and cleanup remain available. No account browser, document viewer, ACL editor, reader linking, Groups or Drive PUBLIC control is added.

Synchronization and Selected content use question-mark help popovers instead of persistent explanatory paragraphs. Guidance remains available by pointer or keyboard, including the broader OAuth-permission boundary. Link count, validation errors, unsaved changes and conflict warnings stay visible. Save selection is right-aligned directly below the links editor, with conditional Reload before it and no separate footer. Non-interactive file rows have no hover fill, so Reindex/Remove retain distinct button hover surfaces and the shared Button focus styles.

The Credentials disclosure retains a visible chevron in both states: down when collapsed, up when expanded. Its action label changes from Manage connection to Close instead of disappearing. The whole native summary remains pointer- and keyboard-operable.

Each Google Source displays its saved Automatic interval in Synchronization. The inline Edit interval form accepts whole minutes from 1 to 2147483647, supports Save interval, Cancel and keyboard operation, and never supplies a client-side fallback for a missing API value. Status refresh preserves interval and link drafts. A schedule conflict requires explicit Reload saved interval, without automatically retrying or replacing the root draft/revision. Editing an interval alone does not block Synchronize now, and a schedule save does not save or discard edited links.

Source management uses accessible, dismissible Radix notifications for creation, upload/finalization, Reindex, Synchronize now, remove/delete, selection/interval saves, credential management and explicit refresh/reload. Accepted asynchronous commands announce acceptance, then observe the returned operation ID for success, failure or supersession; disappearing aggregate `pendingWork` is not proof of that command's success. A status-read failure reports an unknown outcome, not failed processing. Reindex/removal observers are item-specific and cancelled on Source navigation. Synchronization completion means acquisition finished; upload/finalization acceptance also leaves indexing status to normal Source polling. The root notification provider keeps named creation/deletion results visible across redirects while clearing ordinary notices on pathname changes. Every notice, including errors, closes after five seconds without pausing for hover, keyboard focus or window blur; navigation does not restart the timer, and early dismissal remains available. Creation/upload retries retain known partial success instead of repeating completed work. Credential connection is confirmed only from a validated callback and active credential read; confirmation/OAuth failures remain accessible inside their dialog. Validation, conflicts and drafts remain in their editors. Background polling, ordinary navigation and opening/closing an editor do not generate toast noise.

## Application and persistence boundary

`DefaultSourceManagementService` owns common authorization, FILE upload adoption, orchestration, transaction boundaries, transition decisions, and typed failures. `DefaultGoogleDriveAuthorizationService`, `DefaultGoogleDriveConnectionService`, and `DefaultGoogleDriveSourceService` own Google grant lifecycle, revision-fenced provider sessions, and root configuration/sync scheduling respectively. They use capability-owned persistence repositories and public storage services, not object-storage persistence. `JdbcSourceUploadRepository` binds a generic browser upload to one Pair and persists its finalized item/version/attempt receipt. Google acquisition uses `ObjectWriteService`, never a fabricated browser-upload receipt. Application code contains no SQL, row mapping, locks, claims, or bulk updates; concrete internal JDBC repositories own those details.

## Google authorization and credential authority

Google ingestion authorization is separate from MemoryOS login: it never replaces the Actor or links a reader identity. `POST /api/credentials/google-drive/authorization` validates owner authority, credential name and `oauthClientJson` before returning an authorization URL. The JSON must be a downloaded Web application client, at most 16 KiB UTF-8, with nonblank client ID/secret and the exact configured redirect URI; desktop/service-account credentials, ambiguous duplicate/trailing JSON and untrusted endpoint values are rejected. Provider endpoints are fixed, never fetched from uploaded URLs.

Reauthorization requires `credentialId` and `expectedCredentialRevision` together. JSON may be omitted only when that credential already retains an owner app; there is no server-wide default app. The ten-minute, one-use consent continuation binds encrypted app data, Actor, Tenant, target credential and expected authority to the existing browser session, state, PKCE S256 and nonce. The callback `/login/oauth2/code/google-drive` validates signed OIDC identity, issuer, that app's audience/authorized party, nonce, verified email and agreement with the Drive account before rechecking OWNER authority. Required scopes are OpenID/email plus Drive, Sheets and Docs read-only. The Google subject pins the account across reconnects.

Callbacks redirect only to Google setup with a safe `connected` / `authorization-failed` outcome and credential identity where applicable. Owner app credentials and refresh grants are encrypted at rest with Tenant/credential/key-version binding; access tokens remain transient. Browser JSON is cleared before submission/on unmount and does not enter React Query mutation variables, browser storage or returned configuration. Authority changes remount the setup form and abort outstanding consent requests. Requests, continuations, responses and errors redact secrets. Missing Google encryption/redirect configuration fails Google operations closed without disabling FILE. Historical V16 requires owner-app reauthorization for legacy grants; V18 itself requires no new consent.

`GET /api/credentials/google-drive` returns only the active owner's Tenant catalog: ID, name, safe account email, status (`ACTIVE`, `NEEDS_REAUTHORIZATION`, `REVOKED`), authority `credentialRevision`, app-configured flag, creation/update timestamps and attached Source count. Normal refresh-token rotation compare-and-sets authority and payload revisions, increments only `payload_revision`, and preserves publication authority. Reauthorization, accepted authentication failure and revoke advance authority and fence every attached Source atomically; obsolete refresh results cannot defeat newer authority or a winning rotation. Publication checks usable authority inside its acceptance transaction. Locks follow Tenant → credential → Source, with attached Sources ordered deterministically.

`POST /api/credentials/google-drive/{credentialId}/revoke` requires `expectedCredentialRevision`. It commits local revocation, destroys the refresh grant, invalidates mappings and cancels sync/index work across every attachment before best-effort remote revocation. Remote failure or an unavailable encryption key cannot restore local authority. Revoke preserves all Sources, selections and the encrypted owner app for same-subject reconnect. Generic Source deletion cleans only that Source and retains its credential. `DELETE /api/credentials/google-drive/{credentialId}` requires a strong quoted numeric `If-Match`; only an unattached credential at that revision can be deleted. Known foreign IDs and missing IDs have the same result for an authorized other-Tenant owner; nonowners are rejected before lookup.

## Google selection and synchronization

`POST /api/sources/google-drive` accepts `name`, `credentialId`, required `scopeMode` (`GENERAL` or `SPECIFIC`) and `links`. SPECIFIC requires 1–20 explicit links. GENERAL requires an empty links array and resolves `metadata("root")` through that credential, validates the actual My Drive folder and persists its real ID internally. It does not discover Shared with me, Shared Drives or other users' drives. Missing/unknown modes, numeric enum values and mode/link mismatches fail without a partial Source or an expanded selection. Metadata validation runs outside SQL transactions, followed by a recheck of active owner and unchanged usable credential authority before Connector, Pair, Google source, roots and initial sync intent commit together. Different Sources may select the same provider file without sharing item/Document identity. V20 defaults existing Sources to SPECIFIC without changing their stored roots, credentials, intervals or content.

`GET /api/sources/{sourceId}/google-drive` returns `credentialId`, safe connection state, `oauthClientConfigured`, `scopeMode`, scope `revision`, `syncIntervalMinutes`, independent `scheduleRevision`, roots, last sync time, pending work and a safe error code. GENERAL returns `roots: []`, not an invented user-selected root link. The GET ETag remains the scope revision and caching is no-store. `PUT .../google-drive/roots` requires the same mode/link contract and one strong quoted numeric `If-Match`. SPECIFIC accepts distinct HTTPS Google Drive, Docs, Sheets or Slides file/folder links: the server parses supported URL shapes without fetching supplied URLs, then verifies metadata through the authorized provider session. Whole My Drive/Shared Drive links, trash, shortcuts and ancestor/descendant overlap fail; explicit files/folders inside Shared Drives remain supported. Bounded validation failure leaves selection unchanged. No root-browsing endpoint exists.

Accepted mode/root replacement atomically checks active owner, current scope and credential authority, increments scope revision, cancels obsolete sync/index work and invalidates prior retrieval mappings. It does not overwrite the independent interval or schedule revision. `POST .../google-drive/sync` requires usable authority and a saved General scope or nonempty Specific selection, returning a durable `SYNC_SOURCE` operation (`202`). General's empty public roots list does not disable synchronization: its internal verified root enters the existing PostgreSQL membership generations, frontier and page checkpoints. SOURCE_SYNC Redis messages still carry execution identifiers only. Both modes reconcile their persisted roots and descendants without an account-wide listing or Changes feed. Stable file IDs identify items; provider version/modified/checksum metadata determine freshness.

`PUT .../google-drive/schedule` accepts `{ "syncIntervalMinutes": 15 }` with one strong quoted numeric `If-Match` taken from the configuration body's `scheduleRevision`, not the GET response's scope ETag. The interval is an integer from 1 to 2147483647; V19 defaults new and existing Sources to 5 minutes and schedule revision 1 while preserving existing due timestamps. The command requires an authenticated active Tenant OWNER and the existing same-origin browser mutation guard. It locks Source authority, rechecks owner membership, and compare-and-sets only the interval, schedule revision and next due time. Stale schedules return `SOURCE_GOOGLE_REVISION_CONFLICT`. Success returns the full configuration with `200`, no-store caching and the new schedule ETag.

Saving schedules the next run from the database statement time plus the new interval. It neither enqueues nor cancels work, changes scope/generation/credential authority, nor invalidates existing Documents or other Sources. Local schedule edits remain available when the Google grant is unavailable and make no Google request. In-flight work completes normally and its next scheduling transition reads the latest saved interval. The minute-level due check is not a wall-clock start guarantee; no cron, independent pruning schedule or automatic-sync disable mode is exposed.

Folder reconciliation temporarily clears membership eligibility. An incomplete generation releases successfully adopted, confirmed snapshots for indexing but does not prune unseen items; failed files remain discoverable on a later sync. General verifies its persisted root against the current credential's My Drive before traversal and before pruning. Missing, changed, trashed, shared-drive or otherwise unverifiable roots and root enumeration failures cannot become empty completed generations. Only complete scoped traversal permits pruning; mode switches retain this requirement under the new scope revision. Persisted legacy whole-drive roots in SPECIFIC also fail closed before enumeration. Scope replacement, credential revocation and explicit removal fence obsolete acquisition/publication, and old work cannot resurrect removed items. Exact-current input awaiting membership confirmation is deferred without consuming extraction retries. Durable execution and extraction routing belong to [ingestion](ingestion.md); the current Document/artifact contract belongs to [document](document.md).

## File and operation lifecycle

A FILE upload declares 1 byte–10 MiB, a normalized display filename, media type, and lowercase SHA-256. The API commits a Pair-bound generic upload intent, returns a provider-neutral presigned PUT authorization, and receives no file bytes. Finalization verifies provider metadata outside the Connector transaction, then adopts a new immutable `StoredObject` or discards a duplicate staged object. Duplicate content in one FILE Pair converges on one item/version/live attempt. A finalized receipt makes lost-response replay idempotent. Detection and extraction never run in the API transaction.

Reindex is idempotent while work is nonterminal. Item removal and source deletion are explicit POST commands that immediately invalidate retrieval mappings and return durable cleanup operations. Google item removal also excludes that item from subsequent sync acceptance. Connector owns adopted raw-object cleanup for both providers: provider deletion completes before upload/write ownership, versions/items, object metadata, and unreferenced Documents are removed in dependency order. Tracked writes can be released only after their version references are removed, in the same acceptance/cleanup transaction. See [object storage](object-storage.md) for reservation, adoption and abandoned-write cleanup. Cleanup results remain queryable after target deletion; `SUCCEEDED` and `SUPERSEDED` are terminal success states.

Source-level indexing errors represent unresolved failures of currently FAILED items at their current input version, not historical failed attempts. Successful reindex clears the recovered item's contribution while preserving errors from other still-failed items. Historical operations remain available without keeping a recovered or removed item failed in the Source aggregate.

`Source.pendingWork` includes nonterminal item cleanup even while the source remains ACTIVE. The existing detail polling therefore continues through DELETING and refreshes the item/count after durable cleanup completes; terminal cleanup does not keep polling alive.

## Access

`SourceDocumentAccessResolver` grants PUBLIC read clearance only when the actor has current active tenant membership and a live retrieval-eligible mapping whose PUBLIC FILE Pair, FILE Connector, and Document are active/eligible. GOOGLE_DRIVE remains RESTRICTED and is explicitly excluded from that resolver, including after successful indexing. Source-management authority does not imply document-read access; inactive/deleting state fails closed. Google permissions are not collected or enforced, and neither tenant membership nor the ingestion account email supplies a Drive read policy.
