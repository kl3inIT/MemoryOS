# Document capability contract

The implemented Chat UserFile consumer protects `chat_user_file.document_id` alongside Connector mappings in `removeUnreferenced`. UserFile publication stamps server-owned private origin/file/owner metadata; current chunk sets propagate `userFileId` to the index. Source cleanup cannot delete a still-referenced private Document. Private plaintext is owned by Chat, not a reintroduced Document history/full-text ledger.

Document owns the current metadata, extracted-file reference and current chunk set independently of provider implementation. A Document is Tenant-scoped and either ELIGIBLE or INELIGIBLE. Its stable ID, title, detected media type, source-content SHA-256, metadata and extraction artifact reference are updated in place. PostgreSQL stores bounded current chunk text/provenance, not a duplicate full extracted-text column, immutable DocumentVersion history or embedding arrays.

`DocumentCommandPort.publish` creates a Document or replaces the current metadata/reference on the mapped Document under a row lock. Connector owns provenance mappings; Document never imports Connector or Ingestion types. The ingestion transaction commits this replacement and artifact adoption together with provenance and token-fenced operation completion. A failed or stale replacement rolls back and leaves the previous reference intact.

Structured extraction stores one private, SHA-256-verified JSON object under `extracted/<tenant>/<artifact>/document.json`. Every route writes `memoryos-extraction-v2`, the typed `ExtractedDocument` model owned by this module; each provider adapter maps its own output onto it and drops what the model has no place for, so no parser's keys reach a reader. Ordered blocks carry `index`, `kind` (`HEADING`, `PARAGRAPH`, `LIST_ITEM`, `TABLE`, `IMAGE`), `text`, optional `headingLevel`, `locations`, `table`, `sheetName` and, for Docling pictures, `image`. A table has `rowCount`, `columnCount` and one cell shape for every provider: zero-based `row`/`column`, `rowSpan`/`columnSpan` (omitted when 1), `columnHeader`/`rowHeader` only where the provider marked them, `text`, and nested `blocks` for a Google Docs cell. `pages` lists `page_no`, `width` and `height` in PDF points; an image input has none. Spreadsheet formulas, merges, cell types and provider object metadata (Docs styles and elements, Sheets properties) are not stored, and formulas are never evaluated. Google input provenance is carried by the source descriptor. Docling embeds image data in the artifact, but normalized text contains semantic text/table content rather than binary image data URIs; native Docs preserve provider object metadata without promising downloaded image bytes. Plain text is a transient parser result used to build the artifact, not another database copy. Parser configuration is diagnostic metadata, never a uniqueness key or retry constraint. Routing and hard input/output bounds belong to the [Ingestion contract](ingestion.md).

Stored `memoryos-extraction-v1` artifacts remain readable through one upgrader, `ExtractionArtifactReader`, applied whenever an artifact is read. It accepts both v1 flavours: the Docling route's copied `prov` items, `TableData.table_cells` offsets and `pages` object, and the native readers' object provenance, `table.cells` and SharePoint lowercase kinds with `rows`. Nothing else reads v1, so regenerating chunks never needs the original file again.

Chunk `provenanceJson` is also a presentation input, built from block `locations`: no location is `null`, one is that location object and several are an array. Merged text blocks list each block's value, and table rows wrap the block value as `{source, tableRow}`. Readers rely only on these location keys and ignore anything else: PDF and image `page_no` and `bbox` with `l`, `t`, `r`, `b`, `coord_origin` (`TOPLEFT` or `BOTTOMLEFT`) and optional `frame_width` and `frame_height`; workbook `sheetIndex`, `sheetName` and `visibility` (Google Sheets records `sheetIndex` only); Google Docs `tabId`, `section`, `startIndex` and `endIndex`. Changing these keys requires updating the Chat/Search location labels and PDF outlines.

A `bbox` without a frame is in PDF user space, in points. A `bbox` with `frame_width` and `frame_height` is measured from the top left of a frame of that size as a reader sees it, x right and y down, with `coord_origin: TOPLEFT`: a pixel of a picture after its EXIF orientation, or a point of a PDF page as displayed, `/Rotate` applied. Both keys are present or neither is, and they are omitted when absent, so a location written before them reads and writes back unchanged. The PaddleOCR-VL adapter is the only writer of framed boxes; when it writes one, and what the space rests on, is in the [Ingestion contract](ingestion.md#paddleocr-vl-for-scans-and-images).

The stored original of a readable Document is served to a reader as it is, whatever its media type. `DocumentOriginalService` opens it through `SourceSearchService.originals` under the reader's own authority — Search needs `SEARCH_READ`, a Chat citation needs Tenant membership and Document eligibility — and repeats every check after the object is opened, for each byte range too, so a reader who loses access between two ranges is stopped. Originals above 64 MiB are not served. An object that declares itself a PDF still has to begin with `%PDF-` before its first byte reaches the browser. The response carries the object's declared type, `Content-Disposition: inline`, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`; a type a browser would run as script in this origin (`text/html`, `image/svg+xml`, `application/xhtml+xml`) and an unusable declared type are sent as an attachment instead of shown. One `Range` header is honoured so pdf.js reads only the parts of a large original it renders.

The browser reads a PDF original through its own range source (`web/src/features/preview/pdf-range-source.ts`) instead of pdf.js's URL loader. An opening is one authorized request for the head (128 KiB), whose `Content-Range` tells the size, followed by the tail (64 KiB) where the cross-reference table is; a file up to 1 MiB is read whole in those two and nothing probes the file whole. pdf.js is told 16 KiB blocks, and the ranges it asks for together are planned as one (`pdf-range-plan.ts`): neighbours within 64 KiB are a single request; one or two runs are ordinary reading and are extended to 256 KiB, forwards and, where held bytes stop that, backwards; three or more separate runs are fetched exactly. Those are the page dictionaries of a document that lists its pages flat, as a scanner writes one: pdf.js needs every one of them before it can load the document, each a page's picture apart, and megabyte chunks made that the whole file. At most twelve requests are in flight, the most recent ask first, and a failed read falls back to one whole read. The blocks a session fetched are kept in page memory per original URL (which names the document and its generation), 32 MiB in all, least recently used first out, forgotten between ten and twenty minutes after their last use (a sweep every ten minutes drops what was idle for ten) and never written to the HTTP cache: every read asks for `no-store`. A read that fails once the document is open reads it whole too: the document is mounted again at the cited page and follows the reader from there. They are not used before a new authorized request has succeeded: the head when nothing is held, one byte otherwise; a refusal or a different size drops them, so a reader who lost access cannot reopen a document from memory.

The cited page is mounted alone until it is drawn or the reader scrolls, types or picks a page; its neighbours follow, and the page rail draws the thumbnails in view one at a time, nearest the current page first, while the canvas has nothing left to draw. The readers' code, the pdf.js worker and the original's first bytes start together as a dialog or evidence tab shows the original (`warmOriginal`), and a Search result loads the code when it is pointed at or focused. Measurements are in the [fast-open increment](../increments/active/pdf-original-fast-open/verification.md).

A workbook is the exception: it never reaches the browser as bytes, because the app ships no client-side workbook parser. `GET /api/{search,chat}/documents/{id}/spreadsheet` resolves the same original under the same authority and returns each sheet as CSV text through `SpreadsheetPreview`, cut at a row boundary. A Document of any other type is not readable as a workbook.

A citation is shown inside that original, and the rule the whole path exists for is that **an unlocated citation is never drawn**. PDFs and pictures read by PaddleOCR-VL carry recorded coordinates, so the recorded `page_no`/`bbox` is drawn directly. Everywhere else the passage is searched for in the text the renderer produced, which legitimately differs from the extraction: a table row is flattened onto one line, a justified paragraph carries soft hyphens, a heading is set in capitals and Vietnamese accents may arrive as combining marks. Both sides are normalized — NFC per grapheme cluster, case folded, runs of whitespace collapsed, soft hyphens and zero-width characters dropped — and the passage is accepted only as its single exact occurrence, or, failing that, as the span between its first and last eight words when that span is within 40% of the expected length and each end has at least three words. Anything else is `none`: nothing is drawn and the reader is told so. A passage repeated in the document — a table header on every page, a figure that appears in two statements — is placed only by the heading it was read under: the trail is tried from its most specific end, and the first heading that itself occurs exactly once bounds the search, giving `approximate`. A repeated passage under no such heading is `none`, because nothing says which occurrence was cited.

A Search result's passage also shows the reader's own words. Inside a located passage of a text original (Word, CSV, Markdown, source and plain text) each occurrence of the question and of its words of two characters or more is painted as a third highlight, `memoryos-citation-term`, above the passage highlight: a darker step of the same highlighter in the document's ink, underlined so that more than a shade tells it apart. One matcher (`matchTerms` in `preview-highlight.ts`) serves the original and the result card, under the normalization the passage locator uses; accents are not stripped, so a word typed without them marks nothing. Nothing is marked outside a located passage or for an unlocated one, and a passage that contains none of the words, as a semantic match may, keeps the passage highlight alone. A PDF stays at its recorded region and a workbook at its row. Source and plain text are drawn twice, plain at once and highlighted when the syntax highlighter has loaded; the passages and the words are placed again in the second rendering, because a range on text that left the document paints nothing.

A workbook citation is not searched for at all. Extraction records the sheet name and the sheet row the passage
came from, and the reader marks that row on that sheet, bringing its tab forward. Searching would fail there for a
reason no normalization fixes: extraction and the preview format the same cell differently, one reading
`$   1,618.50` where the other reads `1618.5`. `SpreadsheetPreview` therefore keeps an absent row on its own empty
line, unlike Onyx, so line *n* of a sheet is sheet row *n*. A row the preview did not render — the header line, a
sheet that is gone, a row past the preview cut — is left unplaced, and nothing is drawn.

Every original with more than one cited passage offers the same previous, position and next control. Text formats and workbooks float it over the document; a PDF takes it as one more group of the toolbar it already has, beside the page field and the zoom. A step selects the passage as its rail card does: the PDF receives that passage's pages and regions and scrolls to the first region, also when the passage is on the page already open. Nothing but another passage moves a reader who has scrolled elsewhere.

A recorded region is drawn once however many passages record it, and every region of a page is painted as one layer. Each row of a Docling table wraps that table's own box, so a cited table records the same region once per row; drawing each one multiplies a translucent highlight over itself until the page reads as a solid block rather than as the document the citation points at.

A box in PDF user space is drawn on an upright page only: on a page with `/Rotate` the extraction frame may already be orientation-corrected (Docling's boxes there are of that kind), so such a box is left undrawn. A framed box is drawn as shares of the surface that shows its frame, at any rotation, and only where the frame is the one shown: on a PDF page when the frame has the displayed page's proportions (within 1%), on a picture when the picture's decoded size (`naturalWidth` × `naturalHeight`, EXIF orientation applied) is exactly `frame_width` × `frame_height`. The image viewer draws the active citation's regions on the picture's one page in a layer that takes the picture's place and transform, so the mark follows zoom, pan and the reader's own turn; it uses the PDF highlight's tokens and one multiplied layer. A box read with half a frame, a frame without a size or a framed box from the bottom left is no box. A region is never scaled onto a picture of another size.

The rail reports a picture's citation as located once the view has drawn it and as not found when the view refused the frame; a picture with no recorded region keeps "Không có lớp văn bản". A PDF citation is reported from what provenance recorded, not from what the page drew: a framed box the PDF reader refuses, or a user-space box on a rotated page, still reads as located.

A Markdown original is read as the document it is — headings, paragraphs and tables — through the same rendering an assistant answer uses, rather than as highlighted source. Source files and plain text keep the source rendering, which is what a reader of those wants.

The chunk header `StructuredDocumentChunker` writes in front of each passage (a `Title:` line and, under headings, a `Section:` line) is not part of the document and is removed before a citation is located or shown. The heading trail is shown beside the citation as the context it was read in.

Docling normalized table text preserves leading and skipped columns with tabs derived from cell offsets, rather than shifting sparse values left. Row gaps retain their offsets, and padding counts against the existing text-size bound before allocation. Canonical cell coordinates and OCR values are not rewritten by text rendering.

The owned OCR image may correct scanned PDF orientation before layout. Canonical `pages`, images and bounding boxes then describe the corrected page frame. Optional `page_orientation`, keyed by physical page number, preserves the service's `body.meta.memoryos__orientation`: detector revision, clockwise correction, reason and, for examined pages, original displayed size and PDF rotation. A null correction means abstention, not an inferred angle. Source bytes are unchanged; the correction is relative to the original displayed page frame. The bounded Java adapter retains the document JSON directly because Java SDK 0.6.5 drops namespaced custom metadata. Orientation does not establish a financial period or authorize correcting OCR values.

Docling OCR text and table row/column associations are inferred output. Successful publication and indexing do not validate digit accuracy, period-column assignment or individual-cell completeness. The [Tasco corpus investigation](../increments/completed/tasco-scanned-pdf-ocr/design.md) records financial fidelity separately from pipeline success.

Docling artifacts add a diagnostic-only `financial_checks` array. A `CASH_FLOW_CLOSING_BALANCE` check evaluates `50 + 60 + 61 = 70` only within one table with recognized English/Vietnamese cash-flow labels, matching ordered row codes and explicit period-column headers. Each check identifies its `block_index` and, where known, `column_index`; status is `CONSISTENT`, `INCONSISTENT`, `INVALID_NUMERIC`, `INCOMPLETE` or `AMBIGUOUS`, with bounded reason and affected-row codes. Exact integer arithmetic accepts balanced parentheses/ASCII minus and consistent grouping; blank, absent and standalone dash amounts are not zero. Merged/overlapping cells and ambiguous period headers are not repaired.

Unresolved row/header structure additionally reports bounded `structure_issues` with `reason` and the relevant `row_code` or `column_index`; any such issue prevents arithmetic assessment of that table. Assessed periods include `period_identity`. Recognition supports explicit beginning-of-year wording, clean Vietnamese numeric-quarter/year headers, and contiguous header ancestry of at most four levels. Shared currency-only parents are allowed; merged period parents, conflicting periods, missing ancestry, damaged codes and combined beginning/end labels remain unassessed. Header-edge rule glyphs may be ignored for identity recognition, never for numeric parsing.

`INCOME_STATEMENT_ROW_IDENTITY` reports `INCOMPLETE` / `NON_ROW_ORIENTED_INCOME_LABELS` when at least two recognized income labels occupy distinct columns of one body row and match codes `10`, `20` or `50` in one unambiguous preceding code row. It identifies `label_row_index` and `code_row_index`, but does not transpose the table or infer periods. Vertical income rows, metric headers, labels without matching codes and ambiguous code bands do not establish this check.

Income code bands require valid table dimensions and at least two distinct supported identities in valid single cells. Malformed code cells neither establish a band nor suppress one established by valid cells. Income-label geometry errors are reported only after a valid code band is established.

The parser configuration records `financialChecks=cash-flow-income-v2` for these assessments; the canonical artifact schema and source blocks remain unchanged.

These checks never rewrite source cells, normalized text or table geometry. An empty array means no supported check was identified, not a clean financial report; `CONSISTENT` certifies only that scoped arithmetic identity. Unsupported split labels and cross-table statements remain unassessed. Work/output is bounded to 128 checks, 20,000 blocks, 100,000 total cells, 4,096 cells/rows per table, 64 columns, 512-character labels and 80-character amounts; global assessment exhaustion emits `ASSESSMENT_LIMIT` rather than silently implying completion. Existing artifacts may omit this additive field; existing chunk readers continue consuming `blocks`, not diagnostic text.

Artifact rows are staged before object writes, marked write-complete after PUT/checksum inspection, and adopted in the transaction that replaces the Document reference. Cleanup never selects an artifact referenced by a current Document. After replacement commits, the old artifact is reclaimed by the recurring sweep. Expired uncertain writes retain a deletion tombstone and are swept daily to catch a late PUT. Retry can produce different output; only the current operation claim may publish.

Google publication is fenced by current source scope, usable credential authority revision, current item/input version and eligible non-excluded membership as well as the processing token/lease. Connector validates these inside the publication transaction; it does not rely on a previously opened Google session. Temporary folder-reconciliation ineligibility defers otherwise-current indexing rather than losing it; changed scope, disconnected credentials or removed items cannot publish stale artifacts. The existing current Document/reference can remain stored after invalidation, but that is not permission to read it. Google Sources are read according to their [access mode](connector.md#source-access-modes); Document ELIGIBLE status is not an ACL grant. Authorization and access exclusions are defined in the [Connector contract](connector.md).

When Connector removes provenance, `DocumentCommandPort.removeUnreferenced` deletes the Document only after no live mapping remains; current chunks cascade and artifact cleanup follows. Synchronous `DocumentChanged` events let Ingestion retain projection deletion work beyond that deletion. V12 removed history/full stored text; V17 adds only current chunks, artifact reader protection and current Search readiness. Missing legacy artifacts require the existing Source reindex flow.

Every successful publication assigns a new `content_generation` and clears current chunk and error markers. It keeps `searchable_generation`, so the previously ready generation stays served until the new generation becomes ready and replaces it; pending or failed indexing of the new generation never withdraws the served one. `DocumentChunkPort` supplies bounded checksum-verified artifact reads, current chunk publication, batch served-generation checks, the retained (served plus current) generations for index cleanup, current passage reads and readiness transitions. The chunk convention prevents reuse of an obsolete chunking representation. An expiring reader row protects an old artifact until its bytes have been read. Late chunk publication requires the matching current generation under a Document lock. The [Search contract](search.md) owns chunking/indexing and retrieval behavior; Document never imports Retrieval or Ingestion internals.

Raw Google input objects and connector input snapshots remain separate from extraction artifacts. V18–V20 add tracked server writes, credential authority and durable synchronization without a Document-version ledger. FILE cleanup still deletes provider objects before relational ownership, including after Tenant deactivation.

Chunk convention `structured-cl100k-768-v4` reads the one table shape. A table with any `columnHeader` cell reads as labelled values (`Header: value`, spanned headers joined with ` / `, a `Row:` line from row-header cells, `Column N` for an unlabelled column); a blank header cell adds no label and a blank cell no line, as in address mode. Any other table reads by cell address (`[A1] value`) under its sheet name, including nested Docs cell blocks. The chunker never infers that the first row is a header; the headers it reads are the provider's, and the PaddleOCR-VL adapter's are measured (see [ingestion](ingestion.md#paddleocr-vl-for-scans-and-images)). Against v2 this changes two things: a Docling table without column headers reads by address instead of `Column N: value`, and SharePoint pages gain their headings, list items and tables, which v2 did not recognise. A SharePoint row of `th` cells marks column headers and a `th` beside `td` cells marks a row header; that is the author's own markup, so nothing is inferred. First chunk publication reloads the canonical repository representation, so its UserFile identity matches later reads. A convention change regenerates chunks from the stored extraction artifact, not raw-file OCR. Because the Search index identity includes the convention, deploying v3 requires the existing projection backfill and may temporarily reduce Search coverage until it completes; it is not a zero-cost index migration.
