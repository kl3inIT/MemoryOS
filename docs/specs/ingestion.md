# Ingestion capability contract

Ingestion owns asynchronous indexing and cleanup orchestration. It depends only on public Connector, Document, Object Storage, and Tenant APIs. Provider parsing enters through `SourceContentExtractor`; no Tika or AWS SDK type crosses the core boundary.

The default Redis command timeout is 5 seconds, above the 2-second blocking stream read.
Overrides must preserve timeout headroom. Consumer failures log exception and root-cause
class names without exposing exception messages or credentials.

PostgreSQL operation rows are the sole durable authority for Tenant ownership, eligibility, stable delivery identity, dispatch evidence, processing tokens, leases, retry counts, and terminal state. db-scheduler relays bounded eligible index and cleanup identifiers to separate versioned Redis Streams. A consumer reloads one operation, acquires a fresh identifier-scoped claim token and two-minute lease, and renews long-running indexing and cleanup through token-fenced updates. Every repository predicate retains the durable `TenantId` without ambient context. Index work carries an immutable `StoredObjectReference`; the worker opens and verifies provider metadata, then streams `ObjectContent` into extraction outside database transactions. Final publication runs in one transaction and requires the current processing token; a stale worker rolls back its Document metadata/reference update before acknowledging the superseded delivery.

Redis messages contain only `tenant_id`, `operation_kind`, `operation_id`, and `delivery_id`. Manual acknowledgement occurs only after durable completion or authoritative proof that the delivery is missing, terminal, superseded, duplicate, or protected by another live lease. Pending reclaim requires both Redis idle evidence and an expired or absent PostgreSQL processing lease. Bounded rediscovery republishes nonterminal work after Redis restart, trim, or loss; publish/evidence races may duplicate but cannot lose the PostgreSQL operation. Inactive-Tenant indexing is cancelled before dispatch, while cleanup remains eligible after deactivation. The runtime has no direct PostgreSQL polling executor or alternate compatibility path.

The FILE adapter detects actual content. PDF/DOCX/PPTX use Docling Serve through the official Java SDK; only UTF-8 TXT/Markdown retain the bounded Tika child JVM. PDF admission checks encryption and page count without extracting content. Docling receives bounded bytes, never source credentials or fetch URLs, and produces JSON plus text with EasyOCR `vi,en`, accurate table extraction, and embedded images. Partial/empty results are rejected; service failures use the existing bounded retry path with no Tika fallback. A 10 MiB input cap, 200-page default, 5-minute default processing timeout, 64 MiB transport response cap, 32 MiB canonical artifact cap, and 2,000,000-character text cap bound work and publication. HTTP cancellation is not a guarantee of remote process cancellation; late work cannot publish without the current PostgreSQL claim.

Diagnostic parser metadata includes the SDK, pinned service/model-image revision and options; it does not pin retry output. Document-owned artifact tracking, adoption and cleanup are defined in the [Document contract](document.md). db-scheduler runs artifact cleanup every minute independently of ingestion; artifacts referenced by current Documents remain protected. Google Drive routing and native Sheets/Docs/table readers are not implemented in this increment.

Cleanup is allowed after Tenant deactivation but cannot create content or access. For REMOVE_ITEM and DELETE_SOURCE, Ingestion renews the operation lease while asking Connector for adopted objects, idempotently marks each `DELETE_PENDING`, performs provider deletion, and only then asks Connector to remove provenance, attempts, upload associations, versions/items/Pair/Connector, stored-object metadata, and unreferenced Documents. Generic abandoned-upload cleanup is a separate object-storage task and never selects adopted objects.

## Processing telemetry

The coordinator records `memoryos.operation.outcomes` for every processing invocation, independently of Redis acknowledgement. Labels are `workload` (INGESTION, CLEANUP) and `outcome` (COMPLETED, SKIPPED, FAILED, UNHANDLED). FAILED includes handled extraction failures and scheduled retries; UNHANDLED means a runtime exception escaped the coordinator. A duplicate or stale claim produces SKIPPED. These are invocation counts, not unique durable operation counts or terminal-failure accounting. An ACK failure cannot change the already-recorded outcome.

`memoryos.operation.initial.queue.wait`, tagged only by workload, measures PostgreSQL `started_at - created_at` at the first successful claim (`processing_attempts = 1`). Both timestamps are database-authored. It includes initial dispatch delay and worker downtime, but excludes subsequent retry/backoff/reclaim waits, processing and ACK. A negative clock adjustment records zero. Rejected claims have no wait sample. First-claim samples can be lost on a crash after claim; no business decision depends on telemetry.

The timer's explicit histogram boundaries are 100 ms, 1/5/15/30 seconds, 1/5/15 minutes and 1 hour. They define diagnostic resolution, not an approved latency SLO. The staging OTLP path exports durations in milliseconds. Grafana shows outcome rates and initial-wait p95 separately from Redis transport processing time.
