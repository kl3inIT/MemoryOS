# Ingestion capability contract

MEM-81 adds `USER_FILE` delivery through the existing PostgreSQL dispatch/Redis relay. Chat owns `chat_file_work` and the public `UserFileWorkPort`; Ingestion's file coordinator reuses extraction and artifact staging, while Chat's work service owns authorized/fenced Document publication and reference release. Worker imports only that service/repository, not Chat inference/catalog/SSE. Processing errors retry up to three attempts; deletion work retries without that processing limit. A stale parse cannot publish after delete. Existing Redis processing metrics include bounded `user_file` labels. Full file-format, large-input and Chat/private-search acceptance remain in the active increment.

Chat HTML/EML/EPUB and image validation reuse the Source Tika child-process lifecycle (512 MiB heap, 90-second timeout, process-tree termination). The child reads the bounded Chat spool by path; its response preserves canonical JSON. Source's original 10 MiB byte-input protocol remains scoped to Source. PNG/JPEG use ImageIO; WebP uses TwelveMonkeys 3.15.0, with one-frame decoding, 144-million-pixel guard and sampled validation. Original image bytes are retained, not reencoded. These bounds are rejection/resource safeguards, not a throughput or peak-RSS guarantee.

Integration boundary: this contract combines the implemented Google branch with main IAM/Search. The [isolated integration plan](../increments/active/google-drive-structured-ingestion/plan.md#isolated-main-integration--2026-09-09) tracks pending combined verification; linked prior tests/runtime observations remain pre-integration evidence.

Ingestion owns asynchronous selection verification, source synchronization, indexing, Search projection and cleanup orchestration. It depends only on public Connector, Document, Object Storage, IAM, and Retrieval APIs. Provider parsing enters through `SourceContentExtractor`; no Tika or AWS SDK type crosses the core boundary. Google source authorization, selection admission and run-history reads are defined in the [Connector contract](connector.md).

The workload set is `INGESTION`, `CLEANUP`, `SEARCH`, `SOURCE_SYNC`, and `GOOGLE_DRIVE_SELECTION_VALIDATION`. Document publication synchronously records durable projection intent; the existing relay/Redis/claim/renewal/acknowledgment mechanism delivers it. `SearchIngestionCoordinator` prepares current chunks, invokes the public `SearchIndex` contract and commits readiness only after verified indexing under its claim. `SearchProjectionMaintenance` rotates through current Documents for backfill/repair and invokes stale projection cleanup. Detailed semantics and limits live in the [Search contract](search.md).

The default Redis command timeout is 5 seconds, above the 2-second blocking stream read.
Overrides must preserve timeout headroom. Consumer failures log exception and root-cause
class names without exposing exception messages or credentials.

PostgreSQL operation rows are the sole durable authority for Tenant ownership, eligibility, stable delivery identity, dispatch evidence, processing tokens, leases, retry counts and terminal state. db-scheduler relays bounded identifiers to separate versioned Redis Streams for INGESTION, CLEANUP, SEARCH, SOURCE_SYNC and GOOGLE_DRIVE_SELECTION_VALIDATION. Consumers reload and acquire fresh identifier-scoped claim tokens/two-minute leases, renewed every 30 seconds through fenced updates. Repository authority remains explicitly Tenant-bound. Index work carries immutable `StoredObjectReference` and persisted `SourceInputDescriptor`; bytes are verified/extracted outside database transactions. Final publication commits Document/artifact replacement, provenance and fenced operation completion together; stale publication rolls back before acknowledgement.

Redis messages carry four business identifiers: `tenant_id`, `operation_kind`, `operation_id`, and `delivery_id`. Optional `origin_trace_id`/`origin_span_id` and `publish_trace_id`/`publish_span_id` provide diagnostic causal links, never business state, credentials or authority. Manual acknowledgement occurs only after durable completion or authoritative proof that the delivery is missing, terminal, superseded, duplicate, or protected by another live lease. Pending reclaim requires both Redis idle evidence and an expired or absent PostgreSQL processing lease. Bounded rediscovery republishes nonterminal work after Redis restart, trim, or loss; publish/evidence races may duplicate but cannot lose the PostgreSQL operation. Inactive-Tenant indexing and synchronization are cancelled before dispatch, while cleanup remains eligible after deactivation. The runtime has no direct PostgreSQL polling executor or alternate compatibility path.

The FILE adapter detects actual content. PDF/DOCX/PPTX use Docling Serve through the official Java SDK; only UTF-8 TXT/Markdown retain the bounded Tika child JVM. PDF admission checks encryption and page count without extracting content. Docling receives bounded bytes, never source credentials or fetch URLs, and produces JSON plus text with EasyOCR `vi,en`, accurate table extraction, and embedded images. Partial/empty results are rejected. Typed `ExtractionException` failures terminate the attempt with `SOURCE_EXTRACTION_<failure>`; unexpected runtime failures use the bounded retry path. No Docling-to-Tika fallback exists. A 10 MiB input cap, 200-page default, 5-minute default processing timeout, 64 MiB transport response cap, 32 MiB canonical artifact cap, and 2,000,000-character text cap bound work and publication. HTTP cancellation is not a guarantee of remote process cancellation; late work cannot publish without the current PostgreSQL claim.

## Durable Google Drive selection verification

`GOOGLE_DRIVE_SELECTION_VALIDATION` uses the existing dispatch/relay/lease/reclaim/control-plane path, not an API executor or second queue framework. Admission commits only an immutable candidate/receipt; create does not expose an active Source before worker activation. Claims serialize selection verification per credential without keeping SQL transactions open during Google calls. V27 checkpoints entries, metadata and ancestor traversal so restart, quota backoff and redelivery do not discard verified progress.

Each batch permits at most 32 uncached metadata calls and checks 30-second elapsed time between bounded calls. Operation request/metadata budgets are `min(100000,maxRoots*64+4096)` and `min(50000,maxRoots*32+4096)`, with 200,000 ancestor checkpoints and a 3,600,000 ms accumulated execution budget. Quota/unavailable/inconsistent provider errors retry from checkpoints after 30 seconds and fail at five such attempts; ordinary batch continuation spends no failure attempt. These are selection limits, separate from per-input acquisition and discovery limits.

Activation rechecks current active Tenant and initiating Actor global `SOURCES_MANAGE`, credential identity/revision, Source/scope/discovery/mode and live claim in one transaction. Invalid/stale/superseded work cannot change active scope, schedule or Documents. Shared authority and Source/Tenant deletion fence pending intents, including creates whose Source is not yet active. Worker workload routing, topology, relay and bounded metrics allowlists include selection validation.

Measured 20/21/100/1,000-root verification and approval scenarios reused durable checkpoints with processor reconstruction between batches. The [selection-capacity evidence](../tests/connector.md#measured-selection-and-history-capacity--2026-09-08) records exact provider-port call counts and JDBC/resource caveats; this is not HTTP, process-restart, production-pooling or 100,000-file traversal proof.

## Durable Google Drive synchronization

`SYNC_SOURCE` operations use the SOURCE_SYNC workload and durable `source_sync_attempts`, selected-root/folder frontier, membership generations and page checkpoints. The control plane checks due sources every minute. Enqueue, unavailable-grant postponement, successful completion, terminal item failure and exhausted retry all schedule the next source sync using its persisted interval; the default is 5 minutes. An authorized schedule edit does not interrupt an existing operation, whose completion uses the latest saved interval. Manual sync, short retry backoff and continuation timing remain unchanged; the [Connector contract](connector.md) owns the interval editor/API and independent revision semantics. Each claim processes at most 16 steps and checks a 45-second execution budget between steps, then durably continues with a new delivery rather than retaining an in-memory recursive traversal. This is not a cancellation guarantee for a provider call already in progress.

Every sync reconciles its persisted roots and folder descendants, checkpointing each complete page. SPECIFIC uses explicitly selected files/folders; GENERAL uses the connected credential's verified actual My Drive root. Both use the same frontier and acquisition path. General does not enumerate Shared with me, Shared Drives or other accounts, and no account-wide Changes start token, replay or saved change cursor remains. Stable Drive IDs deduplicate discovered paths; provider version, scope revision and credential authority determine whether input can be reused. Membership eligibility is temporarily cleared during reconciliation. Acquisition reserves private input objects before PUT, verifies bytes/metadata/checksum, then atomically adopts the object, accepts the item version, schedules indexing and checkpoints the file under the current claim, generation, scope and usable credential authority. Failed adoption discards the stage; uncertain writes retain cleanup tombstones.

An incomplete generation records per-file FAILED or UNSUPPORTED outcomes and continues other files. Successfully adopted, confirmed current inputs are released for indexing, but unseen items are not pruned. Failed files remain discoverable on the next scoped reconciliation. General revalidates My Drive root identity before traversal and before pruning; root lookup, metadata or enumeration failure cannot complete an empty generation. Only complete traversal under current authority permits pruning, using ordinary REMOVE_ITEM cleanup rather than direct acquisition-time deletion. Specific link replacement fences the old generation and requires complete reconciliation of the new selection before pruning excluded content. General/Specific mode itself is fixed at Source creation.

Google publication additionally requires an active Tenant, non-deleting source/item, exact current input version, current scope revision, eligible non-excluded membership and usable matching credential authority revision. Reauthorization, disconnect, scope replacement or explicit removal cannot be undone by old work. Normal refresh-token rotation changes payload revision, not publication authority. In-flight indexing that loses only temporary membership eligibility rolls back publication and returns to NOT_STARTED if the exact current version, scope and usable authority still hold; it is not permanently superseded. `deferred_attempts` is excluded from the extraction retry budget (`processing_attempts - deferred_attempts`). Changed or revoked authority remains terminally stale.

The source-sync Redis stream/group are `memoryos:execution:source-sync:operations:v1` and `memoryos:execution:source-sync:workers:v1`, with a default batch size of 2, independently bounded from ingestion and cleanup (8 each). SOURCE_SYNC uses the same identifier-only delivery, lease, reclaim and rediscovery protocol.

Run acquisition remains independently terminal so scheduler progress does not wait for extraction. V28 attributes a new automatic index attempt to the exact sync run during input adoption, never by timestamps or the current item. A later run observing existing work records already-pending rather than owning its result. Durable per-file outcomes and child transitions settle unique counters once, including duplicate delivery, supersession and bulk cancellation; deferral does not settle a child. End-to-end completion waits only for that run's owned children. Cleanup cannot erase settled counters, and later manual reindex cannot rewrite closed history. The [Connector history contract](connector.md#synchronization-run-history) defines counter/error/read semantics and protected 90/14-day retention. The control plane invokes bounded history maintenance; metrics are not the history authority.

Pre-integration [isolated runtime acceptance](../tests/ingestion.md#mem-76-isolated-runtime--2026-09-08) exercised real PostgreSQL/Redis/MinIO/worker with owner Keycloak login and controlled Google OAuth/Drive/Docs HTTP fixtures: initial/no-change/changed input, provider and storage failure/recovery, linked approval and scheduled work, plus real FILE upload/reindex with null run attribution. These bounded observations are not live Google acceptance; the later final branch gate and controlled corpus measurement are recorded in the active increment. Verification after this main integration remains pending.

## Extraction routing and bounds

Extraction never opens a Google connection: native Sheets/Docs snapshots are acquired first and read offline from adopted object storage. The descriptor selects GOOGLE_SHEETS or GOOGLE_DOCS readers; BINARY content is detected and routed to Docling for PDF/DOCX/PPTX, Java spreadsheet readers for XLSX/CSV, or the bounded Tika child JVM for UTF-8 TXT/Markdown. Google Slides are exported as PPTX before the ordinary Docling route. There is no Docling-to-Tika fallback for structured office formats.

Sheets preserve all accepted tabs, sparse/default cells, zero/false values, inert formulas, merged ranges, coordinates and spreadsheet locale/timezone. Docs preserve ordered tab content, headings, lists, tables and nested cells, headers/footers/footnotes and source indices. XLSX preserves cached formula values without evaluating formulas or external links and rejects ZIP bombs and excessive sparse dimensions. CSV uses a real UTF-8/BOM-aware parser, retaining quoted newlines, escaped quotes and formula-like text as inert cell content.

XLSX ZIP admission reads central-directory members from bounded in-memory input, accepting streaming ZIP64 descriptors even when local-header sizes are zero. Actual expanded member sizes and CRC checksums must match the directory metadata. Entry-count, expansion-ratio, total expansion, secure XML and structural limits remain enforced before workbook extraction.

All BINARY input, including browser FILE uploads and acquired Slides exports, is capped at 10 MiB. Native snapshots are capped at 32 MiB, 200,000 represented cells and 100 tabs; Google acquisition permits at most 256 provider requests and 120 seconds, with lower configured bounds allowed. Offline structural readers also enforce cell/tab, 120-second processing, 100,000-block, 2,000,000-character normalized-text and 32 MiB canonical-artifact bounds. Missing snapshot windows, inconsistent provider versions and malformed or over-limit content fail explicitly; readers do not silently truncate to fit.

PDF admission checks encryption and page count without extracting content. Docling receives bounded bytes, never source credentials or fetch URLs, and produces JSON plus text with EasyOCR `vi,en`, accurate table extraction, and embedded images. Partial/empty results are rejected. Its defaults additionally bound PDF input to 200 pages, processing to five minutes, transport response to 64 MiB, canonical artifact to 32 MiB and text to 2,000,000 characters. HTTP cancellation is not a guarantee of remote process cancellation; late work cannot publish without current PostgreSQL authority.

### Docling deployment environment

Source and UserFile reuse one `DoclingProperties.options()` SDK model and the same canonical conversion. The disk-backed Chat multipart transport serializes those SDK options instead of maintaining a second list of fields. `memoryos.extraction.docling.api-key` supplies `X-Api-Key` on both JSON and multipart requests; the key is excluded from parser metadata and the configuration object's string representation. `ocr-engine` and `ocr-languages` are configurable, preserving the existing `EASYOCR` / `vi,en` defaults. A private Tesseract deployment can use `TESSERACT` / `vie,eng` with its injected secret. This binding does not update the OCR deployment or prove its ingress accepts 250 MiB. Diagnostic `maxInput` reflects Source's 10 MiB versus Chat's 250 MiB extractor ceiling.

Chat CSV/TSV and XLSX/XLSM now use `SpreadsheetSourceContentExtractor`, sharing Commons CSV and the existing POI canonical mapping with Source rather than a second, lossy SAX-to-text implementation. Large workbooks open `OPCPackage` from a temporary file in `READ` mode. The shared admission pass checks ZIP member CRC/size, duplicates, expansion ratio, XML entity/depth/node/text limits, cells and tabs before POI materializes workbook XML; embedded picture parts remain file-backed. Source retains its 10 MiB input / 64 MiB expanded ZIP limits; Chat permits at most 250 MiB input / 512 MiB expanded ZIP while retaining the same structural/text/artifact limits. These are bounded-input contracts, not an assertion that arbitrary 250 MiB cell-heavy workbooks fit the output budget. Formula expressions remain inert and cached values, dates, formatting, merges, visibility and sheet provenance retain the Source contract.

UserFile lease renewal follows Search's lost-claim pattern: a rejected renewal or database exception prevents artifact staging/publication at the next boundary. Staged but unadopted artifacts retain their existing cleanup owner. Source and UserFile authorization/publication contracts remain separate; neither is replaced by a generic ETL coordinator.

The Worker accepts a positive `memoryos.extraction.docling.timeout` up to fifteen minutes through Spring environment binding. Compose forwards `MEMORYOS_EXTRACTION_DOCLING_TIMEOUT` and reads every Docling service environment setting from the deployment environment or `--env-file`; [the environment example](../../infrastructure/deployment/staging.env.example) lists their unchanged defaults.

| Environment variable | Default | Fifteen-minute configuration |
| --- | --- | --- |
| `MEMORYOS_EXTRACTION_DOCLING_TIMEOUT` | `5m` | `15m` |
| `DOCLING_SERVE_MAX_DOCUMENT_TIMEOUT` | `300` seconds | `900` |
| `DOCLING_SERVE_MAX_SYNC_WAIT` | `310` seconds | `910` |

Configure both processes together: the Worker request budget must not exceed the Docling maximum, and the service synchronous wait must allow that processing budget plus response overhead. The SDK HTTP read timeout remains the Worker budget plus fifteen seconds (`915` seconds for `15m`); there is no separate HTTP-timeout env. A Worker-only increase against the old service maximum is rejected. Applying a deployment env file does not update already-running processes; recreate/restart the affected Worker and Docling runtimes in the deployment's coordinated rollout. The existing deployment script uses `--no-deps` for application rollout, so it does not recreate Docling automatically.

The exposed service settings also cover worker/thread counts, page/file limits, accepted source/target types, UI enablement and offline/model-cache options. Defaults remain private file-to-inbody conversion, disabled UI and offline models. Changing those options is an operator decision; changing timeouts alone does not alter EasyOCR `vi,en`, table extraction, Java admission limits or publication fencing. See the [change and verification record](../increments/active/docling-timeout-configuration/plan.md).

Diagnostic parser metadata includes parser identity/configuration and, for Docling, SDK, pinned service/model-image revision and options; it does not pin retry output. Document-owned artifact tracking, adoption and cleanup are defined in the [Document contract](document.md). db-scheduler runs artifact cleanup every minute independently of ingestion; artifacts referenced by current Documents remain protected.

## Cleanup

Cleanup is allowed after Tenant deactivation but cannot create content or access. For REMOVE_ITEM and DELETE_SOURCE, Ingestion renews the operation lease while asking Connector for adopted objects, idempotently marks each `DELETE_PENDING`, performs provider deletion, and only then asks Connector to remove provenance, attempts, upload associations, versions/items/Pair/Connector, stored-object metadata, and unreferenced Documents. Generic abandoned-upload cleanup is a separate object-storage task and never selects adopted objects.

Server-acquired input writes have a separate one-minute `ObjectWriteService.cleanup(16)` sweep. Reservation/adoption tombstones and current item-version references govern their cleanup; this does not replace browser abandoned-upload cleanup or permit deletion of adopted, still-referenced inputs. Extraction-artifact cleanup remains Document-owned and separate from both input-object lifecycles.

## Processing telemetry

The coordinator records `memoryos.operation.outcomes` for processing invocations independently of Redis acknowledgement. The bounded `workload` labels are INGESTION, CLEANUP, SEARCH, SOURCE_SYNC and GOOGLE_DRIVE_SELECTION_VALIDATION; `outcome` is COMPLETED, SKIPPED, FAILED or UNHANDLED. FAILED includes handled failures/retries; UNHANDLED means an exception escaped the coordinator. Duplicate/stale claims, deferred publication and continued/superseded sync or selection execution produce SKIPPED. These are invocation counts, not unique durable-operation or terminal-run counters. ACK failure cannot rewrite an already-recorded outcome.

`memoryos.operation.initial.queue.wait`, tagged only by workload, measures PostgreSQL `started_at - created_at` at the first successful claim (`processing_attempts = 1`). Both timestamps are database-authored. It includes initial dispatch delay and worker downtime, but excludes subsequent retry/backoff/reclaim waits, processing and ACK. A negative clock adjustment records zero. Rejected claims have no wait sample. First-claim samples can be lost on a crash after claim; no business decision depends on telemetry.

The timer's explicit histogram boundaries are 100 ms, 1/5/15/30 seconds, 1/5/15 minutes and 1 hour. They define diagnostic resolution, not an approved latency SLO. The staging OTLP path exports durations in milliseconds. Grafana shows outcome rates and initial-wait p95 separately from Redis transport processing time.
