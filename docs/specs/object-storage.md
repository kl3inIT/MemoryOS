# Object storage capability contract

Integration boundary: this contract combines the implemented Google branch with main IAM/Search. The [isolated integration plan](../increments/active/google-drive-structured-ingestion/plan.md#isolated-main-integration--2026-09-09) tracks pending combined verification; linked prior tests/runtime observations remain pre-integration evidence.

## Ownership and provider boundary

`objectstorage` owns tenant-scoped immutable raw-object metadata, generic browser-upload authorization, tracked server-write reservations, verification claims, adoption, discard, and pre-adoption cleanup. Its public `ObjectStorage` port provides provider-neutral presigned uploads, server writes, metadata inspection, streaming reads, deletion and bounded readiness checks; AWS SDK and MinIO types remain inside `objectstorage.s3`. `ObjectUploadService` owns browser intents, while `ObjectWriteService` owns server-acquired raw bytes. Connector owns accepted source provenance and post-adoption deletion. Extracted-artifact ownership is defined by [document](document.md), not a second raw-upload lifecycle.

`S3ObjectStorage` is the first provider adapter. It is configured with separate service and browser-upload endpoints, static service credentials, region, bucket, path-style behavior, bounded HTTP timeouts, and a bounded authorization lifetime. The browser endpoint requires HTTPS except for explicit loopback development/test addresses. The internal service endpoint may use plain HTTP only inside the private single-host Docker bridge; adding speculative MinIO PKI there would not protect browser traffic. MinIO is the verified S3 implementation, not a type in the capability contract.

## Object and upload lifecycle

Every initiated browser upload creates one `STAGED` `StoredObject` and one generic `ObjectUpload` before returning authorization. Object keys are server-generated and tenant-partitioned. The signed PUT binds the immutable key, media type, SHA-256 checksum, and declared `Content-Length`; the browser cannot choose a bucket or key. Browsers supply `Content-Length` automatically, so it is signed but omitted from the client-managed required-header map. Size is also verified from provider metadata during finalization. FILE browser admission is 1 byte–100 MiB (104,857,600 bytes); native snapshots retain their separate 32 MiB ceiling.

Upload states are `PENDING`, `VERIFYING`, `VERIFIED`, `ADOPTED`, `DISCARDED`, `CLEANING`, and `EXPIRED`. Verification uses a token and lease, performs provider inspection outside a database transaction, and compares the actual key-bound size, media type, and SHA-256 with durable declared metadata. Adoption or discard requires the current verification token and an unexpired adoption deadline. A completed adoption is capability-owned and never selected by generic abandoned-upload cleanup.

Expected missing or mismatched uploaded content returns `OBJECT_UPLOAD_INTEGRITY_MISMATCH`. Provider availability or authorization failures return `OBJECT_UPLOAD_STORAGE_UNAVAILABLE` at the upload application boundary. Wrong-tenant identifiers are indistinguishable from absent uploads. A finalized owning-capability endpoint persists its capability receipt, so replay after a lost response returns the same result without adopting twice.

## Tracked server-write lifecycle

Google acquisition stages raw binary bytes or native snapshots through `ObjectWriteService`, without a browser `ObjectUpload` or forged finalization receipt. Before any network PUT, a transaction persists a unique `raw/{tenantId}/{storedObjectId}` key, immutable metadata and an `object_writes` reservation with a write token/deadline. Writes and provider inspection occur outside database transactions. The service computes SHA-256 over the bounded bytes, writes them, and checks exact size, media type and checksum before making the reservation `READY` with an adoption deadline.

Raw write states are `WRITING`, `READY`, `ADOPTED`, `DISCARDED`, and `CLEANING`. Adoption requires an existing caller transaction, the matching tenant/token/full stored reference, positive write completion, and an unexpired adoption deadline. Source-item acceptance adopts the object and records its version atomically, so rollback cannot leave an accepted raw object detached from that transaction. An obsolete or failed acceptance discards its unadopted stage; it cannot revive an expired or cleaning claim.

BINARY object admission is 1 byte–100 MiB (104,857,600 bytes), shared by FILE upload and Google binary acquisition; native snapshots remain capped at 32 MiB. Durable input-kind constraints enforce the separate bounds, and native snapshots cannot be authorized as browser uploads. Provider request, cell/tab/time bounds and extraction routing remain in [ingestion](ingestion.md).

## Cleanup and readiness

The generic browser-upload reaper claims only expired pre-adoption uploads and discarded duplicate objects. `CLEANING` plus a token and lease fences cleanup from verification/adoption. Provider deletion precedes token-guarded metadata removal and is idempotent; a row failure remains recoverable after its lease without aborting later claimed rows.

Tracked server writes have a separate worker control-plane sweep: `ObjectWriteService.cleanup(16)` runs on a one-minute fixed delay. It claims expired writing/ready reservations, discarded stages and expired cleanup leases, excluding every object still referenced by a ConnectorItem version, including an unexpected pre-adoption reference. A failed deletion leaves a retryable leased claim and does not abort other rows.

A timed-out PUT is not proof that the remote write stopped. Cleanup retains the key and reservation as a durable tombstone when positive completion was unknown at claim time, deletes again after the one-day retry delay, and does not age out that uncertainty. A writer completing during deletion cannot revive the claim or make that sweep forget a possibly later write; a subsequent sweep observes completion before deleting and releasing metadata. Thus even an arbitrarily delayed PUT remains tracked.

After adoption, the owning capability controls deletion; generic reapers never select adopted objects. Connector invalidates provenance, marks the `StoredObject` `DELETE_PENDING`, deletes provider bytes, and then removes source-upload associations and versions/items before releasing tracked-write ownership and object metadata in a claim-fenced transaction. `releaseAdopted` requires the caller transaction and rejects release while any item version still references the object; release is idempotent once ownership is absent. Retried provider deletion and `DELETE_PENDING` marking are idempotent. These rules apply to FILE uploads and Google-acquired objects; [connector](connector.md) defines their source lifecycle.

Deployment bootstrap owns bucket creation, private access, the readiness sentinel, CORS, service users, and least-privilege policies. API credentials may sign PUT and inspect `raw/*`; worker credentials may write, inspect, stream and delete `raw/*` for provider acquisition/indexing/cleanup and `extracted/*` for document artifacts. Both identities may read only the configured sentinel outside those data prefixes, and neither can list the bucket. API and worker readiness open a one-byte range from the sentinel and never mutate or list at startup.

## Staging inspection

Staging exposes MinIO's native Console on a dedicated HTTPS origin without publishing container port `9001`. A dedicated confidential Keycloak client uses Authorization Code and an exact `/oauth_callback`. The pinned Console does not emit a PKCE challenge, so this exact client does not require PKCE; its client secret, exact callback, OIDC state validation, and claim boundary remain mandatory. Its realm-role mapper emits only the client-scoped `memoryos-inspector` role into the MinIO `policy` claim; the realm assigns that role only to the reconciled initial owner. MinIO uses claim-based authorization rather than a provider-wide role policy so an ordinary realm user cannot gain storage authority through the public STS endpoint.

Deployment bootstrap reconciles the matching `memoryos-inspector` MinIO policy. It may list buckets, inspect the configured bucket, and read its objects, but grants no upload, delete, bucket mutation, IAM, policy, or server-administration action. It explicitly denies create/list/update/remove service-account actions because self-service access-key creation is otherwise available to authenticated MinIO identities without an allow. The human receives expiring OIDC-derived STS credentials, never the root, API, or worker secret. Production has no Console route, OIDC client-secret mount, or MinIO OIDC configuration.
