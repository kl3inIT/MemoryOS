# Chat session contract

## Answer toolbar and editing

The Chat header offers an assistant-ui ConversationSearch finder over text parts of the current loaded branch, with literal case-insensitive matching, next/previous navigation and a 500-match display bound. It does not search other sessions or hidden tool payloads. Loaded sidebar history is grouped by local-calendar Today/Yesterday/Earlier using session updatedAt, without client-side title filtering; existing routes, pagination and real session actions remain authoritative.

`GET /api/chat/sessions/search` (`searchChatSessions`) searches the caller's own non-deleted sessions in the active Tenant across titles and every persisted USER/ASSISTANT text version, including unselected branches. It accepts `query` (0–200 characters, no NUL), `offset` (0–10000) and `limit` (1–50, default 20), returns `{items: [{session, snippet}], hasMore}` ordered by `updatedAt DESC, id`, and a blank query returns recent owned sessions. `snippet` is a PostgreSQL `ts_headline` fragment (one fragment, 10–24 words) of the newest indexed matching message, computed for the returned page only, with matched tokens wrapped in U+E000/U+E001 private-use delimiters that the browser renders as text highlights (never HTML); it is null for a blank query, title-only matches and messages above the 64 KiB index bound. Matching uses PostgreSQL `simple` full-text tokens (all query tokens, no English stemming) through V50 GIN expression indexes; message bodies above 64 KiB are excluded from the index so large answers never fail `tsvector` limits, and remain matchable by the same tokenizer at read time. Membership is resolved per request inside a read-only 10-second transaction; inactive membership is forbidden. File bodies, tool payloads and other users' shared conversations are not searched. Pagination is live, not a snapshot. A search icon beside the sidebar collapse button (beside Close in the mobile drawer; an icon row in the collapsed rail) or Ctrl/Cmd+K opens a cmdk command palette (ChatGPT search layout, owner-approved 2026-09-14): a blank query shows New chat and recent conversations grouped Today/Yesterday/Earlier; a query shows matches grouped the same way with title, matched fragment and time. It keeps 250 ms debounce, cancelable paged queries, localized loading/empty/error/retry states and no local filtering of server hits. Opening a hit navigates to the session and keeps its currently selected branch.

The composer toolbar has one `+` menu on the left and the model picker beside Send on the right. The `+` menu offers Upload file (native attachment adapter, disabled at 20 files), Choose existing file (compact recent files and the full recent-file dialog) and Web search; Web is the only implemented tool. Its row toggles Web for the turn (enabling it selects automatic; an active Web turns off) and its options view keeps the Off/Auto choices, capability checks and model-manager settings link. While Web is on, a Web chip with a dismiss button sits beside `+`. No OpenURL, native hosted-search or future tool is advertised independently. Recent files show status as a labelled leading icon: a spinner while processing or unconfirmed, a warning on failure and a muted mark when not yet searchable; ready files show the plain file icon. The full recent-file dialog repeats failures as text beside Retry. Settings separates search engines from page readers with provider marks and a built-in MemoryOS reader; Exa/Tavily retain one credential record. Completed Web result lists are collapsible. The source panel uses assistant-ui DocumentReference with real citation IDs/excerpts rather than fabricated page counts, preserving authorized reader navigation.

Sources remains one grouped control in the answer action row, following the inspected Onyx toolbar. It shows the localized Sources label and up to three distinct source icons (Web hostnames or document type); its accessible name retains the citation count. Clicking toggles the selected message's existing responsive source panel. It does not introduce a separate row of source-title chips or change authorized document/inline citation navigation. The assistant-ui-derived favicon component sends only Web hostnames to the upstream favicon service, without referrers or cross-origin credentials, and falls back on failure; internal document metadata stays local.

Question editing uses the controlled server-backed edit flow with a library-autosizing input (one to eight rows), no manual resize handle, and a single attachment/Cancel/Save footer. Escape cancels and Ctrl/Cmd+Enter saves outside IME composition; pending/busy and attachment-only admission remain enforced. Document Search is its own sidebar entry (Search documents) and the header Chat/Search mode selector was removed (owner-approved 2026-09-14, superseding the earlier mode-selector decision); this is distinct from searching conversation history.

## External Web search and URL reading

`web_search` accepts a `queries` array (1–8); `open_url` accepts a `urls` array (1–5). Java methods are `webSearch` and `openUrl`, with stable external names declared in tool annotations. Duplicate inputs are suppressed per turn. Batches reuse `SearchTasks`' bounded parallelism and cancellation; ordinary per-request failures retain successful results in input order without exposing raw provider errors. A whole-batch deadline failure is not partial-result recovery.

Send/Edit/Regenerate accept `deepResearch` (absent means false). V66 persists it in command identity, so a replay with a different mode conflicts. `GET /api/chat/settings` lets members read Tenant Chat settings; `PUT` with `MODELS_MANAGE` and the current `revision` changes them (a stale revision conflicts). `deepResearchEnabled` is true while no settings row exists, as Onyx treats an unset value. While it is false, a research command is rejected with `CHAT_RESEARCH_UNAVAILABLE` before reservation; Onyx only hides its button. Send/Edit/Regenerate accept `webSearch: off | auto` (absent means off). V49 persists this in command identity, narrowed to those two values by V61; replay with different Web intent conflicts. Internal `searchEnabled` is unchanged. Admission resolves one tenant-owned search/content configuration snapshot, then the existing Embabel runner executes `web_search` and `open_url` within the current turn, Stop/task scope, deadline and context budget. Naming does not receive Web tools.

Model managers configure connections at `/settings/web` using the existing encrypted provider-credential mechanism. Brave, Tavily, Exa, Serper, Google PSE and SearXNG implement external search; Tavily, Exa and Firecrawl implement content extraction. Exa/Tavily share one connection across the two functions. Saving a key does not enable a provider or send a paid probe; testing and selecting are explicit. Members can read availability, not connection secrets. Availability lists authorized tool-capable model IDs and the subset whose adapter supports required named tool choice. This is not native provider-hosted search. Unsupported required mode fails before a turn is reserved; a provider ignoring the forced tool is a failed response, not a successful searched answer.

Web search is offered, never forced. Enabling Web means the turn carries `web_search`/`open_url` and the model decides, matching every provider whose hosted search is model-arbitrated once attached: OpenAI states the model "can choose to search the web or not based on the content of the input prompt", Anthropic lists conversational turns and greetings among the requests Claude answers directly, and Google's grounding analyses the prompt and searches only if needed. A turn that answers without searching is a complete answer, so no failure code exists for it and the composer has no forcing control.

A Web turn that cannot search reports `CHAT_WEB_UNAVAILABLE`, distinct from the model provider's own `CHAT_PROVIDER_UNAVAILABLE`: either the selected model declares no tool calling or the Tenant has no active usable search connection. Both rejections log the discriminating condition without the credential, endpoint or query text.

A search gateway is one connection that routes to an engine it selects per request. 9Router is such a gateway: `POST {endpoint}/search` carries `{model, query, max_results}` where `model` is the configured engine identity (`tavily`, `brave-search`, `searxng`, …), the reply maps `results[].url/title/snippet` with `content` as the snippet fallback, and a copied endpoint already ending in `/search` is normalized rather than doubled. `POST /api/chat/web/connections/NINEROUTER/engines` (model managers) lists the gateway's search engines from `GET {endpoint}/models/web`, skipping fetch-only `webFetch` entries, with the key typed in the form or, when it is blank, the saved key for the same endpoint (Onyx `api_key_changed`); the form offers them as suggestions and keeps free text. Connection-test success in the Web, image, voice and provider dialogs uses the shared `Alert` `success` variant. It requires both its own endpoint and an engine identity, takes a credential, and does not accept the `site:` operator because engine support varies. Its engines live in the gateway, so an engine without credentials there stays unavailable no matter what the connection says.

The built-in reader accepts public HTML/XHTML/plain text and text-based PDFs. PDFBox extracts at most the first 50 pages and 16,000 characters plus a truncation marker, with cancellation checks and no OCR; textless/restricted/malformed PDFs fail rather than becoming evidence. Apache HttpClient pins validated DNS answers, validates redirect destinations, does not forward user credentials/cookies and bounds redirects, bytes (20 MiB) and timeouts. Administrator-configured SearXNG retains the accepted trusted internal-endpoint policy. There is no headless browser, arbitrary HTML execution or OCR invocation. OpenAI provider-hosted search is available only for a model configuration declaring `options.webSearch = "native"` (tool-capable). Its Web turns use the Responses API with the hosted `web_search` tool plus the turn's function tools; helpers keep Chat Completions, and so do turns without Web on an OpenAI-compatible endpoint; a model served by `api.openai.com` streams every turn through the Responses API ([model catalog](chat-models.md#credentials-and-provider-extension)). Requests use `store=false`; reasoning (`include=reasoning.encrypted_content` for reasoning models), hosted search and function-call output items are echoed to the next tool cycle through assistant message properties, and are not persisted across turns. Hosted `web_search_call` items emit STARTED/SEARCHING/COMPLETED events; `url_citation` annotations register `web:` sources in the Sources panel without inline `[n]` markers. Native turns register no external `web_search`/`open_url` tools and need no external connection. Required mode sends `tool_choice: web_search` on the first request and fails an answer that did not search. The final cycle omits hosted search with the other tools. Search calls are counted in `memoryos.chat.native_web_search.calls`; cost remains unknown. Gemini/Anthropic native search remain open.

Web evidence shares the existing 24-source citation namespace and sources JSONB. A source has `web: {url, excerpt, retrievedAt}` and null Document/file identity; it is not an indexed internal Document. The current source panel shows the bounded excerpt and original-page link, with a mobile dialog. Repeated URLs retain the first registered citation/excerpt for that answer. Historical source links do not trigger an automatic page fetch.

The composer reuses its installed Popover/Command controls on the attachment/model action row. The assistant-ui Web Search element renders actual query/progress/results inside the Web tool step of the activity timeline; existing InlineCitation, Sources and reader-panel selection remain the navigation path. Labels are vi/en. Web intent stays in the active transport and each persisted command. Browser-local actor/session preference restores the control after reload, defaults new chats to off, and fails safely if storage is unavailable; it does not grant authority or synchronize between devices. Request timers use bounded provider/operation/outcome dimensions; call counts are not a billing or native-token usage estimate. Provider-specific `site:` guidance is included only when search is callable: Exa is instructed not to use the operator. See [increment verification](../increments/active/chat-web-search/verification.md).

## MCP tools

An MCP server is a Tenant-registered remote endpoint that supplies tools to a turn. Administration needs `MCP_MANAGE`; using a server needs `CHAT_WRITE` plus either the server's organization-wide flag or membership of a Group it grants. A server outside that set is reported as not found rather than listed, so restricted servers are not enumerable. Each server carries an immutable slug of 1-16 characters `[a-z0-9]`, because the model-facing name is `mcp_<slug>_<tool>` and must satisfy `[A-Za-z0-9_.-]{1,64}`; a tool whose composed name does not fit is stored, shown and never offered. Changing a server's URL, authentication type or performer deletes its stored credentials so they never reach another endpoint or scheme, and a URL change also drops the tool snapshot.

Authentication is `NONE`, `API_TOKEN` or `OAUTH`, performed once for the Tenant (`ADMIN`) or by each person (`PER_USER`). Header templates accept the single `{api_key}` substitution, only on API-token servers, and OAuth servers may not template `Authorization`. Secrets are sealed with `MEMORYOS_MCP_CREDENTIAL_ENCRYPTION_KEY`, bound to Tenant, record and purpose. A User's own API key is listed against the server before it is stored; a rejected key is reported as `MCP_AUTHORIZATION_REQUIRED` and nothing is written.

OAuth follows MCP `2025-11-25` authorization with the `2026-07-28` `iss` rule. A server may hold several labelled OAuth clients, because a Google `Internal` application authorizes only its own Workspace; the person chooses one by label when connecting. Discovery is an explicit administrator action that persists nothing until a client is created, and runtime uses only persisted endpoints. Authorization carries PKCE `S256`, the RFC 8707 `resource` and the administrator's configured scopes; the callback is bound to the browser session, consumed once, checked against the actor, and rejected when the server or client revision changed while it was pending. Tokens refresh 60 seconds before expiry outside any transaction, fenced by credential revision, and a refresh that loses a concurrent race adopts the winner's token. `invalid_grant` marks the credential `REAUTH_REQUIRED`; for the shared credential the server also returns to `AWAITING_AUTH`. Disconnecting revokes at the authorization server on a best-effort basis.

Send, Edit and Regenerate accept `mcpServerIds` (at most 8). Access, credentials and OAuth refresh are settled before the model runs, so a turn never blocks on an authorization server mid-call, and the turn owns one session per server which is closed when it ends, including on Stop. Each enabled tool becomes one Embabel tool carrying the snapshotted JSON Schema. A per-call timeout bounds the work and, as Onyx, the cycle limit bounds the number of calls; `mcp-call-limit` is an optional per-turn cap (a turn has no total deadline), and one result is capped against the remaining context. Selected servers that are unusable contribute no tools; the model is told to ask the person to connect them. A Deep research turn runs its own agents and tool set and ignores `mcpServerIds`.

The timeline names each MCP step by tool and server. A failed step carries `failure` on the stream and in history when the person can act on it: `AUTHORIZATION_REQUIRED` (the server rejected the credential), `TIMEOUT` or `UNAVAILABLE`; the value is a category and never upstream text. For a per-User server, an `AUTHORIZATION_REQUIRED` step offers Connect in place and keeps its step group open after the answer; a shared connection points to an administrator instead.

Results are untrusted third-party data: they are labelled as such to the model and never merged with MemoryOS instructions. A failure is reported to the model by category alone — rejected credential, timeout, unreachable server, unusable arguments — derived from the MCP capability's own error codes rather than from matching text, and no upstream body, endpoint or status code reaches the model, the answer or the logs. This is a deliberate departure from the reference implementation, which appends the original exception text to the model-facing message. Calls are timed in `memoryos.chat.mcp.call` with the server slug, tool name and outcome; the free-form server name is never a label.

## Message renderers and read-only presentations

Complete code fences lazily use Shiki's JavaScript regex engine; streaming/fences above 100,000 characters retain plain code. Complete Mermaid uses `beautiful-mermaid`, bounded to 20,000 characters/250 lines and displayed as inert SVG image data. Unsupported diagrams retain source. Radix Dialog owns expansion, zoom, Escape and focus. Raw HTML is not executed; CSP is unchanged.

The `render_gui` tool was removed on 2026-09-19: Onyx has no equivalent, markdown tables, `run_python` files and captured charts cover its cases, and staging used it in 2 of 193 answers. Answers stored with its read-only cards still render them from history. V42 added `chat_message.artifacts` (JSONB array, at most three, 128 KiB database cap). Each has UUID, title (120 characters) and validated JSON spec (16 KiB UTF-8, 80 nodes, depth eight, 24 children/node, 2,048 characters/property). The closed vocabulary is Card, Heading, Text, Metric, Table, Row and Cell with display-only string props. No HTML/JS, forms, URLs, event handlers or application actions.

Artifacts freeze and commit with the same terminal winner as answer content/sources. Authorized owner/shared history returns them. SSE outcome carries `hasArtifacts`, not the large specs; one authorized history read loads the committed answer. Replay gaps/reloads restore artifacts without another inference. Previous artifact data enters the normal bounded follow-up context as data, never system instructions, with the answer's sharing/retention semantics.

Answer cards open the existing right panel/mobile dialog, using assistant-ui `GenerativeUIRender` and allowlisted app components. The native runtime owns content; only panel selection is local. Unsupported historical specs show a localized fallback without removing the answer. Model numbers are not verified computations; factual citations remain in the accompanying answer. See [localization](localization.md).

## Account reply language

Turn admission captures IAM's account `uiLanguage` in its resolved context. Native prompt assembly uses one language hint: `vi` prefers Vietnamese while allowing explicit requests for another language; `en`, absent or unknown values follow the language of the user's question. English does not force English replies. Default prompts with appended Persona/Project instructions replace the default language line rather than adding conflicting language blocks. Custom instructions remain intact after the account preference. Locale changes do not alter an admitted running turn, stored conversation content, retrieval queries or evidence.

`ChatLanguagePromptTest` verifies prompt composition, fallback and instruction preservation. `ChatPersistenceIntegrationTest.accountLanguageIsCapturedAtAdmissionAndChangesOnlyForTheNextTurn` verifies the real persisted preference snapshot across turns. These are request-contract checks, not live-model language-quality acceptance.

## Personal chat preferences

Each Tenant membership has one `chat_preferences` row (V86, deleted with the membership): work role (200 characters), personal preferences (2000), a personal default model, a starting creativity (0–2) and reasoning level (`OFF`, `LOW`, `MEDIUM`, `HIGH`), and auto-scroll (V88 for the two starting values). A missing row reads as the defaults (empty text, no default model, auto-scroll on). Chat is always the entry point; the start page choice V86 carried was withdrawn in V87. `PUT` saves the whole value and rejects a default model outside the caller's available models. The personal default model takes part in [model resolution](chat-models.md) after the Persona default.

As Onyx `prompts/user_info.py`, native prompt assembly appends a `# User Information` section after the Persona or Project instructions, with `## Basic Information` (name and email from the IAM profile, work role) and `## User Preferences`; empty values are omitted and the section is absent when nothing is known. It is read at admission, so an edit applies to the next turn.

Auto-scroll controls the assistant-ui viewport while a reply streams.

One turn's creativity and reasoning level settle in Onyx's order (`resolve_reasoning_effort`, `llm/factory.py`): the level pinned on the conversation (V88 `chat_session.reasoning_effort`), then the model configuration, then the member's own defaults, then the provider's default. The settled values ride on the options converter, which runs per inference, so a cached client binding still serves every member and a helper call (conversation naming, selection) keeps the low effort its configuration gives it. A model whose `capabilities.reasoning` is false receives no level and shows no control; a reasoning model receives no sampling creativity, the pairing the model editor already enforces. Levels are Off, Low, Medium and High: Onyx's `xhigh` is left out until levels are filtered per provider, because only OpenAI and Anthropic adaptive models tell it apart. The composer's model picker pins the conversation's level; Settings › Chat holds the two starting values. The Settings area (`/settings/general`, `/chat`, `/connections`, `/usage`) holds these preferences with the profile, theme, language, voice, prompt shortcuts, per-user MCP connections, the member's own [AI usage](ai-usage.md#http) and Delete all chats. Settings rows follow Onyx: the explanation is inline under the label, and a tooltip is reserved for why a control is unavailable and for icon-only buttons. The default model uses the composer's own picker, with vendor marks and one group per provider; Usage lists model prices as one collapsible group per provider, each model on one `input · output · cache` line, and marks each model's spend with a bar proportional to the period's priciest model, as Onyx does instead of a chart.

## Chat file backend

Chat message files and answer citations share the existing responsive reader workspace: one right-hand panel on desktop, a focus-contained Radix modal drawer on mobile. File triggers keep the originating focus target; closing preserves the composer draft and native Chat runtime. The readers retain current authority checks and zero-retention private query behavior. Shared transcript file descriptors remain non-opening. Composer attachments use bounded horizontal cards with a truncated name/full tooltip, known size and adjacent remove action; native upload/readiness and the upstream preview store remain authoritative. This does not introduce generated HTML artifacts, code execution, artifact editing or version history.

The implemented attachment flow adds owner-private UserFiles independently of conversations. `/api/chat/files` provides policy, idempotent upload initiation (`requestId` plus filename/type/size/SHA-256), finalize, recent-list/status, processing retry and deletion. API selects the `CHAT_FILE` storage purpose; browser input cannot select it. Finalize verifies storage outside the ownership transaction, then rechecks active membership/owner and atomically adopts the upload and queues PostgreSQL work. Replaying a completed finalize does not enqueue again. List/get do not return raw keys or plaintext. Stable extraction failure codes accompany failed metadata.

The browser repeats initiate/finalize once on a fetch network TypeError with the same request/file identity, without repeating PUT. It does not retry HTTP authorization/validation failures or canceled requests. Existing recent-file/finalize/expiry paths remain the recovery surface after reload; this is not resumable chunked upload or persistent browser drafts.

Worker publication saves the normalized plaintext and a private Document reference together, fencing stale work with a claim token/lease. `READY` here means content publication, not search readiness. Delete makes the file unavailable first; separate durable cleanup removes raw bytes and the Document projection/artifact. A historical upload receipt survives cleanup. Source Document cleanup respects live UserFile references.

Messages carry ordered descriptors in one `files JSONB` column; command replay compares the ordered file IDs. The frontend sends server file identities, not binary data, through the native assistant-ui attachment adapter. The composer has one action row: paperclip, model selection and Send/Stop. The paperclip opens a Radix popover with upload and three recent files; the full picker/recovery actions open in a separate dialog. Message editing reuses this compact picker. Project files live in the workspace Files section, separate from the name/instructions editor; removing a Project association does not delete the file. Custom Personas reuse the picker, and their file list overrides the Project list, including when empty. The picker preserves unavailable selected identities until the owner explicitly removes them, and file deletion uses the existing confirmation dialog.

The native composer is wrapped only for the application readiness rule: Gửi and Enter are blocked while any attachment is running/incomplete, lacks a server file identity, or the draft exceeds 20 files. Text remains editable. Adapter `send` also validates the ready identity; this does not replace backend admission checks. The library's default send gating alone does not enforce worker readiness.

Owner-private `GET /api/chat/files/{fileId}/text` reads at most 16,000 Unicode code points from cached extraction; zero-based `offset` and returned `nextOffset` use PostgreSQL character semantics, not UTF-16 offsets. `GET /api/chat/files/{fileId}/content` streams the original adopted object with attachment disposition, `application/octet-stream`, `nosniff` and `Cache-Control: no-store`. Both require current owner/Tenant authority and READY content; raw download rechecks ownership, membership and object metadata after opening storage and closes rejected streams. Raw keys and signed download URLs are not persisted in message descriptors.

The history reader renders text as inert text, follows the returned cursor and offers an authenticated original download. PNG/JPEG/WebP preview fetches owner-authorized bytes on opening, uses the existing assistant-ui object-URL lifecycle hook, and releases the URL on closing. Reader queries have no inactive cache retention. Shared transcripts render descriptors without private reader/download actions. This UI does not grant file authority through transcript sharing. The AI SDK converter places sent user files in `message.attachments`; `MessagePrimitive.Attachments` renders them and editing retains file/image identities from that collection, not only message parts.

Vision turns load owner-authorized original bytes inside the cancellable file-work scope and pass native ImagePart messages to the SDK. The local OpenAI HTTP test verifies the exact data URL, not only an intermediate Prompt. Non-vision turns preserve text markers for history/workspace images without reading bytes or charging image tokens. Image admission uses a 4096-token heuristic per image; this is not exact provider tokenization or a billed usage value. Native response usage remains authoritative. No provider-specific cap is invented for the current OpenAI adapter.

File context/tools share a bounded citation namespace with Source search. API history preserves nullable `fileId` versus Source `documentId`/`generation`. Optional `fileLocation` records either a Unicode character `offset`/`count` from `read_file`, or an indexed `generation`/`ordinal` from `search_files`. Character citations open and highlight that cached-text window. Indexed citations reuse the Search document reader through owner-private `GET /api/chat/files/{fileId}/passages?generation=…&from=…`; the server resolves the private Document, rechecks current generation and owner/Tenant authority after IO, and returns at most 20 passages. Distinct locations receive distinct citation IDs. Whole-file context and historical citations without a location remain explicitly whole-file; there is no invented PDF page or exact-passage guarantee for those citations. When private search dependencies fail, `search_files` advises `read_file` for cached text; authorization and cancellation exceptions are not swallowed. Control-plane expiry turns abandoned uploads into `FAILED/UPLOAD_EXPIRED`; they require a new upload. Expired worker claims can be reclaimed while late publishers remain fenced.

MEM-81 is implemented and its delivery record is complete. Two real-model vision cases and isolated large-XLSX parser resource measurements passed on 2026-09-12; exact boundaries are in the [completed increment](../increments/completed/chat-attachments-production/verification.md#live-vision-và-đo-tài-nguyên--2026-09-12). Those checks do not certify a production rollout or full worker/API resource sizing. OCR remains separately bounded; local XLSX 100/250 MiB tests do not prove OCR acceptance at the same sizes. The existing Source-backed Chat contracts below remain unchanged.

## File library

`/library`, reached from the Chat sidebar beside Search documents and Assistants, is the owner's own view of every file Chat holds for them ([MEM-142](../increments/completed/mem-142-file-library/design.md)). `GET /api/chat/library` unions the three places those files live — uploads (`chat_user_file`), files `run_python` generated (`chat_file_artifact`) and generated images (`chat_image_artifact`) — into one paginated list. It accepts a name `query` (at most 200 characters; an image also matches its revised prompt), `sources`, `categories`, `sort` (`NEWEST`, `OLDEST`, `LARGEST`, `SMALLEST`), `offset` (0–10000) and `limit` (1–100, default 50), and returns `{items, totalCount, totalBytes, hasMore}` where the totals cover the whole filter, not the page. A category (`DOCUMENT`, `SPREADSHEET`, `IMAGE`, `PRESENTATION`, `OTHER`) is derived from the stored media type and name, never stored. The list is owner-private and Tenant-scoped: it never shows another member's file, never shows a file of a soft-deleted conversation, and lists only a READY upload, because the library's preview and download routes serve no other status.

An artifact carries its owner and conversation (V90 `owner_actor_id`, `session_id`, backfilled from the answer and written on insert), so a page reads them without joining and a caller cannot record a foreign owner. A generated image is also named and measured for the first time (V90 `filename`, `size_bytes`): `image-<yyyyMMdd>-<HHmmss>-<8 hex>.<ext>` from its creation time and media type. An upload has no conversation — it may be used by several, by a Project or Agent, or by none — so the library offers it no "open the conversation" action; artifacts have one.

`DELETE /api/chat/file-artifacts/{id}` and `DELETE /api/chat/image-artifacts/{id}` delete an artifact the caller owns. Deletion is idempotent: deleting one already deleted, or one the cleanup sweep has already removed, answers 204, because an absent artifact is the outcome the caller asked for; an artifact another member owns answers 404, as the upload route does. The request only sets `deleted_at`, which hides the file from the library, from the serving and chart routes, from the pptx preview and from the turn context that lets `edit_image` reuse an earlier image. Conversation history is the single exception: it still returns the row with `deleted: true` and no size, so the answer keeps a card reading "file deleted" instead of losing it, and the `file_link` in the answer body answers 404 as any unavailable artifact does. Because shared transcripts carry no image or generated-file references, a deleted file is gone from a shared conversation as well. An upload keeps its existing lifecycle at `DELETE /api/chat/files/{id}`, and a Project or Agent holding it refuses the deletion with `409 CHAT_FILE_IN_USE` and a `usedBy` list naming them — Onyx answers the same case with 200 and `has_associations`, while MemoryOS reports a refused command with a status. The library labels such a file and disables its delete action. There is no bulk delete endpoint: the page deletes a selection one request at a time and reports each outcome, because a partly refused selection is the normal case.

Artifact bytes are adopted object writes, which the generic reapers never select ([object storage](object-storage.md)), so the owning capability releases them. A `memoryos-chat-artifact-cleanup-v1` recurring task (one-minute fixed delay) claims deleted artifacts with `FOR UPDATE SKIP LOCKED` and a two-minute lease, marks the artifact object and its V73 preview object delete-pending, deletes both keys outside any transaction, then releases ownership and the metadata and turns the row into a tombstone (`purged_at`, storage columns emptied) in one claim-fenced transaction, so the answer that generated it keeps saying the image or file was deleted while the library, the trash and restore all leave tombstones out; a failure leaves the claim to lapse and the artifact to be swept again. A pptx conversion that finishes after the deletion records nothing and discards the object it staged, so a race leaks no bytes. Deleting a conversation withdraws its files from the library; whether the conversation itself is ever removed is the retention switch below. A conversation's own files are reachable from its header, through the same listing.

A generated file or image is reused by copying it, not by reference ([MEM-152](../increments/completed/mem-152-file-library-v2/design.md)). `POST /api/chat/library/{source}/{id}/copy` (`source` `GENERATED` or `IMAGE`) copies the artifact's bytes on the server into a new file of the caller through the server-write lifecycle (`ObjectWriteService`: staged outside any transaction, adopted in the transaction that records the file under the owner lock, discarded on every other outcome), then hands it to the file worker like any upload, so it is `PROCESSING` until extracted and then usable wherever an upload is: a message, a Project, an assistant, `edit_image` and file search. Only an artifact the library lists can be copied; another member's or a deleted one answers 404, and `UPLOAD` is rejected because an upload needs no copy. V92 records `copied_from_source`/`copied_from_id` with a unique index over the owner's live copies, so asking again — a double click, a retry, a second tab — returns the same file, and a concurrent loser discards its own staged object. `chat_user_file.stored_object_id` (V125) names the object every file is, and `upload_id` only the browser upload a file came from: a copy has none, so deleting it makes the file work release the adopted write itself (delete-pending, delete the key, `releaseAdopted`, remove the metadata), while a browser upload is still retired through its upload. Meeting minutes taken into the library follow the same path. The copy owns its bytes: deleting or purging the artifact leaves it intact, and deleting the copy lets the artifact be copied again. Every library row also carries `messageId`: the answer that produced an artifact and, when the list is narrowed to one conversation, the first message there that attached an upload.

The composer's "choose an existing file" offers the three most recent uploads and opens the library itself: a dialog with name search, source tabs, category chips and multi-select up to the draft's remaining room, where the list is the only thing that scrolls and a narrowing filter keeps the rows being read on screen, dimmed and `aria-busy`, until the next ones arrive. *Attach* hands the choice to the composer and closes: each generated file is copied there as a tile of its own with a spinner among the draft's other files, a failed copy stays as a tile its owner takes off, and only a ready copy becomes an attachment, so Send's readiness rule never sees a half-prepared file. Files still being prepared hold their place against the twenty a message may carry, and the composer keeps its tiles to two rows with the rest behind a "+N" card that still removes them. The conversation panel counts the conversation's files on its header button, refreshes when a turn finishes, searches and filters within the conversation, and gives each row *attach to the next question*, *show in conversation* — which switches message versions from the top down when the message is on another branch, then scrolls to and highlights it — *add to project*, download and delete.

A file can also be taken in, renamed, starred and found by its contents (MEM-152 phase 2). `/library` uploads through the composer's own `/api/chat/files` pipeline — an *Upload* button, a whole-page drop target and a tray with per-file progress and cancellation — so a file taken in there is an ordinary upload that belongs to no conversation. `status=PENDING` on the listing shows the owner's uploads that are `UPLOADING`, `PROCESSING` or `FAILED` (never an artifact) with `status` and `errorCode` on the row, offering *Retry* and *Remove*; `READY` stays the default. `PATCH /api/chat/library/{source}/{id}` takes `{filename?, favorite?}`: a rename rewrites the file's own `filename`, so the listing, the name search, the conversation cards and the download follow at once while the stored object, its key and its bytes stay as they are, and a message keeps the name it was sent with; the new name is trimmed, carries no control character or slash, and keeps the file's extension, appended when omitted. Starring writes V93 `favorite_at`, which `favorite=true` filters by, and `sort=NAME` is available beside the four existing sorts. `GET /api/chat/library/search?query=…` finds files by what they contain: it runs the same owner-private file search as the `search_files` tool over the caller's most recent 4000 `READY` uploads that have an indexed document, and answers each file as a library row with up to three matching passages — never a Source document, never another member's file and never a generated file, which is not indexed.

The file the preview is showing also carries three actions of its own ([file detail actions](../increments/active/library-file-detail-actions/design.md)). A question typed under the preview copies the file into an upload, creates a conversation titled after the question and opens `/chat/{id}?ask=…&attach={fileId}`; Chat attaches the file before it sends the question, and a file that never becomes usable leaves the question in the composer rather than asking about nothing. An empty question opens that conversation with the file attached and sends nothing. An image can be cut: crop mode shows it upright at 100 %, a dragged rectangle is reported in the image's own pixels, and the browser encodes the selection — PNG unless the source was JPEG or WebP — either straight to a download or into `<name> (đã cắt).<ext>`, taken in through the same `/api/chat/files` upload pipeline, with no server-side image editing. The listing itself pages like every other table in the application: a summary, a page counter and a page size of 12, 24, 50 or 100 rows, which restarts at the first page when it changes.

A selection is downloaded as one ZIP through a recorded request the Worker packs (MEM-152 phase 3). `POST /api/chat/library/archives` takes at most 100 files of at most 30 MiB together — the storage adapter writes one object of at most 32 MiB — refuses more with a named reason, allows one owner three waiting requests, and answers 202 with the archive. `memoryos-chat-library-archive-v1` (five-second fixed delay) claims a request with a lease and an attempt count as the usage report does, resolves the selection against the library again, packs the bytes into a tracked server write with colliding names suffixed ` (2)`, ` (3)`, and records in `skipped` every file that had gone; a request with nothing left to pack fails with its own reason instead of storing an empty ZIP. `GET /api/chat/library/archives` and `…/{id}` report progress, and `…/{id}/content` streams the ZIP to its owner alone while `expires_at` (six hours) holds. The same task sweeps expired archives: mark the object delete-pending, delete the key outside any transaction, then release ownership and the row under the claim, as the artifact sweep does. The preview modal also gains rotation, drag-panning while zoomed and previous/next across the files the page lists, with the arrow keys.

How much a person's library may hold is a deployment setting: `memoryos.chat.storage.library-bytes` (`MEMORYOS_CHAT_STORAGE_LIBRARY_BYTES`, default 512 MiB; `0` means no limit) bounds every person's library, because the bytes live in one object store whose size is an operational fact rather than a per-Tenant decision. `GET /api/chat/library/usage` answers the caller's used bytes, file count, per-category breakdown and that limit, all from the library's own union rather than a listing of object storage, and `/settings/storage` shows it to the person with a row per category leading into `/library?category=`. Nothing in the product raises it for one person: there is no Tenant limit, no exception table and no administration route. A write that would pass the limit is refused before any byte is stored — `POST /api/chat/files/uploads` and the server-side copy answer `409 CHAT_STORAGE_FULL` before an upload is authorized — while a generated file or image is simply not stored and the tool reports that in the answer, so a full library never fails a turn.

Deleting a library file moves it to a trash ([ADR 0014](../decisions/0014-file-library-trash.md)). The file leaves every listing, preview, download, turn context and search at once, as before, and history keeps its tombstone; what changes is that its bytes are released only after `memoryos.chat.retention.trash-after` (`MEMORYOS_CHAT_TRASH_AFTER`, default `30d`; `0` releases at once as MEM-142 did). Nothing new deletes bytes: the artifact sweep refuses to claim a row whose window holds, and `memoryos-chat-library-trash-v1` (five-minute fixed delay) queues the existing upload DELETE work once the window has passed. `GET /api/chat/library?status=TRASH` lists what the owner deleted with `deletedAt` and `purgeAfter`; `POST /api/chat/library/{source}/{id}/restore` takes one back while its bytes are still there, `…/purge` ends its window now, and `POST /api/chat/library/trash/empty` ends every window the owner has. An upload whose release is already queued can no longer be restored, and the page's delete confirmation names the configured window, so a deployment with no trash still says deletion is final.

Deleting a conversation stays a soft deletion, and `memoryos.chat.retention.hard-delete` (`MEMORYOS_CHAT_HARD_DELETE`, default off) decides whether it stays that way. With the switch on, a `memoryos-chat-session-purge-v1` recurring task (one-minute fixed delay) claims deleted conversations with `FOR UPDATE SKIP LOCKED`, skipping any whose reply is still `RUNNING`, marks their generated files and images `deleted_at` so the artifact sweep releases the bytes, and deletes the conversation's `chat_command`, `chat_feedback`, `chat_sharing`, `chat_message` and `chat_session` rows; uploads are never touched, as Onyx skips a message file carrying `user_file_id` ([MEM-143](../increments/completed/mem-143-chat-hard-delete/design.md)). Onyx purges inside the delete request; MemoryOS purges in the worker, because artifact bytes need the claim-fenced sweep and because a switch turned on later must also drain what was deleted before it.

`memoryos.chat.retention.deleted-after` (`MEMORYOS_CHAT_DELETED_AFTER`, default `30d`) bounds that claim: a conversation is purged only once it has been deleted for longer than the window, and `0` purges at once as before ([MEM-153](../increments/completed/mem-153-chat-lifecycle/design.md)). The window is invisible — a deleted conversation leaves every listing immediately — and the sweep logs how many are still waiting beside how many it purged.

Each person also decides how long their own conversations are kept: `chat_preferences.retention_days` (1–3650, absent means no policy) is theirs alone, read and written through `GET/PUT /api/chat/retention` by the owner with no further authority, and offered in personal Chat settings as Never, 30, 90, 180 or 365 days or a typed number. `memoryos-chat-retention-policy-v1` reads one policy per person and soft-deletes 200 of that owner's conversations per run as their owner deleting them would, after which the purge above treats them like any other deletion; one member's number never touches another member's history. `GET /api/chat/retention/preview?days=` answers how many of the caller's own conversations the number would delete now, so nobody saves a policy without seeing what it takes. A Tenant that had recorded the earlier administered policy handed that number to each of its members when it moved (V104).

`sessionId` narrows the listing to one conversation ([MEM-144](../increments/completed/mem-144-session-files/design.md)): its artifacts by `session_id`, and the uploads attached in it, read from that conversation's own `chat_message.files` descriptors. The upload branch also requires the caller to own a non-deleted conversation, so an Agent-attached upload cannot reveal where else it was used; a conversation the caller does not own simply matches nothing. A paperclip button on the conversation header opens a right-hand sheet with those files, each with preview, download and confirmed deletion. Onyx's `GET /projects/session/{id}/files` returns the session's **project** files instead, so it is not the shape used here.

The page offers a table and a grid (image thumbnails), the source and category filters, name search, the four sorts, Today/Yesterday/Earlier grouping of the server's order, the total size of the current filter, and per-file preview (the MEM-111 modal, which now also opens a generated image), download, open-conversation and confirmed deletion, plus a multi-select deletion. Deleting an artifact and each sweep that releases bytes log `chat.artifact.deleted` and `chat.artifact.cleanup.released` with the artifact kind and counts, never file names, prompts or object keys.

Multi-select works at two places and belongs to the page being read: the bar above the list chooses every file on this page (its label says so, and it shows a dash while only part of the page is chosen), and each day heading chooses that day alone. Paging or changing a filter drops the selection, because the commands act on the files the page is holding, not on a filter the server would have to re-resolve.

Every surface that draws a generated image small — the library rows and cards, the library picker and the conversation file panel — requests `variant=THUMBNAIL`, while a preview and the answer's own images request the artifact. The thumbnail is a JPEG whose long side is 512 px, kept in object storage beside the artifact (`thumbnail_*` columns, V106) and written the first time one is asked for. An original at or below 64 KB, bytes this build cannot decode, and a rendering no smaller than its source produce none, and the artifact itself is served instead. A thumbnail is derived from bytes the owner is already charged for, so it does not count against their storage limit, and it is released with the artifact by the same sweep, which claims it where a generated file carries its converted PDF.

## Browser integration

`/` starts a new conversation; `/chat/{sessionId}` loads a private selected-branch transcript. The shared application sidebar header holds the brand, the conversation search icon and the collapse button; its list contains New chat, Search documents, Assistants, project folders (a link and a drop target, with no inline expansion) and paginated conversation history. A saved conversation has one header with its title, Share and an overflow menu; other pages show their plain title, with no Chat/Search mode menu. Sidebar navigation does not cancel a running inference. The mobile sidebar is the existing modal drawer. Welcome and composer are centered together before the first message; the conversation composer stays at the bottom. Layout and interaction follow the MemoryOS tokens and Radix controls. ModelSelector, MarkdownText, Logos, InlineCitation, Sources, ThinkingIndicator, EditMessage, MessageActions, MessageBranches, FeedbackDialog and ThreadList are CLI-installed assistant-ui elements under `web/src/components/assistant-ui/elements`. The controlled editing/branch/feedback elements call MemoryOS commands; `ThreadListItemMorePrimitive` supplies the conversation menus. MarkdownText accepts the citation plugin and app Copy control. InlineCitation exposes the registry specimen as a streamed marker using the existing Radix HoverCard. Sources retains the compact toolbar trigger and opens the application-owned source panel. The picker displays one model-name row without repeating the raw model ID; the composer omits a permanent keyboard-helper note. Native Logos cover OpenAI, Claude and Gemini; unrecognized model names use the generic icon without changing catalog IDs or provider routing.

The composer model picker loads the session-aware authorized catalog, groups models by provider, and sends `modelConfigurationId` per turn. Automatic leaves the ID absent so the backend applies Persona → Tenant default resolution. A selected ID is a browser-session preference scoped to Actor; the backend revalidates every send. Selection is captured before asynchronous admission and disabled while running/recovering. A backend fallback updates the displayed selection and shows a notice. Thinking effort remains provider/admin configuration, not an unsupported browser override. Catalog administration is separate MEM-77 work.

`useChatRuntime` from `@assistant-ui/ai-sdk` connects native assistant-ui primitives to Vercel AI SDK message state. `MemoryOsChatTransport` implements public `ChatTransport` and uses the generated Java API client and SSE parser. It converts named events into UI message chunks; it does not execute tools or create another message store. Server tool calls become `dynamic-tool` parts marked provider-executed, reasoning becomes reasoning parts, and answer text opens a new text part after other activity, so parts keep their streamed order. Unknown event types are skipped rather than failing the reply. Stable UUID request IDs and server-assigned user/assistant IDs are retained. A new session is created lazily from the first question, including the draft's project ID when present. After acceptance, the URL changes to its session while the same runtime, composer and SSE reader remain mounted; no history hydration or extra metadata read occurs during promotion. Opening a different conversation or project resets the draft. Unsent composer text is kept per actor and conversation in the tab's sessionStorage and restored after a reload; sending or clearing it removes the entry. Metadata invalidation after rename/move updates the header without reinitializing the transcript.

The composer supports native Enter/Shift+Enter and IME handling, with a 32000-character limit. Markdown/code blocks and copy use native message parts; math renders with KaTeX as Onyx (`remark-math` with single-dollar math): LaTeX `\(...\)`/`\[...\]` delimiters are normalized to dollars and currency such as `$5` is escaped first. A question's attached files sit above its bubble as outlined cards, as in Onyx, rather than inside it. Every file surface (search results, cited sources, attachments, the file picker and generated files) uses one tinted file-type glyph from `documentKind`: the media type decides, and an octet-stream, `text/plain` or unknown type falls back to the file name's extension, as Onyx `getFileIcon`. While a run is live and nothing streams — before the first part or after a step while the model writes its next call — the answer shows "Đang suy nghĩ…": before the first part as its own indicator, afterwards as the last activity group's live header, which keeps saying it is working until answer text follows or the run ends; the action bar (copy, sources, regenerate) appears only when the run ends, and a step's read documents show one chip per document, not per passage. Previews and charts run under the deployment Content-Security-Policy (`style-src 'self'`): chart series colors are custom properties set through React styles, Word previews apply docx-preview's inline and `<style>` rules through CSSOM (element styles and adopted stylesheets), PDFs reach pdf.js as a Blob rather than a `blob:` URL, and `img-src` allows `blob:` for image previews; links use explicit HTTP(S) URLs and open outside the app. Native viewport behavior follows output while at the bottom, preserves an upward-scrolling reader, and offers a return-to-latest control. Stop calls the Java cancel endpoint while retaining the reader; only committed cancellation invokes native runtime cancel. History metadata renders saved FAILED/CANCELED outcomes after reload.

The adapter ignores duplicate sequences, checks run IDs/cursors, caps each stream connection at 65 seconds and resumes from the last applied cursor until the outcome, as described under [Streaming and reconnect](#streaming-and-reconnect). A reset or sequence gap falls back to saved history, polling only the reply after its stable USER parent every two seconds for as long as the reply remains RUNNING. A turn has no total deadline; lease reconciliation fails a run whose process died. It never resubmits the question automatically. EOF is not a successful terminal outcome. If a history poll fails, sending remains disabled and Check conversation reloads authoritative history. Stop during send admission is retained until the reservation supplies an assistant ID. HTTP 401/403/404 hides the current transcript and refreshes identity. Route unmount and authority changes release subscriptions; they do not cancel backend execution.

Browser bounds: stream response 8 MiB per connection, reply 1000000 characters, complete history 8000000 characters/100 pages and a 30-second history fetch deadline. Exceeding history bounds reports an unavailable conversation instead of silently dropping its prefix. These are browser protection limits, not configurable backend context limits or a claim of unlimited history support. The transport retains only the current text prefix needed to reconcile a durable fallback with SDK-owned text.

## Voice

Voice connections are Tenant-owned Chat configuration, separate from the LLM model catalog. `MODELS_MANAGE` controls `/admin/voice`; reads expose only `credentialConfigured`. OpenAI, OpenAI-compatible, ElevenLabs, Azure AI Speech and Soniox have provider-specific validation and adapters. Soniox is speech-to-text only: its connection rejects read-aloud model and voice settings, it cannot be selected for Text-to-Speech, and `/admin/voice` lists it only under speech to text (the provider response carries `speech`). One active STT and one active TTS connection may be selected per Tenant. Member settings store Auto-Send, Auto-Playback and playback speed. Chat and Search authorize transcription with `CHAT_WRITE` or `SEARCH_READ`; synthesis requires `CHAT_READ`.

The browser requests a CSRF-protected, single-use ticket whose purpose is `TRANSCRIBE` or `SYNTHESIZE`, then opens the matching same-origin WebSocket. Tickets expire, are consumed atomically and live in one API process. The transcription socket accepts only PCM16 24 kHz mono binary frames plus one `{type:"end"}` control message, with 64 KiB frame, 25 MiB recording, 60-second idle and 10-minute session bounds. Audio remains in memory for the connection and is never persisted. The server response is `{type:"transcript", text, isFinal, utteranceEnd, revision}`. `revision` increases on that MemoryOS connection; the browser ignores a non-increasing revision so delayed provider work cannot regress the composer. `isFinal` means committed text, while `utteranceEnd` is reserved for a real provider VAD boundary and alone may drive future server-side pause semantics.

The public OpenAI connection uses a provider Realtime transcription WebSocket with fixed live model `gpt-live-transcribe`, PCM 24 kHz, low transcription delay, the member UI language and turn detection disabled. Provider deltas become cumulative interim text. Browser Stop sends the provider buffer commit; the MemoryOS handler emits the final transcript with `utteranceEnd:false`. The configured STT model remains authoritative for REST and fallback. Realtime connection, send, parse, close or final-timeout failure replays the complete bounded recording through the chunked batch path. An initial Realtime connection failure selects a chunked session during setup. OpenAI-compatible endpoints do not inherit this behavior by name; they, ElevenLabs and Azure use the existing chunked/REST adapters.

Soniox uses its realtime WebSocket (`stt-rt.` host derived from the REST endpoint, `/transcribe-websocket`): the key and a PCM16 24 kHz mono configuration with the language as a strict hint travel in the first text message, audio as binary frames. Final tokens are committed text and non-final tokens extend the interim preview; `<fin>` and `<end>` markers are dropped. Stop sends `finalize` and an empty frame and waits for `finished`. A provider `error_code`, close or send failure replays the bounded recording through the chunked path, whose REST adapter is Soniox async: upload, transcription with the matching `stt-async-` model, polling, transcript read, and deletion of both the transcription and the file on success or failure. A key is verified by an authorized one-item transcription listing.

The composer freezes send while dictation is settling, preserves the pre-recording draft and applies cumulative transcript updates. Auto-Send remains tied to the current client stop/pause behavior until a provider VAD adapter emits a genuine utterance boundary. Read-aloud and Auto-Playback stream synthesized audio without storing it; stopping, navigation and authority changes close their sockets and players. The UI reuses the installed shadcn/Radix controls and assistant-ui primitives; comparative UI references inform presentation but do not change the provider or authorization contract. Full active scope and open live-provider/Safari gates are in [MEM-91](../increments/active/mem-91-chat-voice/design.md).

## Conversation editing, assistants, projects and collaboration

V36 extends the existing tree without changing old message IDs. `chat_command` records SEND, EDIT and REGENERATE receipts per session/request UUID, including the target, text and requested model. A replay returns the same reservation; changing these inputs under one UUID conflicts. EDIT creates a sibling USER plus ASSISTANT; REGENERATE creates only an ASSISTANT under the selected USER. Both run through the same native execution, budget, Stop and finalization path. Selecting a stored version changes its parent's latest child, preserves descendant branches and generates nothing. The caller supplies the expected selected child to detect competing selections. Settings, branch mutations and admission recheck current owner/Tenant authority, serialize through capability repository locks, and reject changes to the conversation's context while a reply is active.

Rename changes the header/sidebar title. New browser conversations start with a whitespace-normalized first-question fallback, limited to 40 whole grapheme clusters (preserving joined emoji and combining marks) and the API's 200 UTF-16-unit limit including the truncation marker. After a completed answer, the browser requests `POST /api/chat/sessions/{id}/title`; the server atomically claims naming once, resolves the Tenant conversation-naming model when one is set and still eligible and otherwise the conversation's authorized model ([task models](chat-models.md#task-models)) through the existing catalog/native inference lifecycle, and generates a bounded title (10-second deadline, 128 output tokens, at most 80 Unicode characters stored). This separate best-effort request never blocks answer streaming. Failure retains the fallback; manual rename or a changed session snapshot wins over late generation. V40 preserves existing session names and does not mass-rename history. The header truncates visually while retaining the full title as a tooltip. No naming queue/worker is added.

Delete hides the session from every private/shared read and list, cancels any active reply and discards local replay/readers for all branches. Delete all chats applies the same deletion to every session the caller owns in the Tenant; shared conversations of other members are untouched. Conditional terminal writes cannot resurrect the deleted session. This is a soft deletion; no restore or hard-purge promise accompanies it. Deleting a Project instead unlinks its sessions and retains their history. Deleting a custom Persona retains its reference for history but blocks subsequent admission until an available assistant is selected.

Custom agents (Persona, UI: assistant) follow Onyx authority, sharing, discovery and prompt shortcuts as specified in the [MEM-119 design](../increments/completed/mem-119-custom-agents/design.md): `AGENTS_CREATE` creates, use and edit authority comes from ownership (Actor or Group), direct and Group shares, public access and `AGENTS_MANAGE`, and every view carries fail-closed `permissions` hints (`edit`, `share`, `setPublic`, `delete`, `transfer`, `leave`, `manage`). Fields are name (200 characters), description (2,000), instructions (20,000), task prompt (20,000), up to 20 starters, direct Sources and up to ten Document Sets. Direct Sources and Document Sets are additive; a Document Set is a named, shared Source allowlist that only narrows the actor's existing Source and Document authority. `AGENTS_CREATE` creates a Set; its owner and `AGENTS_MANAGE` may edit, share, publish or delete it; direct user and ordinary-Group shares permit use only. A Set may also be public, which lets every Tenant member use it without a share and still narrows each of them to their own Source authority; public is off by default and only an editor may change it. A viewer who is not an editor sees only the Set Sources they may themselves select, plus a `hiddenSources` count. The agent editor and the `/admin/document-sets` manager (list, `new` and `$documentSetId` form) reuse the existing Source and principal pickers. Empty or unavailable Document Sets never widen retrieval: a turn distinguishes an agent that attaches nothing (search every authorized Source) from one whose attachments resolve to nothing for the asking actor (search nothing).

Builtin Persona provisioning inserts only when absent; create/send/catalog reads no longer overwrite saved instructions or model selection. `JpaPersonaRepository`, `JpaProjectRepository`, `JpaChatSharingRepository` and `JpaChatFeedbackRepository` own lifecycle operations and scoped reads. Services own authorization and transaction boundaries; `@Version` detects stale editors. The catalog uses the same Spring Data approach for providers/models/defaults; tree/command/conditional execution operations remain in `JdbcChatRepository`. No IAM repository is migrated here; that handoff is recorded in MEM-55/MEM-36.

`/projects` lists private projects; `/projects/{id}` edits instructions and manages conversations. `ChatWorkspaceService` creates a conversation with its assistant/project atomically and applies combined settings atomically; an unavailable project rolls back an assistant change. A custom Persona supplies instructions even when empty and takes precedence over Project instructions. The builtin assistant adds Project instructions. Resolution reads the Persona model binding and configuration revision in one SQL snapshot under the owner lock and a shared Persona row lock; admission repeats the locked read and checks the revision. The row lock also excludes edits to the builtin Persona by another owner. Admission captures the effective instructions, options and configuration revision in the in-memory turn context, so later editor changes do not change an admitted run. No transcript from another project conversation is imported.

Creating a Project asks only for a name, then opens its workspace with its files, the native Chat composer and recent conversations. The name and instructions are edited in one settings dialog reached from the workspace's overflow menu, which is also where the project is deleted; the workspace itself shows no instructions card. No empty session is created merely by opening a project or typing. Conversation menus move/unlink the existing session; desktop drag and drop uses the same command. Project deletion preserves conversations in general history.

Conversation rows rename inline: Enter saves, Escape cancels, and a failed save retains the draft. Header and row menus provide sharing, project membership and confirmed deletion; existing assistant settings remain in the header menu. Message editing is inline and keeps its draft and request UUID after a failed command. Regeneration and saved-version controls call generated server commands, then reload the selected branch and resume any admitted reply. A menu beside Regenerate lists the authorized model catalog and regenerates with the chosen model without changing the composer choice. Answers show their local time on hover or focus, from the saved `createdAt`; a live reply uses the time its send was accepted until reload. External Markdown links in answers render as inline source chips adapted from the assistant-ui Sources element; only hostnames of the answer's Web sources are sent to the favicon service, other links show a letter fallback. Selecting a passage inside one answer offers Quote; the pending quote appears above the composer and is sent as a leading Markdown blockquote of the question, which saved questions render as a quote block. Previous versions remain selectable. Feedback has separate positive/negative buttons and a reason/comment dialog; clicking the saved reaction again removes it. Each answer version retains its own feedback. The server tree remains authoritative after reload. Starter buttons fill the composer. Busy or uncertain execution blocks additional edits and sends until status is confirmed; canceling the inline editor remains possible after a failed command.

The sharing dialog creates/copies the link without closing, exposes a selectable URL when clipboard access fails, and lets the owner revoke in the same dialog. Reopening fetches the current sharing revision and prevents writes until that fetch succeeds. Access choices are native radio controls usable with the keyboard.

Sharing starts private. The owner can enable/revoke the session link with an expected revision. `/shared/{sessionId}` requires an active same-Tenant membership with `CHAT_READ` and reads only the currently selected saved branch through dedicated shared APIs. It has no composer, editing or Stop and does not subscribe to the owner's inference. The page rechecks access using the lightweight shared-session endpoint on focus and every 30 seconds, removing displayed content on denied reads. Full history loads on entry, focus or manual reload; the periodic access check does not paginate the transcript. Every API read revalidates sharing and membership. Sharing grants transcript access only: citation previews still use the reader's source authority. Revocation cannot retract text already viewed or copied.

The browser keeps one assistant-ui remote thread list for the authenticated application. The sidebar lists conversations from it, and the route selects the visible thread. Only the visible thread keeps a reply reader open. A reply in a conversation the user leaves keeps running on the server and is resumed from saved history when that conversation is shown again. Title generation runs once after the first completed answer. A conversation may be archived: `archived_at` takes it off the sidebar and keeps everything else about it, `?archived=true` lists the archive, `POST …/archive`, `…/unarchive` and `…/archive-all` are owner-only and idempotent, and sending a message into an archived conversation unarchives it in the same transaction that reserves the turn. History search still finds an archived conversation and marks it. "Search conversations" sits under "New conversation" in the sidebar and also opens with Ctrl/⌘+K.

Feedback belongs to the owner Actor and a specific saved ASSISTANT output with nonblank content. It supports nullable positive/negative rating, comment (4000 characters), reason (100), and removal; at least a rating or nonblank comment is required. Regenerated outputs have independent feedback. Shared readers cannot mutate feedback or conversation state.

## Owner authorization

`ChatSession` belongs to the configured Tenant and an Actor. An active membership is necessary; even a different member/admin cannot read another Actor's private session through these endpoints. Identity comes from the existing principal; Tenant/owner fields are not accepted in the creation body. Missing, wrong-owner and inaccessible session lookups return `CHAT_UNAVAILABLE` without disclosing contents. The existing API membership filter rejects revoked membership with 403 before Chat handling.

`Persona` is the AI role configuration, not a user profile. The built-in default Persona is provisioned idempotently when an authorized session is first created; subsequent creates reuse its identity and apply the configured defaults. `memoryos.chat.persona.name`, `.instructions` and `.model` have initial defaults MemoryOS, a general assistant instruction, and gpt-5-mini. The runtime registers this configured model as a native Embabel LlmService; the deployment model initializes the catalog once, and each turn explicitly selects its native service. Backend model selection and access now follow the [catalog contract](chat-models.md).

`ChatMessage` stores a root, USER or ASSISTANT node and its parent/latest child. Root nodes are not returned as visible history. Latest child must be a direct child in the same session, enforced by a deferred composite FK. One root and at most one RUNNING assistant per session are enforced by partial unique indexes. `runId` is the reserved assistant message ID; no separate ChatRun table exists.

## Internal persistence contracts

Within a transaction, IAM shared-lock revalidation precedes the session write lock. A send reservation atomically creates USER and ASSISTANT nodes and updates latest-child pointers. Retrying the same client request ID with the same parent/text/requested model ID returns the original message IDs and selection; changing any of these fields conflicts. A different send while a reply is RUNNING conflicts. Send accepts an optional stable `modelConfigurationId`; the [catalog contract](chat-models.md) owns precedence, access and fallback.

The USER row retains `original_assistant_message_id`, written with the initial pair. Retry resolves that original assistant even if latest-child selection has changed or another turn is RUNNING; it neither changes branch selection nor creates messages. The original reference is required on USER rows and must identify a direct child in the same session. It is internal persistence data, not a history response field. Branch changes are exercised with database fixtures; edit/regenerate endpoints remain unimplemented.

Request idempotency, composite tree constraints and conditional PostgreSQL terminal writes are MemoryOS implementation choices. Their rationale and costs are retained in the [completed Chat design](../increments/completed/mem-11-production-chat/design.md). Private-only access is the base contract; sharing uses its own authorized read path and any future administrative transcript access requires a separate operation.

Continuation accepts the selected leaf, not arbitrary branch edits. Session history is bounded to 9999 nodes including the root; input text is limited to 32000 Java characters. Internal reservations receive a positive run lease of at most one day. A terminal write accepts up to 1000000 characters, changes RUNNING once, and cannot overwrite a terminal result. Local Stop accepted before the immutable terminal decision wins cancellation. Only lease reconciliation fails a RUNNING row; a live process can still finish after a slow renewal. Finalization reads back the actual DB winner before publishing an outcome; a successful conditional write does not mean generation succeeded.

Flyway V18 owns the session schema; V19 adds execution metadata, and V20 removes the former DB Stop marker without rewriting V19. V33 adds the provider/model catalog and historical request/selection IDs; V34–V35 add grounded sources/search metadata, V36 adds editor/project/sharing state, V54 backfills legacy catalog tokenizer profiles, and V55 widens the `chat_web_connection` provider constraint for the search gateway. SQL and locks stay in `chat.persistence`; actor-facing application services own access and transactions, with JPA lifecycle repositories for mutable catalog/editor entities. No temporary execution profile, fixtures, provider credentials or QA files are installed in the application.

## Execution lifecycle

The API owns a Spring SimpleAsyncTaskExecutor using virtual threads, without replacing Boot's applicationTaskExecutor. ChatTurnService admits at most the configured number of active turns, including outcomes waiting for a DB retry or native work to stop; there is no Chat queue or worker. Native Reactor cancellation terminates the stream on Stop. Shutdown signals cancellation and waits up to five seconds for task finalization before Spring closes the executor. Spring owns executors; Search tracks actual tool/native bodies so cancellation can interrupt them and retire resources after they exit. A process kill or exhausted drain can still lose unsaved partial output.

ChatTurnPersistence loads authorized product context and freezes the effective Persona/Project instructions, search/source restrictions, token limits and framework prompt contributions for the admitted turn. The builtin Persona is seeded only when absent; editor/model-default updates remain authoritative. One immutable binding policy checks complete mandatory instructions/question before inserting messages, selects history and measures every converted native request. The hosted O200K estimator retains an explicit framing allowance. The DB read is capped at 201 ancestor nodes and 1 MiB of content; model input omits root/placeholder nodes and an orphan oldest assistant. Selected context stays in RAM.

ChatModelExecutor calls native PromptRunner, streamer and tool loop. One runner-wide `ChatToolActivity` tool-call inspector publishes `STARTED` and a terminal stage with the provider tool call ID and duration for every tool; tools and evidence attribute their progress to that call. StreamingLlmService binds verified streaming capability without a discovery inference. ChatModelGuard validates finish metadata, applies capability/output/input policy to every native call after framework conversion, independently disables tools on the final cycle, and records native LlmInvocation usage once per inference. Validate shares the binding policy. Native Embabel computes totals/cost and evaluates configured budgets. Missing usage/pricing stays unknown; estimates do not replace it. Search tool accounting and authorization boundaries are specified under Grounded Chat below.

Stop authorizes the assistant/session and signals local execution directly. A bounded array of session command locks prevents Stop from overtaking reservation/registration. No active-row Stop polling or replica signaling remains. A turn has no total deadline, as Onyx. PostgreSQL stores a run lease (`memoryos.chat.execution.lease-ttl`, 30 minutes) that the owning process renews every `lease-renewal` (60 seconds) while the run is active. A failed renewal is logged and retried without stopping the run; a run whose row is no longer RUNNING at renewal is interrupted locally. Reconciliation fails up to 100 RUNNING rows with a lapsed lease per pass after a five-second grace, so only process death, or a renewal outage longer than the lease, ends a run this way. A graceful shutdown fails in-flight runs within five seconds. After a hard kill, API startup fails every remaining RUNNING row with `CHAT_INTERRUPTED` before the web server accepts requests, because the single-replica deployment means a new process owns no run; several API replicas would require removing this. Until the API starts again, a RUNNING row stays until its lease lapses (up to `lease-ttl` plus the five-second grace): the session rejects a new send as a conflict and the browser keeps polling that reply. Cycles, token/cost budgets, the provider read gap and per-call tool timeouts bound work. No model/tool call is retried. Terminal persistence can retry while keeping the active slot; process death can lose output not yet saved.

The provider composition owns reusable synchronous/asynchronous Spring AI SDK clients, a connect and read/write gap timeout (`memoryos.chat.execution.provider-read-timeout`, 60 seconds) with no total call bound, disabled automatic retries, close hooks and native observations/meters. `ChatModelBinding` retains the native SpringAiLlmService and request policy; each run resolves it into RAM before dispatch. Decorating a model preserves converter/pricing/capabilities/adapters. The generic executor uses `Ai.withLlmService` and has no OpenAI options cast. The [catalog contract](chat-models.md) owns UUID selection, Group/Persona access, encrypted BYOK, installed tokenizer profiles, bounded client/native-asset leases and Models/default administration. The existing `openai` adapter serves both configured profiles; Chat selector UI remains separate, and API-to-real managed-model qualification is still pending.

`OpenAiCancellation` cancels the raw HTTP call before attempting to close a reader that may be blocked. Each stream subscription owns its cancellation state, covering pre-header and active-read cancellation without one subscription canceling another. Local real-socket tests establish this transport behavior, not real vLLM work/slot release; the latter remains a managed-model acceptance gate.

Saved-connection validation probes the combination the turn will actually send: a model declaring tool calling validates with one never-called tool declaration and `tool_choice: none`, so a provider that refuses function tools beside this entry's reasoning options fails at configuration time instead of on the first tool-bearing turn. When such a rejection names `reasoning_effort` `none` as the remedy, the Chat Completions route retries that request once with that effort and logs the downgrade; an already-started stream is never retried.

Provider endpoints are server-owned configuration. HTTPS remains the default; explicitly configured HTTP endpoints are supported for internal deployments. HTTP(S), host and URL structure are validated before SDK construction; URL credentials, query strings and fragments are rejected without echoing their values. Network transport protection is a deployment responsibility; Chat does not infer trust from a hostname or categorically reject internal HTTP.

## Streaming and reconnect

`StreamBufferWriter` keeps each reply's ordered events (`text-delta`, `reasoning`, `tool`, `image`, research events and `outcome`) in Redis, as Onyx's stream buffer ([MEM-26](../increments/active/mem-26-chat-stream-redis/design.md)): one Redis Stream `memoryos:chat:stream:{assistantMessageId}` whose entry IDs are the sequences (`0-n`), with the event JSON as its `data` field. Reasoning shares the answer's chunking and a change between text and reasoning flushes the pending chunk. Every event carries the assistant ID and sequence; only an outcome published after the terminal transaction commits confirms completion/cancellation/failure, and the outcome entry is the done marker. Chunking stays in the API process that runs the turn; the flush tick writes queued entries to Redis outside the chunking monitor, so Redis latency never blocks the model writer. A failed write is logged, kept in the reply's queue and retried on the next tick; entries Redis already holds (a timed-out write that was applied) are acknowledged from the stream's last ID, so the sequence stays contiguous. Replay survives an API restart and any API process can serve it; execution does not survive: a dead process's reply still ends through startup or lease reconciliation. A missing prefix or a truncated replay produces an unnumbered `reset` with `BUFFER_GAP`; a missing buffer produces `BUFFER_MISSING`. `BUFFER_EXPIRED` remains in the contract but is not emitted, because an expired key cannot be told from a missing one. Consumers then read history and poll RUNNING with a bounded policy; they must not start a new inference automatically.

The MVC controller returns `ResponseEntity<Flux<ServerSentEvent<Object>>>`, following OrgMemory's HTTP composition style. Spring owns SSE writes and subscription lifecycle. `ChatEventStream` reads bounded batches on the existing virtual-thread executor, with prefetch 1 and resource cleanup on cancellation/error/completion. HTTP disconnection or connection timeout closes only its reader. The model writer is independent. MVC socket writes remain blocking on Boot's application executor; this is not a WebFlux migration or a claim of higher throughput.

Authorization and cursor preflight run synchronously before the response. Reader allocation is deferred until subscription, and each subscription owns its own cleanup; an unconsumed publisher holds no reader slot. Terminal persistence uses a nonblocking finalization claim independent of the state monitor, so a slow terminal write does not hold the monitor used by Stop and text callbacks. Terminal publication is serialized. Admission is released exactly once after both persistence and actual work retirement complete.

Each read replays from the cursor with `XRANGE`, draining the backlog without sleeping, then polls every `poll-interval` (200 ms, Onyx `CHAT_RESUME_POLL_INTERVAL_S`) until events arrive or the 15-second heartbeat is due. A blocking `XREAD` is not used because it would stall the shared Lettuce connection. When a read finds nothing new, first at once and then at every heartbeat, the reader re-authorizes the actor for the reply and checks that it is still RUNNING; a revoked membership ends the stream with the authorization failure. A reply that is no longer RUNNING gets a final drain of up to 2 seconds for its outcome and otherwise ends with a reset, as Onyx ends a resume when the processing fence lapses. Every live stream therefore ends with an outcome, a reset or the connection timeout; a dead writer, a startup- or lease-failed run, an expired buffer and a Redis outage all reach history instead of hanging. A reader that cannot reach Redis ends at once with `BUFFER_MISSING`, as Onyx's resume endpoint answers without a buffer, rather than failing the subscription.

## Query history for administrators

An organization can read what it is being asked, under `CHAT_HISTORY_READ` — an ordinary grant given through a Group,
implied by administrator access, and held apart from every other administrative power, as `AUDIT_READ` is. This is
the separate administrative read path that *Internal persistence contracts* reserves; no owner-scoped endpoint is
widened.

`chat_settings.chat_history_visibility` (V107) decides how much is visible, as Onyx's `query_history_type` does, and
a model manager changes it. It defaults to `NORMAL`.

- **`NORMAL`** names the person who asked.
- **`ANONYMIZED`** drops their name and e-mail before the answer leaves the server, and refuses to narrow a read to
  one person. It hides nothing else: the questions and answers stay as they are, and a question often names its
  author, so the screen says so rather than letting the word promise more than it does.
- **`DISABLED`** refuses every read. Conversations are still recorded.

What the read covers:

- **A temporary conversation never appears**: its message content is not written at all.
- **A conversation its owner deleted is listed and marked as deleted**, as Onyx lists one. Hard deletion is off by
  default, so the row is still there; the retention policy eventually removes it and it leaves this screen too.
- **Citations are named, not opened.** A transcript carries the titles a message cited; reading a source goes through
  the reader's own Source authority, never the asker's, which is the rule sharing already follows.

| Method and path | Contract |
| --- | --- |
| `GET /api/chat/history` | A page of conversations, newest first, on an opaque `(updated_at, id)` cursor. Filters: `from`, `to`, `q` (asker or title; `%` and `_` are literal), `actorId`, `feedback` (`POSITIVE`, `NEGATIVE`, `MIXED`, `NONE`). `size` is 1–100, default 30. Each page also carries the period's counts |
| `GET /api/chat/history/{sessionId}` | One conversation's transcript on its selected branch, with each message's feedback and cited titles |
| `GET /api/chat/history/export` | The filtered conversations as CSV, at most 50,000 rows, with a byte-order mark and formula prefixes neutralized |
| `PUT /api/chat/settings/history-visibility` | Chooses the mode; requires `MODELS_MANAGE` |

Every transcript opened is recorded as `chat_history.read` and every export as `chat_history.export`, through
[audit](audit.md), written outside the read so a failed read still leaves evidence. Listing is not recorded: it shows
no message body beyond the first question and answer, and at chat volume it would drown the stream. Onyx records
nothing at all here.

Admin › Monitoring › Conversation history (`/admin/chat-history`, vi "Theo dõi › Lịch sử hội thoại") shows the
period's counts, one row of filters, the shared table and pager, a conversation in a centred dialog, and an export
link carrying the filters on screen.

## Conversation lifecycle

Branching copies one conversation's selected path into a new one of the caller's own: `POST /api/chat/sessions/{id}/messages/{messageId}/branch` copies every message up to and including that one, keeping its text, status, attachments, citations, activity and model record, and records `branched_from_session_id`/`branched_from_message_id` so the branch's header links back. A branch always ends on an answer, so naming a question copies the answer that followed it; a running reply, a message off the selected path, a conversation the caller does not own, a path longer than 1000 messages and generated files beyond 50 artifacts or 30 MiB are each refused by name. Generated files and images are copied as the branch's own objects, so deleting either conversation leaves the other whole; uploads are not copied, because an upload belongs to its owner rather than to a conversation.

A temporary conversation (`chat_session.temporary`) is left out of the sidebar, the archive, history search, the file library, Projects and sharing, and `memoryos-chat-temporary-session-v1` soft-deletes it once its last message is older than `memoryos.chat.retention.temporary-after` (default `24h`). The purge then removes it without the deployment switch and without the window, and releases the uploads sent into it — the one case where an upload's lifecycle follows a conversation, recorded as `chat_user_file.temporary_session_id`. AI usage is still recorded for a temporary conversation; its message content is not.

`POST /api/chat/exports` records an export of the caller's own data, which `memoryos-chat-export-v1` packs under a lease as the MEM-152 library archive is packed: every conversation the owner has not deleted, as JSON and as a self-contained HTML page, plus the files their library lists, bounded at 30 MiB with what was left out named in the ZIP's index and in the response. One export per person at a time; `…/content` streams to its owner alone while `expires_at` (24 hours) holds, and the same sweep releases the bytes. Deleted and temporary conversations are in no export.

Defaults under `memoryos.chat.stream`: 16 MiB per reply (`run-bytes`), a 60-minute TTL refreshed by each write, 10 minutes (`done-ttl`) of retention after the outcome, 16 KiB text chunks or 25 ms flush, 256 KiB read batches, 200 ms poll interval, 4 readers/reply and 64/process, 15-second heartbeat and 10-minute connection timeout. Bytes count the event JSON. Past `run-bytes` the writer adds one `truncated` entry and stops appending, as Onyx; readers that reach it reset. A slow reader holds no writer memory. Staging Redis runs without `maxmemory` and is shared with the ingestion queue; the Chat bound is `concurrency` × `run-bytes` of live replies plus completed replies for `done-ttl`.

The browser caps each SSE connection at 65 s and resumes from the last sequence it applied until the outcome, as Onyx's `resumeInFlightRun`. A connection that ends without an outcome, including one that delivered only heartbeats, reconnects at once and keeps the streaming state, so a Deep research agent that works for minutes without an event is not shown as reconnecting. A failed connection (network error or HTTP 5xx) backs off from 0.5 s doubling to 10 s and shows the recovering state until the next event; while the browser reports itself offline it waits for the `online` event. A `reset` event or a sequence gap switches to polling the saved reply while it is RUNNING, and polling applies the committed answer only when the turn ends. HTTP 401/403/404 fail closed as above.

Maintenance and flush use two Spring-managed virtual scheduler threads so a DB reconciliation wait does not block flushing. Chat executors are excluded as default candidates, preserving Boot's application executor. The existing Nginx honors `X-Accel-Buffering: no`; responses use `Cache-Control: no-store, no-transform`. The generated SSE SDK is retained, while the parser excludes this operation from TanStack query generation because its cursor represents a stream, not page fetching. PostgreSQL history and lease reconciliation remain authoritative; Redis holds only replay.

The API connects to Redis through `spring.data.redis` (`MEMORYOS_REDIS_*`, TLS through the `memoryos-redis` SSL bundle on staging) as ACL user `memoryos-api`, limited to `memoryos:chat:stream:*` keys and `XADD`, `XRANGE`, `XREVRANGE`, `PEXPIRE`, `DEL` and `EXISTS`. Development shares the worker's Arconia Redis dev service. There is no in-memory fallback.

Configuration: MEMORYOS_CHAT_API_KEY (fallback SPRING_AI_OPENAI_API_KEY) and optional MEMORYOS_CHAT_BASE_URL supply server-side provider access. Missing credentials reject a new send before reservation while history/cancel and other capabilities remain available. The OpenAI adapter takes an explicit options family; it does not require a GPT-5 model name. gpt-5-mini remains the live baseline, not certification of every compatible or local model. Execution defaults are concurrency 8, no total deadline, six cycles (Onyx `MAX_LLM_CYCLES`), a 1024-token answer reserve (`max-output-tokens`, Onyx `GEN_AI_NUM_RESERVED_OUTPUT_TOKENS`), no deployment context cap (input follows the model window with a 5% margin; see [model binding](chat-models.md)) and 1000000 answer characters. As Onyx `llm_loop` passes no `max_tokens`, the answer request is bounded only by the selected model's catalog `maxOutputTokens`; `max-output-tokens` only reserves room for the answer when the input budget is computed, because reasoning tokens count toward the request limit and a small cap cut long tool calls off. An OpenAI Responses stream that ends `response.incomplete` ends the turn like Onyx (LiteLLM finish reason `length` for `max_output_tokens`): the streamed text is kept, a cut-off function call is not run, and the reason is logged; `response.failed` and error events still fail with `CHAT_INCOMPLETE_RESPONSE`. Token and cost budgets are unset by default, meaning no cap; setting `memoryos.chat.execution.token-budget` or `cost-budget-usd` applies it through native Budget, and a monetary cap requires configured input/output pricing. Basic pricing does not certify cached-token billing parity. Provider transport has automatic retries disabled.

A nonblank provider finish reason, including length, ends an answer normally when text exists; empty answers fail with CHAT_EMPTY_RESPONSE. EOF without terminal metadata fails and keeps partial text. Incomplete tool arguments at a length boundary must not execute. Safe failure codes and exception class names provide diagnostics; prompt/provider exception payloads are never logged. Send returns stable message IDs, and history carries the authoritative status used for reload.


## Grounded Chat — Phase 3.1

The backend registers `search_knowledge` through Embabel `@LlmTool`/`Tool.fromInstance` for tool-capable bindings. Every Chat tool name is snake_case (`search_knowledge`, `web_search`, `open_url`, `search_files`, `read_file`, `generate_image`, `edit_image`, `run_python`); answers saved before the `search_knowledge` rename keep `searchKnowledge` in their activity, which the timeline still renders. Arguments contain one to three focused queries and optional explicit source/date filters. Two native helpers produce semantic and keyword expansions once per turn; later calls omit this expansion unless entering a previously unsearched source type. Tool queries and the original question remain. RRF k=50 sums semantic (1.3), keyword (1.0), tool (0.7) and original (0.5) contributions, including duplicate roles within a group: semantic/tool/original with identical text totals 2.5. Up to eight grouped queries retain separate weights; identical text shares embedding/hybrid IO. Both groups use the configured hybrid pipeline with the server's default 50/50 lexical/vector weights. The tool's `hybrid_alpha=0.2` does not override that pipeline mix.

Retrieval checks current source eligibility and generation before titles/content/metadata reach any model or event. Adjacent hits merge by document/generation before candidate limits. Selection sees at most three chunks around each section's best-ranked anchor plus permitted source/date/author metadata under a total token budget. Search prompts are the reference prompts verbatim except for their typed output lines. As in the reference, out-of-range selection ids are skipped, an empty, unparseable or entirely invalid selection falls back to the top-ranked candidate sections, and a NOT_RELEVANT classification keeps the selected main section, so a query that only names a document is not answered as if no document exists. The source scope is decided per search cycle from the last five user turns, this cycle's queries and previous cycles, restricted to the persona/tool sources, and latches off for the turn once no source is named; a scoped result carries a note naming the covered sources and queries. The time decision runs once per turn and returns created or updated with inclusive date or relative-offset bounds; a start after today and an end on or after today are dropped, and the end covers its whole day. Malformed optional author JSON yields no author and does not drop otherwise eligible documents. Reading progress bounds titles to 255 Java characters without splitting a surrogate pair; final citation titles retain their existing limit. Selected sections first read two neighbors around their full boundaries; separate typed classification chooses NOT_RELEVANT, MAIN_SECTION_ONLY, INCLUDE_ADJACENT_SECTIONS or FULL_DOCUMENT. FULL_DOCUMENT reads at most five neighbors per side and never widens when no neighbor exists. Expanded overlaps merge before bounded evidence/citations. Expansion reuses the authorized search set and checks generation; independent source previews check current permission.

`ChatPrompts` and `SearchPrompts` are MemoryOS-owned prompt contracts for registered tools and native structured output. The default Persona instructions are configurable through `memoryos.chat.persona.instructions`; the current UTC datetime placeholder resolves into the in-memory turn setup. Inference guidance derives from actual request tool callbacks: internal versus public sources, freshness, complementary queries and reputable primary pages. Every callable tool contributes its own block under a single `# Tools` heading: the knowledge base, `web_search`, `open_url`, the attachment pair `search_files`/`read_file` and `generate_image`; a tool absent from the request is never advertised. When `search_knowledge` is callable, an explicit request to answer from existing, connected or internal documents, a named internal Source/provider or a named document must search before answering; absent evidence is reported rather than replaced by general model knowledge. This provider-neutral instruction hardens the Onyx automatic-tool baseline after a Search-ready SharePoint turn completed without a tool call; it does not add provider-specific `tool_choice` behavior or claim protocol-level forcing. Evidence that answers only part of a request is answered in part: the uncovered part is named, never completed from general knowledge even when a law, a standard or common practice would give the same answer, and adjacent evidence is introduced as the nearest thing found rather than as the answer. A citation may not carry a statement its document does not support. The MEM-141 benchmark found replies that answered their half and then asserted the other half — a charter threshold, an appointment authority, once a figure the document contradicts — because a statutory default reads as general knowledge; its `cross_department` category is the regression test (`ChatGroundingPromptTest`). `web_search` queries are normalized (control characters and padded whitespace) before validation, while `open_url` still rejects a malformed URL. A recent `web_search` tool response triggers an open-page reminder only when `open_url` is available and another tool cycle remains; sufficient snippets do not require opening a page. Historical search before a new user message does not trigger it. Inference requests also receive inline citation reminders once evidence exists and a final-cycle reminder when tools are disabled. Guidance preserves Persona instructions and does not modify the stored transcript or user message. Unavailable tools are not advertised.

`memoryos.chat.search` configures, with Onyx's sizes, candidates (50 merged sections, `NUM_RETURNED_HITS`), sections (10 selected), selection-tokens (25600: `MAX_CHUNKS_FED_TO_CHAT` 25 x 512-token chunks x `SELECTION_TOKEN_BUDGET_MULTIPLIER` 2), helper-timeout (60 seconds per helper call), auto-detect-filters (true), and cleanup-timeout (1 second, positive and at most 5 seconds). Helpers use the selected native binding/process with no tools and `withoutThinking()`; the adapter applies the supported helper reasoning effort after native conversion, independently of answer settings. See [model options](chat-models.md#credentials-and-provider-extension). Two native binding attempts remain allowed, within one helper deadline. As Onyx, neither search calls nor their helper inferences have a count of their own: `max-cycles` (Onyx `MAX_LLM_CYCLES`, 6) bounds tool work, with the optional token and cost budgets. Missing native usage leaves accounting unknown. Parallel requests reserve input/output token and known cost allowance before IO; native Embabel records usage once. Unknown/failed requests retain their allowance. The stream cycle/final-tools-off limit remains separate.

Tool-capable turns reserve up to 4096 input tokens (at most one third of the configured input limit) for tool context. The full transcript remains unchanged in PostgreSQL. The guard counts text, tool arguments/results, reminders and tool schemas before provider inference. Helpers bound history/candidate/neighbor text; truncation is marked. As Onyx, selected evidence is bounded by chunk count, not tokens: at most 10 sections, each widened by at most five chunks, then by the context the model has left. Invalid rewrites retain a valid original/tool query; invalid selections fall back to ranked candidate numbers; invalid classifications retain the matching passage. Model-invented document IDs are never accepted. Empty evidence and unavailable search produce distinct tool results; cancellation and budget failures cannot trigger fallback.

Blocking tool continuations run on a bounded scheduler outside provider IO threads. Independent rewrite/filter, hybrid, and expansion/classification phases each use at most four concurrent tasks, propagate observation context, and preserve input order. Failures cancel siblings. Stop and lease loss seal admission to queued/running tool and native helper work and interrupts running bodies. SearchTool waits up to cleanup-timeout for actual completion, including native usage recording. If IO ignores interruption, the terminal outcome can still be persisted; its usage/cost stays unknown. The native process, model-client lease and execution slot remain owned until that work actually exits. Late work cannot start another provider attempt or publish progress, citations, text or updated terminal accounting. This retains backpressure instead of admitting unbounded abandoned work; a permanently stuck provider consumes its slot until process restart. Helpers use their own timeout covering native binding attempts. Web tool batches are bounded to 30 seconds, file reads and attachment materialization to 60 seconds, and image calls by the image client's connect and response timeouts. The provider may charge work already accepted. Existing partial/terminal winner and RAM replay semantics remain.

V34 adds only `chat_message.sources`, a JSON array. V64 removes its 24-entry cap and bounds it to 1 MiB, as Onyx has no citation count cap; evidence past that estimated byte bound is not registered. Each entry contains a turn-local `citationId`, document/generation IDs, title, inclusive ordinal range and per-chunk provenance. Overlapping/adjacent passages are merged; repeated identical evidence reuses its citation number. The model is instructed to cite `[n]`. Source metadata identifies supplied evidence; it does not by itself prove that every sentence or model-produced citation is supported. The browser transforms prose citations and resolves them only against the current message's server-owned sources. Inline/fenced code is preserved and unknown citations remain plain text. Resolved prose citations are compact numbered title chips with an excerpt on hover or keyboard focus. The Sources action beside Copy opens an answer-specific right panel on desktop; selecting a source or clicking its inline chip opens the inclusive cited range in that panel, with Back to sources and focus restoration. Mobile uses a modal right drawer with keyboard focus containment. The open panel follows the selected message in native runtime state as sources arrive. Chat and Search share `DocumentPreviewContent` and the generated document reader; Search retains its dialog. Source list excerpts and hover previews load from that same reader when displayed, using the requested generation, with no new endpoint or persisted excerpt. Full document preview queries use zero stale time and release data after the last observer closes. Excerpts use a separate 30-second cache keyed by Actor, authorization version, document, generation and read window; repeated hovers reuse it, while opening the reader always performs its own current read. A first source-list opening can still read up to the bounded source count (24); no unmeasured performance guarantee is claimed. An unavailable source does not remove the historical answer.

MEM-87 adds presentation metadata to each stored source without a migration: `mediaType` (document media type, or the file descriptor's for file citations), `sourceTypes` (distinct Source types of the actor-readable mappings when cited) and `providerUrl` (Google Drive's `https://drive.google.com/open?id=<providerFileId>` for the first readable Drive mapping, null otherwise). Web sources carry none of them; answers saved earlier omit them and render the generic document icon. They describe the evidence at answer time and grant no access: the provider enforces its own permissions when the link opens, and MemoryOS readers still recheck current authority. The browser accepts only that exact Drive URL shape.

Inline citations render a neutral chip with a file-type icon, the citation number and the truncated title (a Web citation shows its favicon when available and the hostname instead of the page title; its hover card shows the title and full URL); the chip is `aria-current`, with an outlined state, while its evidence is open. Hover/focus previews and the evidence header show the title, then `Source n · type · provider · page/sheet`, where location comes from chunk provenance (Docling `page_no`, spreadsheet `sheetName`) and the provider name itself is the Google Drive link when `providerUrl` exists; panel list cards are buttons, so they show the same meta as plain text. A document citation whose media type is PDF and whose provenance records pages offers `Passages | PDF pages` tabs; passages open first, except for a table row (provenance `tableRow`), which opens on its PDF page because the passage text flattens the columns (owner decision 2026-09-15). With more than one source, the open source's header shows `Source n / total` with previous/next buttons that keep focus. On a wide panel an expand button opens a document citation in the large preview dialog with Chat authority (Chat passage and original endpoints); the panel shows a note meanwhile, so one reader and one pdf.js document exist, and closing returns focus to the button with the same evidence tab. The PDF view lazily loads pdf.js, reads `GET /api/chat/documents/{documentId}/original?generation=` (membership plus current Document eligibility, like the passage reader), shows the whole document opened at the first cited page (pdf.js reads it by HTTP range with streaming and pre-fetching disabled, in 1 MiB chunks; only pages near the viewport render, others are sized placeholders; a failed range load falls back to one whole read and is reported to Sentry as workflow `pdf-view`; scanned images decode through the self-hosted pdf.js JBIG2/JPEG 2000 JavaScript fallbacks passed as `wasmUrl`), with a current-page counter, a "Back to cited passage" action once the reader scrolls to an uncited page, fit/150/200/300% zoom that keeps the current page, and highlights the Docling boxes with a multiply-blend highlighter that keeps the cited text legible; rotated pages render without highlights.

Sources and `activity` commit atomically with the assistant's content and terminal outcome, including partial canceled/failed answers; a losing terminal write cannot replace them. V59 `chat_message.activity` (constraint added `NOT VALID`, validated by V60) holds at most 32 steps `{position, toolCallId, toolName, status, startedAt, durationMs, textOffset, queries, filters, documents, citations}` and at most 32 reasoning segments `{position, textOffset, text}` (16,000 characters in total plus a truncation marker), bounded to 131,072 bytes and allowed only on assistant rows. Summaries are allowlisted, never raw tool arguments or results; queries are cut to 500 characters, and detail is dropped from the latest steps first when the history would exceed its budget. Steps still running at the terminal outcome are recorded as failed. `position` orders steps and reasoning together and `textOffset` is the answer length when the item started, so history rebuilds reasoning, tool and text parts in streamed order. Legacy rows return empty activity. History returns `sources` for every message (empty for user messages and legacy answers). Source metadata has no live document FK and no transitive ACL check on conversation history: an update/delete does not rewrite an old answer or grant permission to open the current document.

SSE `tool` events carry `{assistantMessageId, sequence, toolCallId, toolName, stage, source, search, documents, durationMs}` for every tool; `STARTED`, `COMPLETED` and `FAILED` apply to all tools and `durationMs` only to terminal stages. SSE `reasoning` events carry `{assistantMessageId, sequence, text}` from providers that expose reasoning. SEARCHING publishes at most eight actual query texts and effective source/time filters before retrieval. EXPANDING publishes at most ten authorized selected document ranges before reading neighbors. These reading candidates are separate from final citations. STARTED, SELECTING, SOURCE, COMPLETED and FAILED remain; `source` is non-null only for SOURCE and `search` only for SEARCHING. Events share the text/outcome sequence, replay byte limit and TTL. Native tool IDs correlate them. The transport deduplicates replay by sequence and carries tool progress in the tool part input, because the assistant-ui AI SDK converter treats any tool output as completion. The UI groups adjacent reasoning and tool parts with `MessagePrimitive.GroupedParts` into one activity disclosure: it stays open while the assistant works and names the current phase; each step shows one scoped label (search filters read as "in Uploaded files (since date)", `read_file` names the file) and chips only: queries, then documents being read or the evidence it returned, with the first four and "+N". Steps carry no citation numbers, per-step durations or nested disclosures. Once the answer starts it collapses to "Thought for {duration}" ("Stopped thinking" for a canceled or failed turn) with a step count, following the Onyx timeline header. A step without a result fails when its turn is no longer running. Buffer loss restores final sources and committed activity from history without fabricating intermediate progress; tools the stream never finished take their committed status. Terminal outcome still follows the DB commit.

Native tool observations keep timing, tool name and status. Search phase observations and `memoryos.search.stage.duration` timers distinguish prefetch, semantic/keyword rewrite, source/time filters, embedding, hybrid IO, authorization, fusion, selection, expansion and classification. Concurrent tasks retain the parent observation context. Tags contain bounded stage/outcome values, never questions, document metadata or identity. An ordered handler strips sensitive tool values before start/error handlers; a filter strips result/payload/error text before stop. Content-bearing Embabel loggers are disabled and Spring AI content capture remains off.

Current source policy remains PUBLIC FILE. Restricted/provider principal ACL metadata and permission-aware top-k await the source authorization implementation. The opt-in grounded model corpus check and its recorded result are separate from fixture contracts; neither establishes broader ranking quality or browser citation acceptance.

## Deep research

Deep research mirrors Onyx `160f9b143` (`dr_loop.py`, `research_agent.py`); recorded departures are in the [MEM-101 design](../increments/completed/mem-101-deep-research/design.md#departures-from-onyx).

- Entry: `deepResearch: true` on Send/Edit/Regenerate while the Tenant `deepResearchEnabled` setting is on (see Web search above for the setting and replay identity). Admission also requires a tool-calling model with a context window of at least `memoryos.chat.research.minimum-context-tokens` (50,000) and a chat outside Projects; otherwise `CHAT_RESEARCH_UNAVAILABLE`. Research uses external Web tools even when the model hosts search, and only when the turn has Web search on.
- Phases (`ResearchExecutor`), one guarded `streamInference` each, prompts ported verbatim in `ResearchPrompts`: clarification with only `generate_plan` (skipped when the parent assistant message was a clarification; a text answer ends the turn as a clarification), a streamed plan, orchestrator cycles with required tool choice (`research_agent`, `generate_report`, and `think_tool` for non-reasoning models; 8 cycles, 4 for reasoning models; report forced at 30 minutes or the last cycle), and a final report streamed as the answer. Research agents (≤3 per cycle, parallel through `SearchTasks`) start from their task only, call `search_knowledge`, `web_search`/`open_url` and, with attachments, `search_files`/`read_file` directly, stop at `generate_report`, 12 minutes or their cycle limit, and write an intermediate report. A timed-out or failed agent answers the orchestrator with the Onyx timeout or failure message.
- Guards: every research inference runs through its own `ChatModelGuard` in research mode (prompts unchanged, hard cycle bound), all sharing one `ChatAdmissionLedger` for the turn's token and cost budget. Research input is bounded by the model window minus the report tokens, not the normal-answer context limit. Stop cancels every agent and provider call.
- Citations: each agent numbers its own evidence; after a cycle its cited sources merge into the turn sources by source key and its report markers are renumbered. There is no source count cap on any Chat turn.
- Stream: `research-plan`, `top-level-branching`, `research-agent-start`, `intermediate-report` and `intermediate-report-citations` events; research agent calls carry `tabIndex` and their steps and reasoning carry `parentToolCallId`. Agent-local `SOURCE` events are not streamed; merged sources arrive as `SOURCE` events of the agent call.
- Persistence (V67, V68): the terminal finish writes `is_clarification`, `research_plan` (≤100,000 characters) and `research_agents` (≤64 agents, 4 MiB; cycle, tab, task, status, duration, intermediate report, citation mapping and the agent's own activity) with the answer. History returns them as `research`. Agents still running at the outcome are saved as failed; over the byte budget the latest agents lose their reports first.
- Web: a composer Deep research toggle (outside Projects, while the setting is on) sends `deepResearch`; the transport folds research events into one `data-research` part rendered as the plan and one tab per parallel agent above the answer, and history restores it.
- Telemetry (`ResearchTelemetry`): span `memoryos.chat.research.phase` and timer `memoryos.chat.research.phase.duration` with `phase` and `outcome`; `memoryos.chat.research.cycles`, `memoryos.chat.research.agents` (`outcome`) and `memoryos.chat.research.forced.reports` (`scope`, `reason`). No content in labels or spans.

## Image generation

Image generation is a per-tenant provider connection that mirrors the Web search stack: model managers (MODELS_MANAGE) configure, test and select one image provider under `/api/chat/images` (`chat_image_connection`, credential stored like other provider credentials), and generation itself is gated by IMAGE_GENERATE. Implemented adapters are `OPENAI_IMAGE` (OpenAI Images) and `CLOUDFLARE_WORKERS_AI` (Workers AI, e.g. `@cf/black-forest-labs/flux-1-schnell`); adding a provider is a new enum value, a `case` in `ImageProviderClient` and a migration that widens the provider CHECK. Provider errors, credentials and raw bytes never reach the model or UI.

`GET /api/chat/images/providers` returns the backend-declared catalog for model managers: per provider the credential requirement, default/required endpoint, the fixed edit model when the provider has one (Cloudflare), and the known models with display name, output media type, declared sizes, edit support and deprecation. Catalog entries cover only models the adapter serves end to end; a model outside the catalog can still be typed manually. Saving a connection rejects a blank endpoint when the provider requires one, and a bare 32-hex Cloudflare account ID expands to its account endpoint before validation. The `/admin/image-generation` page renders this catalog for `MODELS_MANAGE`: the in-use provider, per-provider cards for disconnected/connected/in-use states, endpoint and KEEP/REPLACE key entry, catalog or manual model choice, connection testing, selection, disabling generation, and disconnecting a provider with an optional replacement. The test sends the dialog's unsaved endpoint/model/key to `POST /api/chat/images/connections/{provider}/test`, which validates and generates one real provider request without persisting anything; a blank key falls back to the stored credential, and a bodyless call tests the saved connection. Disabling generation also disables editing because both share the active connection.

A turn carries an image mode (`off`/`auto`/`required`, browser preference only; the API re-authorizes every command). When it is not `off` and the selected model supports tool calling and an active connection resolves, the model gets a `generate_image` tool; the tool takes `prompt` and an optional `shape` (`square`, `portrait`, `landscape`) that the backend resolves to a catalog-declared size of the configured model — an unknown shape is refused before any provider call, and a model without declared sizes ignores it. The tool generates one image, stages it through `ObjectWriteService` (stage → adopt) into a `chat_image_artifact` row on the assistant message, and streams a `ChatImageEvent` (`GENERATING` → `COMPLETED` with the artifact `id`, or `FAILED`). Generated images serve owner-authorized bytes at `GET /api/chat/image-artifacts/{id}/content` (PNG/JPEG/WebP) and are returned on history messages as `images`. The composer keeps the image toggle row disabled with a notice while `GET /api/chat/images` reports no available connection; the active image state shows as a chip that toggles off when clicked. The assistant message renders each image with a develop reveal (clip + unblur) and a fullscreen viewer.

### Image editing

With image mode on, the model also gets an `edit_image` tool (`imageId`, `prompt`, optional `maskId`). The source is an image generated earlier in the same session, looked up with owner and session scope, or an image attached in the turn's context that the owner can read and that is READY; any other id is refused before a provider call. History names earlier images on their answers (`image_id`), and attached files already carry their ids, so the model refers only to ids present in the conversation. The source is decoded as PNG or JPEG with pixel limits and normalized to at most 1024 px on the long side, on multiples of 16. Cloudflare edits with `@cf/black-forest-labs/flux-2-klein-9b` (multipart `prompt`, `width`, `height`, `input_image_0`); OpenAI edits with `POST /images/edits`, adding `input_fidelity=high` for `gpt-image` models.

A mask is an attached PNG named `mask-for-<image_id>.png`: white may change, black or transparent stays, and its name chooses the image it was painted on. The provider edits the whole image and the server takes its result only inside the mask, feathered inward, so every pixel outside the mask equals the source. A mask that selects nothing is refused; one that selects the whole image is a whole-image edit. The result is a new `chat_image_artifact` on the current answer recording `source_artifact_id` or `source_file_id` (provenance only, no foreign key), streamed with the same `ChatImageEvent`; the `memoryos.chat.image.request` timer is tagged `operation` `generate` or `edit`. On a generated image the UI offers an edit action: an optional brush mask and an instruction go to the composer as the mask attachment and the message text, and image mode is turned on for the session.

## Code Interpreter

`run_python` follows the Onyx 40eb240df Code Interpreter. It calls the `memoryos-interpreter` service (`interpreter/`), which runs model-written Python in a disposable, network-less executor. Design decisions and phases are in [MEM-110](../increments/completed/mem-110-memoryos-interpreter/design.md).

- **Availability.** The tool is registered only when all of these hold:
  - the selected model supports tool calling;
  - `memoryos.chat.interpreter.base-url` is configured;
  - the Tenant has enabled Code Interpreter (`chat_interpreter_setting`; no row means disabled);
  - the service's `/health`, cached for 30 seconds, is ok.

  An unavailable interpreter omits the tool and never fails the turn. There is no separate capability: sending a turn (`CHAT_WRITE`) is enough. Model managers (`MODELS_MANAGE`) read and change the setting at `GET`/`PUT /api/chat/interpreter`, whose `revision` detects conflicts. Enabling is refused (503) when the deployment has no interpreter. `GET /api/chat/interpreter/health` returns the uncached `{connected, error, version}`.
- **Input files.** The tool stages the turn's READY attachments that the owner can read:
  - files named in the code come first, then the newest, at most 25 files and 100 MiB (at least one file is always staged), in chronological order;
  - names are sanitized and de-duplicated as in Onyx;
  - uploads stream from object storage and are reused within the turn by name and stored SHA-256;
  - files left out or failing to upload are listed in `staging_notice`.
- **Searched source files.** As Onyx `llm_loop.py` does after `internal_search`, when the tool is registered each `search_knowledge` call records the stored original behind its hits (any media type, at most 64 MiB, read through the same Chat citation authority as the source reader) and the next `run_python` stages them after the attachments, under the same caps. A staged file is named with Onyx `sandbox_filename_for_document`: the sanitized title with `_{storedObjectId}` before its extension; a title without an extension takes the stored file's. Its evidence then starts with the Onyx `FILE_ASSOCIATED_GUIDANCE` naming that file. A newer generation of the Document replaces the recorded file, and opening it for upload rechecks authority and the stored object.
- **Execution.** `POST /v1/execute/stream` runs with a fixed `timeout_ms` of 60 000 and an HTTP timeout 10 seconds longer, as in Onyx: a turn has no total deadline to subtract from. Stop and the tool-cycle limit bound a turn instead. Every `/v1` call sends the service `X-Api-Key`. The client reads the service's `output`/`result`/`error` events; unknown event names are ignored and only `result` ends a run successfully. Abandoning the read — a Stop or a listener that throws — closes the connection, which kills the executor container and frees the service's execution slot instead of holding it until the timeout.
- **Spreadsheets.** The executor ships LibreOffice Calc and `recalc-xlsx`, and the tool guidance tells the model to run it after saving an `.xlsx` with formulas: openpyxl writes formulas without values and xlsxwriter caches 0, so without it computed cells read as empty outside a spreadsheet application. It recalculates every given workbook in one LibreOffice start, in place, keeps formulas and formatting, and prints one JSON line per file with up to 20 error cells; `.xlsm` and `.xls` are refused.
- **Documents.** A model cannot see the file it just wrote, so a `.docx` built with `add_paragraph` alone arrives as one flat block: no headings, borderless tables, bullets typed as characters. The executor ships `check-docx`, which reports those faults as JSON (one line per file, naming the fix), and the tool guidance states the structure to use and tells the model to run the check and fix what it reports before answering. As the Anthropic docx skill does, the faults are named concretely rather than asking for a "professional document"; unlike that skill, nothing renders a picture for the model, so the report is text. Onyx instead has its Build session convert Markdown to `.docx` server-side, which this does not.
- **Output location.** Files are written to the current directory, `/workspace`. `/mnt/data`, where ChatGPT-trained models save by habit, is a symlink to it in the executor image, and the tool guidance asks for relative paths; before this, such a run failed with `FileNotFoundError` and the model spent further cycles retrying.
- **Result.** The model receives `{type: "python_execution", stdout, stderr, exit_code, timed_out, generated_files, error, staging_notice}`.
  - `stdout` and `stderr` are truncated to 50 000 characters.
  - `error` is `stderr` unless the exit code is 0.
  - A failed call (unreachable or busy service, an HTTP error with up to 2 KiB of its body, a stream error or a stream that ends without a result) returns `exit_code` -1 with the exception text as both `stderr` and `error`, as Onyx returns `str(e)`, and the step is recorded as failed. Interpreter file ids never reach the model.
  - When files were generated, the Onyx file reminder follows the JSON.
- **Generated files.**
  - Each workspace file of at most 25 MiB is downloaded, staged and adopted as a `chat_file_artifact` (V71) on the assistant message, then deleted from the service. Larger files are named in `staging_notice`.
  - `file_link` is `/api/chat/file-artifacts/{id}/content`, which serves owner-authorized bytes with `no-store` and `nosniff`: PNG, JPEG and WebP inline, every other type as an attachment.
  - The model links files with markdown `[filename](file_link)`. An answer body links only this exact path shape; every other relative path a model writes stays plain text.
  - Generated files are returned on history messages as `generatedFiles` and rendered as download cards below the answer, like generated images.
  - **Charts.** A figure the code leaves open is captured by the executor ([interactive charts](../increments/completed/chat-interactive-charts/design.md)) as a PNG artifact with E2B-model chart data (V72, at most 256 KiB). The model result lists `charts: [{title, type, file_link}]` without the data; generated files carry `chart: true` and the data is served owner-only at `GET /api/chat/file-artifacts/{id}/chart`. The answer draws line, scatter, bar and pie charts with Recharts in a card with an Interactive/Static toggle and shows the PNG for anything else.
  - A card's name, a `[file](file_link)` link in the answer and a message attachment chip open the file in a centered preview modal ([MEM-111](../increments/completed/mem-111-generated-file-preview/design.md)), following Onyx `PreviewModal`: variant-sized, with the Onyx header description, a floating footer (counts, image zoom, copy, download), PNG/JPEG/WebP/GIF images, PDFs in the pdf.js reader, CSV as a table, xlsx as one table per sheet, docx through `docx-preview` with DOMPurify-sanitized output, and code, JSON, markdown and text highlighted; text-like previews read the first 1 MiB and tables show 1 000 rows. A generated pptx shows its PDF rendering, converted by `pptx-to-pdf` (LibreOffice) in the interpreter executor on first preview and cached beside the file (V73), from `GET /api/chat/file-artifacts/{id}/pdf-preview`. Other types download. `GET /api/chat/file-artifacts/{id}/preview` and `GET /api/chat/files/{id}/preview` return an owner-private xlsx as `{sheets: [{name, csv, truncated}]}`, read with POI's streaming reader without evaluating formulas, each sheet cut at a row boundary past 500 000 characters as Onyx `parse_spreadsheet_for_preview`; other types are rejected.
- **Progress.** Besides the generic tool `STARTED`/`COMPLETED`/`FAILED` events, a run publishes SSE `code` events `{assistantMessageId, sequence, toolCallId, stage, code, output, files, stream}` with stages `RUNNING` (the code, at most 8 000 characters), `OUTPUT` (stdout or stderr, named by `stream`, as it is produced, at most 16 000 characters in total for the whole run; a failed call publishes its error text on stderr), `COMPLETED` and `FAILED`. A run that timed out or exited non-zero is `FAILED`, and both terminal stages carry the files the run produced. This is the one place the timeline carries a tool's own arguments and output; it is bounded so one run cannot exhaust the replay buffer. As the Onyx `PythonToolRenderer`, the step renders the highlighted code, stdout and stderr in separate sections, the number of files created and "No output" for a finished run without output. Code and output live only in the replay buffer: they are not committed to `chat_message.activity`, so a reloaded conversation keeps the step and the generated files but not the transcript of the run.
