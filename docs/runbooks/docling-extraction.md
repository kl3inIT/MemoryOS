# Docling extraction runtime

The base compose service pins Docling Serve CPU v1.32.0 by image digest. Models and EasyOCR English/Latin assets are baked into that same image. Worker `engine-revision` records the image digest in parser metadata; update it with the image for accurate diagnostics. It does not lock retry output or create a new Document version. Explicit FILE reindex runs extraction again and replaces the current reference after successful publication.

V12 is a dev/staging cutover: it copies the current version's metadata/reference to Document and removes version history, database text and processing-profile attempts. It does not require pre-migration reindex. Legacy documents without artifacts can use normal FILE reindex afterward; their raw input remains available. This migration intentionally discards the old derived text/history, as approved for these environments. No live environment has been migrated merely by editing this repository.

The local Compose service uses one conversion worker, no GPU, a read-only root filesystem and bounded `/tmp`. It is reachable only on the internal network and accepts file bytes/in-body results; it receives no Google or MinIO credentials. CPU 4 and RAM 8 GiB are initial enforced limits, not a measured capacity guarantee. A cold start loads models before `/health` becomes available. Requests default to EasyOCR `vi,en`; operators may explicitly select the optional Tesseract image and languages described in the [ingestion contract](../specs/ingestion.md#docling-deployment-environment). The service's default warm-up may also initialize RapidOCR. There is no runtime model download in the pinned image. These local image/resource facts do not establish the remote server's revision, installed models or capacity.

Java submits once through the asynchronous conversion endpoint, polls the same task and retrieves its result only after task success. It requests structured non-aborting errors but rejects failed, partial and error-bearing documents. Transport limits responses to 64 MiB and rejects redirects; canonical output remains limited to 32 MiB and text to 2 million characters. Default service limits are 100 MiB, 200 pages and 300 seconds. Worker defaults to `5m`, accepts an explicit budget up to `60m`, bounds individual HTTP exchanges to two minutes and observes for the document budget plus five minutes. Synchronous clients may still need coordinated `MAX_SYNC_WAIT`; the Worker does not use that endpoint. Full failure/retry rules live in the [ingestion contract](../specs/ingestion.md#extraction-routing-and-bounds). A stopped observer does not cancel remote processing or retain its task across Worker restart; check residual work before explicit replay. PostgreSQL claims fence publication, and local container resource limits bound only the local service.

For 100 MiB input, set the actual service's `DOCLING_SERVE_MAX_FILE_SIZE=104857600` and account for SDK base64 expansion: the file alone becomes 139,810,136 bytes before the JSON envelope. An Nginx ingress body limit of `150m` accommodates that envelope; a `100m` request limit does not. Verify the effective ingress and parser behavior after an authorized deployment rather than inferring it from repository defaults. Larger admitted files increase existing buffered-input memory pressure; admission is not a throughput or full-file OCR capacity guarantee.

For the approved shared-dev sixty-minute selection, the actual remote service needs `DOCLING_SERVE_MAX_DOCUMENT_TIMEOUT=3600` and, for any synchronous clients, `DOCLING_SERVE_MAX_SYNC_WAIT=3610`; Worker needs `MEMORYOS_EXTRACTION_DOCLING_TIMEOUT=60m`. An authorized operator must preserve/back up the real service and ingress configuration, apply the managed values, recreate the actual Docling service, validate and reload the actual ingress, then await readiness. Verify one-page timeout admission and bounded exact-size file admission before refreshing/restarting Worker and replaying a Source. Infisical readback proves desired configuration, not deployed configuration; local Compose changes cannot reload a remote host. Current rollout blockers are recorded in the [correction evidence](../tests/ingestion.md#tasco-corrections--2026-09-11).

## Local or authenticated remote runtime

Set `MEMORYOS_EXTRACTION_DOCLING_ENDPOINT` in the Worker's runtime environment. A direct Worker defaults to `http://localhost:5001`; Compose defaults to `http://docling:5001` and accepts an override from its environment or `--env-file`. Keep private remote addresses out of checked-in examples. HTTP on the user-authorized trusted VPN is intentional; credentials must not be sent over an untrusted network.

`MEMORYOS_EXTRACTION_DOCLING_API_KEY` is an optional managed Worker secret, bound to `memoryos.extraction.docling.api-key`. Empty/unset retains unauthenticated local behavior. The Docling Java SDK supplies `X-Api-Key`; do not put a key in the endpoint URL, parser configuration or command history. Property rendering redacts the key, parser metadata omits it, request/response logging stays disabled and redirects are refused. Store the current authorized key in Infisical **dev**, not staging. Compose deliberately does not interpolate this secret, including a blank default that could shadow managed injection. Restart Worker after endpoint/key changes; refresh the managed development cache through the existing launcher first when using IntelliJ.

Worker does not contact Docling on startup, and Compose no longer makes Worker depend on local `docling` health. For local extraction, explicitly start `docling` with the deployment's existing Compose files/environment (`up -d --wait docling`) and await `/health` before processing PDF/DOCX/PPTX. For a remote endpoint, establish VPN reachability and remote readiness before processing; selective Worker startup or the existing application rollout does not need the local service. A full Compose `up` still includes local `docling`; selecting a remote endpoint does not stop an already-running local container.

Set `MEMORYOS_EXTRACTION_DOCLING_ENGINE_REVISION` from the actual server's verified revision rather than retaining the local digest as a remote claim, and confirm that the chosen OCR engine/languages are installed. The current endpoint, optional key and observed engine revision were explicitly authorized in Infisical **shared dev**; developers using this baseline need the trusted VPN. Authenticated real conversion and isolated Worker DOCX publication passed after VPN recovery, and the retained Worker restarted successfully. See the [verification matrix](../tests/ingestion.md#authenticated-remote-docling--partial-runtime-verification) for measured evidence and its limits; these results do not establish remote whole-corpus capacity, financial fidelity or sustained-load acceptance.

## Local verification

Start the pinned image with the environment and limits in `compose.base.yaml`, on a loopback-only test port if needed. Set `DOCLING_TEST_ENDPOINT` only in the test process, then run the checked-in wrapper:

```powershell
$env:DOCLING_TEST_ENDPOINT = 'http://127.0.0.1:15062'
.\gradlew.bat clean check --rerun-tasks --no-build-cache --no-daemon
```

The connector service tests cover Vietnamese DOCX tables and scanned PDF OCR. The worker integration test switches its synthetic upload from TXT to DOCX when that endpoint is supplied, exercising Redis, PostgreSQL and MinIO end-to-end. Without it, the real-service tests skip and the worker exercises TXT; do not describe that run as Docling verification. Unit tests separately verify transport limits and typed failures.

Artifact cleanup runs each minute. `document_extraction_artifacts` tracks STAGED, ACTIVE and DELETING objects. A DELETING row with `write_complete=false` is an intentional tombstone for an uncertain PUT and is retried daily; do not delete it solely because the object is currently absent. Back up the private `extracted/` prefix with the database references. No new public artifact endpoint or separate operator UI is introduced.
